# 审查机器合同的端到端闭合

Type: prototype

Blocked by: 15 冻结 composition 与 deterministic fault seam

本文是过程审计证据，不是行为 authority。当前行为只由 `plugins/draft/docs/spec/` 下的正式 owner 页面定义；`.scratch` foundation、wayfinding 与本 issue 只记录 tracker、provenance 或闭合诊断，不能补出未签行为。

## Question

把已批准的领域合同、公共协议、状态/所有权模型、平台合同、时间/ID、canonical encoding、所有 durable schema、Handoff 协议和测试 seam 连成端到端控制流后，是否每个入口都从权威输入经过派生、副作用、失败、重试和恢复到达唯一可观察结果？是否还存在重复 authority、未定义状态、循环依赖、不可故障注入的分支或需要执行者自行选择的行为；哪些结论应进入 ADR、spec、总控计划或执行 ticket？

### 跨页闭合待决项

下列接缝必须在正式 spec 中补齐、更新 provenance 与消费者并获得所需 signer 批准后，才可移除 `unresolved`。如需记录取舍，ADR 只能解释理由，不得定义或覆盖行为。

1. `unresolved`: 一个 `operation_id` 跨 manifest、progress、content、catalog/head 和 `Outcome` 的语义关联已定义；其生成、intent/snapshot 比较集合、旧操作关联及 attempt/phase 的公开字段仍未定义。
2. `unresolved`: 每个领域入口纳入同一逻辑提交的 machine-zone/导航成员，以及 authority 已替换但 committed progress 缺失时的 `Outcome` 公开投影未定义；owner 已定义 authority/head 的逻辑提交门槛，不能由本表补字段或崩溃结果。
3. `unresolved`: `read` 的 snapshot token 编码，以及 `ReadOutcome` 的 token、projection、分页、warnings、blockers 与 partial 的字段名、可选性和顺序未定义。
4. `unresolved`: `notification` 的外部重试调度器身份、接口和退避策略，以及 warning/lifecycle result 的 envelope 顺序未定义；允许的 delivered 与所有 error 行排除 delivered 已由 owner 决策表定义。
5. `unresolved`: Trash/Restore package、receipt、attempt、catalog membership 的精确成员、排序与 cleanup record 字段未定义。
6. `unresolved`: move/promote/collapse 的 manifest mapping、自动 collapse 子阶段与领域 effects 的内部关联，以及 `Outcome` 完整字段集合未定义；owner 已定义单一完整、规范化、去重、确定的内部 mapping，且公开结果不暴露 mapping 或路径列表。
7. `unresolved`: `Outcome`/`ReadOutcome` 的完整字段集合、错误 envelope 与普通 JSON 的字段顺序未定义；领域 Outcome 边界、machine error/exit 语义和 mapping 的唯一派生关系仍只由正式 owner 定义。
8. `unresolved`: `RecoveryOutcome` 的前后 phase、epoch、cleanup state 字段 ABI，以及已认证 staging 的 Q20 orphan predicate/cleanup 范围和 Q21 progress 补记/公开投影未定义。已接受的 Q16/Q17 高层 disposition 语义不等同于 Q20/Q21 的 signer-approved 细分；无法认证或不匹配 staging 为 `runtime.corrupt`，不得与该 `unresolved` 分区合并。
