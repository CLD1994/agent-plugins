## 要解决的问题

D4 已确认五组正式关系。现在必须根据关系是否改变目标页面的当前理解，决定只保存正向标签，还是在目标页面同时保存明确的反向标签。

本页只决定关系保存方向。一个标签怎样列出多个目标，以及链接能否指向草稿网络外，继续分别讨论。

逐标签的具体检查流程和例子见 [D12.2.1 检查器如何逐个处理标签](12-2-1-checker-workflow-by-label.md)。该页当前是解释草案，用于在确认本页方案前暴露检查流程中的缺口。

## 第一性原理

关系表示需要同时服务于整图一致性和单页阅读。合适的方向应满足：

- Agent 不必猜该写正向还是反向；
- 不受影响的目标页面不机械保存无用反向标签；
- 页面被取代或受到未解决质疑时，不依赖全图查询就能看到事实；
- 检查器可以证明必须成对出现的标签彼此一致；
- 关系声明、父子导航和状态生命周期类别各自职责清楚。

## 三种路线

### A：所有关系都同时保存正反标签

父子、依赖、取代、质疑和产出全部在两端保存标签。阅读很直接，但 `被依赖` 和 `来源于` 不改变目标页面当前含义，会制造大量低价值同步内容。

这条路线过度维护。

### B：只把影响目标页面的反向事实写回

采用以下分层规则：

| 关系 | 发起页面保存 | 目标页面保存 | 处理方式 |
| --- | --- | --- | --- |
| 父子 | 子页面保存 `父主题` | 父页面保存普通子页导航 | 两端可读，只有 `父主题` 建立关系 |
| 依赖 | 需要前提的页面保存 `依赖` | 不保存 `被依赖` | 反向按需推导 |
| 取代 | 新页面保存 `取代` | 旧页面保存 `被取代` | 两个标签必须相互对应 |
| 质疑 | 质疑页面保存 `质疑` | 目标页面保存 `被质疑` | 两个标签必须相互对应 |
| 产出 | 已确认且当前未被取代的来源页保存 `产出` | 草稿内产出页正文汇总结论并链接来源页 | 只有 `产出` 标签建立关系，正文链接服务渐进阅读 |

这既避免把所有反向查询结果写进文件，也保证旧方案或受质疑方案单独打开时不会隐瞒当前事实。

这是当前推荐路线。

### 索引页和其他父页面仍然必须链接子页面

“父子关系只由子页面正式声明”不等于“父页面没有子页面链接”。父子导航仍然必须双向可见：

```markdown
# 索引页

> 状态：`当前提案`

## 子主题索引

- [D12 最小机器可识别结构](pages/12-minimal-structure-syntax.md)
```

对应的子页面保存唯一正式关系：

```markdown
# D12：最小机器可识别结构

> 状态：`已确认`
>
> 父主题：[索引页](../index.md)
```

因此，文件中确实存在两个方向的链接，但两者职责不同：

- 子页面顶部的 `父主题` 是机器判断父子关系的唯一权威声明；
- 索引页或其他父页面正文中的子页面链接，是人类向下阅读所必需的导航；
- 检查器从子页面的 `父主题` 得知谁是父页面，再验证父页面确实链接回这个子页面；
- 父页面单独出现一个普通链接，并不会自动把目标认定为子页面。

根 `index.md` 只是没有自己的父主题，并不是没有子主题索引。任何页面只要有直接子页面，就必须在正文中为这些直接子页面提供可见链接；安全改名或移动也必须同时修复两个方向的链接。

### C：作者按阅读方便任选保存方向

页面可以写 `依赖` 或 `被依赖`、`取代` 或 `被取代`。局部文字更自由，但工具无法知道两条反向声明是在重复同一事实，还是两个不同事实；Agent 每次也要重新选择方向。

这会把本应由协议消除的歧义交给维护者，不适合第一版。

## 为什么 `被取代` 和 `被质疑` 必须是标签

页面被取代，或者受到尚未解决的质疑，都是这个页面自身的当前事实。要求读者通过 Obsidian 反向链接或全图查询才能发现，会让单页阅读得到错误印象。

因此目标页面直接保存：

```markdown
> 被取代：[新方案](new-plan.md)
```

或者：

```markdown
> 被质疑：[并发反例](concurrency-challenge.md)
```

它们不是状态说明的解释附件，而是关系在目标页面上的明确结果标签。检查器要求 `取代 / 被取代` 和 `质疑 / 被质疑` 成对一致；任何单边出现都是客观结构错误。新增、删除或修复这种关系属于一次可恢复的多文件结构操作。

## 对抗性审查

- **双向标签会不会漂移？** 会，所以不能依靠人工尽力同步。结构工具必须成对更新，检查器必须把任一单边关系报告为客观错误。
- **为什么不让 `状态` 承担反向关系？** 程序只识别有限生命周期前缀，前缀不能说明是谁取代或质疑了当前页；明确的 `被取代` 和 `被质疑` 标签才保存关系目标，也不需要 `状态依据`。
- **为什么 `被依赖` 不同样写回？** 被其他页面依赖不会让当前页面失效，也不会改变读者理解当前结论所需的警告；需要时反向查询即可。
- **为什么产出页还要链接来源页？** 产出页是结论索引，需要让后续流程先读摘要，再按需深入原始论证。来源页的 `产出` 建立正式关系，产出页正文链接负责渐进阅读。
- **父页面的子主题索引会不会重复？** 它重复的是导航入口，不是第二份正式机器声明。检查器用子页面的 `父主题` 判定关系，再检查父页面是否存在可读的返回链接。
- **如果一个页面既质疑又取代另一个页面呢？** 这是两个含义不同的事实，可以分别声明，不能因为目标相同而合并。

## 当前建议

采用修正后的路线 B：父子关系使用子页面 `父主题` 加父页面普通导航；`依赖` 只保存正向标签；`取代 / 被取代`、`质疑 / 被质疑` 必须在两端成对保存；来源页保存 `产出`，草稿内产出页正文必须汇总并链接来源页，但不增加 `来源于` 标签。不新增 `状态依据`。

## 已确认结论

用户确认按影响分层保存关系：

- 父子关系使用子页面 `父主题` 加父页面普通导航；
- `依赖` 只保存正向标签，`被依赖` 由工具推导；来源页保存 `产出`，草稿内产出页正文汇总并链接来源页，不保存 `来源于` 标签；
- `取代 / 被取代`、`质疑 / 被质疑` 必须在两端成对保存；
- 不新增 `状态依据`，也不从状态说明中推断关系目标。
