## 要解决的问题

`依赖` 表示理解或修改当前结论前，必须先理解一个前置结论。如果 A 依赖 B，同时 B 又依赖 A，检查器应该把它当作错误、提醒，还是合法结构？

## 第一性原理

依赖关系描述的是阅读和决策顺序，不只是“两个页面有关”。合适的规则需要：

- 能给出一个实际可执行的起点；
- 不把普通的互相关联误写成互相依赖；
- 检查器只根据明确关系图判断，不理解自然语言；
- 出现问题时报告具体环路，但不擅自删除关系；
- 不为循环关系额外发明分组节点或求值算法。

## 三种路线

### A：任何依赖环都是客观错误

```markdown
# A
> 依赖：[B](b.md)
```

```markdown
# B
> 依赖：[A](a.md)
```

如果两页都要求先读另一页，就不存在满足声明的阅读顺序。检查器报告一条闭合路径，例如 `A → B → A`，但不猜哪条边应该删除。

真实含义若只是“两个问题互相影响”，应使用正文普通链接；若它们实际不可独立理解，应合并问题或抽出共同前提，而不是削弱 `依赖` 的含义。

这是当前推荐路线。

### B：依赖环只产生审查提醒

它允许维护者暂时保留环，但也意味着后续流程无法把 `依赖` 当成可靠阅读顺序。每个消费者都要重新判断某个环是否可以忽略，正式关系的价值会明显下降。

### C：自动把环折叠成依赖组

工具可以找出互相依赖的一组页面，把它们当成一个整体。但这会新增“依赖组”概念、组内顺序和展示规则，也掩盖页面边界可能划分错误的事实。

第一版没有必要建立这套机制。

## 检查器怎样处理路线 A

- 页面依赖自己，立即报告客观错误；
- 两个或多个页面形成闭合依赖路径，同样报告客观错误；
- 诊断至少列出一条完整环路和涉及页面；
- 检查器不自动打断环，也不把某条边降级为普通链接；
- 没有环时，工具可以按依赖顺序帮助 Agent 渐进读取页面；
- 页面状态是否已确认不影响环检测，检查器只分析明确的 `依赖` 标签。

## 对抗性审查

- **两个问题确实相互影响怎么办？** 相互影响不等于必须先完成对方。用普通链接记录关联，在正文解释反馈关系。
- **讨论过程中临时形成环是否可以接受？** 文件仍可人工阅读，但检查器不应把它报告为结构健康。维护 Agent 可以在同一轮讨论中修正页面边界或依赖方向。
- **环很长会不会难以理解？** 诊断只需给出一条闭合路径，不必枚举所有可能环路。
- **是否要求所有依赖目标已经确认？** 不要求。状态前缀虽然可识别，但依赖可以合理指向仍在讨论的共同前提；本页只决定图结构能否形成环，不额外规定依赖目标的生命周期。
- **为什么取代环和依赖环都报错，质疑环却允许？** 取代和依赖都隐含方向顺序；质疑只表示未解决反例，不要求先后顺序。

## 当前建议

采用路线 A：任何长度的依赖环都属于客观结构错误；检查器报告环路但不自动修复。

## 已确认结论

用户确认路线 A：任何长度的依赖环都属于客观结构错误。检查器至少报告一条完整闭合路径和涉及页面，但不自动删除、降级或改写关系。
