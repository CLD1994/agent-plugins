# D12.4：看起来像标签的未知行怎样处理

## 要解决的问题

D12 允许顶部引用块包含额外的人类说明，检查器忽略不认识的普通文字。D11 又要求未知关系类型能够被发现。

如果有人把 `被质疑` 误写成 `被质凝`，检查器不能既把它当成普通说明忽略，又声称能发现未知标签。第一版需要划清“普通说明”和“看起来正在声明结构字段的未知行”。

## 第一性原理

合适的规则需要同时做到：

- 拼错关系标签时不能静默丢失一条边；
- 新版本增加标签时，旧检查器不能假装结构正常；
- 人类仍能在顶部写一两句普通说明；
- 正文自然语言完全不受影响；
- 不为机器字段再引入 YAML、HTML 注释或旁置文件；
- 标签语法应当与当前中文示例一致。

## 三种路线

### A：所有未知行都忽略

```markdown
> 被质凝：[并发反例](challenge.md)
```

检查器把它当作人类说明。结果是页面在人眼看来像声明了 `被质疑`，机器却完全没有记录这条关系；对应的 `质疑` 只会表现成“缺少反向标签”，而其他可选标签的拼写错误甚至可能没有任何诊断。

这条路线失败得过于安静。

### B：保留“标签形状”，未知标签直接报错

规定顶部引用块中形如下面的行属于结构标签行：

```markdown
> 标签名：值
```

第一版已知标签为：

- `状态`
- `父主题`
- `依赖`
- `取代`
- `被取代`
- `质疑`
- `被质疑`
- `产出`

处理规则：

- 使用全角中文冒号 `：` 的“标签名：值”行会进入结构解析；
- 标签名不在已知集合中，报告未知标签客观错误；
- 已知标签误用英文半角冒号 `:`，报告标签格式错误；
- 不符合标签形状的普通引用文字继续忽略；
- 人类若要写“注意：……”之类带冒号的说明，应放在正文，或改写为不使用标签形状的完整句子。

例如下面的普通说明仍然合法：

```markdown
> 这是一段给读者的补充说明，检查器不会解释它。
```

这是当前推荐路线。顶部引用块本来就是机器结构区和简短人类提示的混合区域；只为“标签名：值”保留明确含义，代价很小，却能避免可选关系因拼写错误静默消失。

### C：给所有机器标签增加专用前缀

```markdown
> @被质疑：[并发反例](challenge.md)
```

前缀能彻底区分机器字段和普通文字，但会推翻已经确认并广泛使用的 `状态：`、`父主题：` 形式，使人类阅读更像配置文件。当前没有足够理由重写已确认语法。

## 检查器的具体反应

### 正确标签

```markdown
> 被质疑：[并发反例](challenge.md)
```

进入正常关系解析。

### 拼错标签

```markdown
> 被质凝：[并发反例](challenge.md)
```

报告“未知标签”，不猜它本来想写什么，也不自动修复。

### 已知标签使用错误冒号

```markdown
> 被质疑: [并发反例](challenge.md)
```

报告“标签格式错误”。程序可以指出这里像已知标签，但不能悄悄接受两套语法。

### 普通说明

```markdown
> 这段内容只提醒人类阅读，不参与机器检查。
```

检查器忽略。

## 对抗性审查

- **为什么未知标签是错误而不是提醒？** 它可能代表检查器不认识的新结构或拼错的重要关系。继续报告整体结构正常会产生错误安全感。
- **这会不会约束人类文字？** 只约束顶部结构块中“标签名：值”形状的行。正文完全自由，顶部普通完整句子也仍然自由。
- **能否自动把 `被质凝` 修成 `被质疑`？** 不能。相似拼写不等于相同意图；自动修复可能创造用户没有确认的关系。
- **未来增加新标签怎么办？** 新版检查器和 skill 一起升级。旧检查器看到未知标签应明确失败，提醒版本不兼容，而不是丢弃新语义。
- **为什么固定使用全角冒号？** 当前文档和中文标签已经统一使用 `：`。只接受一种分隔符能减少解析分支；英文命令、字段名或 URL 不受影响。

## 当前建议

采用路线 B：顶部引用块中的“标签名：值”形状保留给结构标签；未知标签和已知标签的格式错误属于客观错误；不具有标签形状的普通引用文字继续忽略。

## 已确认结论

用户确认路线 B：

- 顶部引用块中所有“标签名：值”形状的行都进入结构解析；
- 未知标签和已知标签的格式错误属于客观错误；
- 不具有标签形状的普通引用文字继续忽略；
- 检查器不猜测或自动修复未知标签。
