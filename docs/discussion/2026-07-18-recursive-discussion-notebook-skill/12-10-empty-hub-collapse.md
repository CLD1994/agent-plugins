## 要解决的问题

D12.9 已确认叶子页面产生独立子问题时，从 `topic-name.md` 升格为 `topic-name/index.md`。反方向也可能发生：最后一个直接子页被移动、合并或送入回收站后，枢纽目录只剩 `index.md`。

这里的“空枢纽”只表示没有直接子页，并不表示 `index.md` 没有正文。问题是：这个仍有内容的页面是否还应继续包在一个枢纽目录中。

## 先澄清当前是不是归档制

当前采用的是历史保留式草稿，通俗地说属于归档式管理：

- 已确认、已取代、已关闭和历史条件方案仍留在草稿网络中；
- `状态`、`取代 / 被取代` 等信息说明它当前是否有效；
- 讨论完成或方案被取代，不会自动删除页面，也不会自动把页面移出父主题树；
- 只有确认内容本身不应继续保留时，才通过插件临时回收区和系统回收站执行可恢复删除。

但它还不是一个拥有独立 `archive/` 目录、归档命令和迁移协议的正式“归档子系统”。更准确的叫法是“历史保留式草稿”。历史页面仍是草稿网络中的普通受管理页面。

因此，正常的讨论结束、确认或被取代都不会让枢纽变空。旧子页仍然存在，也仍然是子页。

## 空枢纽实际上怎样产生

健康结构中的非根空枢纽只会由结构变化或未完成的结构操作产生，常见情况是：

1. 把最后一个直接子页改挂到另一个父主题下；
2. 把最后一个直接子页的内容合并进其他页面，再将原页送入回收站；
3. 明确把最后一个直接子页送入回收站；
4. 手工修改文件，或者结构操作在中途崩溃，留下只含 `index.md` 的半完成结构；
5. 过早创建枢纽目录，实际子问题尚未创建成功。

并非所有重命名或移动都会产生空枢纽：

- 在原枢纽内重命名子页，子页仍然存在，不会变空；
- 移动或重命名整个枢纽目录，直接子页随它一起移动，也不会变空；
- 只有最后一个直接子页离开当前枢纽，才会形成空枢纽。

## 第一性原理

枢纽目录的唯一结构作用，是表示“这个页面拥有直接子页”。如果没有直接子页，`topic-name/index.md` 与普通叶子 `topic-name.md` 在语义上相同，多出来的目录不再表达任何事实。

允许它长期存在会带来三个问题：

- 文件树暗示这里还有下一层内容，实际进入后却没有子页；
- 同一种叶子页面出现两种物理表示，检查器和结构工具必须永久兼容无意义的歧义；
- 空目录包装会随着整理累积，使目录树不再可靠地反映讨论分叉。

原推荐路线担心自动降级会沿父链级联，这个推理不成立。把：

```text
parent/
└── topic-name/
    └── index.md
```

降为：

```text
parent/
└── topic-name.md
```

以后，`topic-name.md` 仍然是 `parent` 的一个直接子页，因此不会导致 `parent` 变空。降级确实要修复入站链接，但 D10.5 已经把改名、移动、链接重写、暂存检查和崩溃恢复定义为同一次安全结构操作。这是工具应完成的确定性工作，不需要 Agent 再判断一次语义。

## 三种路线

### A：最终状态禁止空枢纽，由原结构操作自动规范化

当一次移动、合并或回收操作会移走最后一个直接子页时，同一次可恢复结构操作必须：

1. 在暂存的新结构中把 `topic-name/index.md` 降为 `topic-name.md`；
2. 修复所有受影响的入站和出站链接；
3. 验证物理父子关系、`父主题` 和父页导航仍然一致；
4. 只有最终结构整体通过检查，才完成切换；失败时按操作日志恢复或保护现场。

操作中间阶段可以暂时为空；对外可见的完成状态不可以。若一次较大的重组先移走旧子页、随后又加入新子页，工具只判断整次暂存操作的最终状态，不在中间步骤反复升降级。

根 `index.md` 是整个草稿网络的固定入口，不适用降级规则。空枢纽的 `index.md` 也不会被自动删除：降级只保留原内容并改变物理表示。是否连这页本身也要回收，仍是独立的语义决定。

这是修正后的推荐路线。持续存在的非根空枢纽属于可以从文件事实直接判断的结构错误，而不是审查提醒。

### B：允许空枢纽暂时作为完成状态，之后显式降级

最后一个子页离开后先保留目录，由检查器提醒 Agent 再决定是否降级。

这曾是原推荐路线，但历史保留式草稿使它没有实际收益：正常归档不会清空子页；真正清空时，枢纽身份已经客观消失，不存在“近期可能还要不要它”的语义判断。它还把一次本可闭环的结构操作拆成两次，重新制造人类或 Agent 扫尾。

### C：空枢纽永久合法

它执行操作最少，但同一叶子概念会同时允许 `topic-name.md` 和 `topic-name/index.md` 两种表示。文件树不再准确反映讨论层级，长期只会积累无意义包装，因此不推荐。

## 对抗性审查

- **也许以后还会新增子问题，保留目录不是更方便吗？** 未来真的出现子问题时，再由安全结构操作把叶子升格为枢纽即可。为尚不存在的子问题提前保留目录，是用当前结构表达猜测。
- **自动降级是否暗中扩大用户操作？** 它会多移动一个仍有内容的页面并修复链接，但这是“移走最后子页”导致的必然结构后果。工具必须在执行前展示完整变更计划，并把它纳入同一恢复日志；不能静默执行不可见副作用。
- **如果 Agent 真想删除枢纽自身呢？** 先降为叶子并不替 Agent 作删除决定。回收这张叶子页需要另一项明确、可恢复且满足引用约束的操作。
- **崩溃后发现空枢纽怎么办？** 操作日志存在时优先恢复或完成原操作；没有可恢复日志时，检查器报告客观错误，由安全结构工具修复，不能把损坏状态长期合法化。
- **会不会递归降级整条父链？** 不会。空枢纽降为叶子后仍然占据原来的父子位置，上级仍有这个直接子页。只有另一项操作连这个叶子也移走，才需要重新判断上级。

## 修正后的当前建议

采用路线 A：历史页面继续留在原草稿树中；非根空枢纽没有长期语义。移走、合并或回收最后一个直接子页的同一次安全结构操作，必须把枢纽规范化为普通叶子页并修复链接。检查器把遗留的非根空枢纽报告为客观结构错误。

正式设计需要让 CLI 直接表达这两种结构变化：

- `promote ROOT PAGE CHILD [CHILD ...]` 把叶子 `PAGE.md` 升格为 `PAGE/index.md`，并在同一次安全结构操作中把至少一个已有页面改挂为它的直接子页；
- `collapse ROOT HUB` 只用于修复已经存在的空非根枢纽，把 `HUB/index.md` 降为普通叶子；
- 普通 `move` 或 `trash` 若导致最后一个直接子页离开，则自动调用与 `collapse` 相同的内部原语，不要求 Agent 再发第二条命令。

升格必须携带至少一个已有子页，因为完成状态不允许先创建空枢纽等待以后填充。需要新建子页时，Agent 先把它写成同一父主题下的合法叶子，再用升格操作一次完成结构变换和改挂。

## 已确认结论

用户确认修正后的路线 A：最终状态禁止非根空枢纽。导致最后一个直接子页离开的同一次可恢复结构操作，必须自动把枢纽降为叶子、修复链接并验证新结构；根 `index.md` 永不降级。检查器把操作完成后遗留的非根空枢纽报告为客观结构错误。
