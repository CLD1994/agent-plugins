# D13.1：结构格式版本不兼容时怎样处理

## 要解决的问题

D13 已确认 `.discussion-notebook/notebook.json` 第一版只保存 `format_version`（结构格式版本；代码字段保留英文）。这个字段只有在工具遇到不同版本时采取明确行为，才不是装饰。

本轮只决定三种情况：当前版本、工具认识的旧版本，以及比当前工具更新或完全未知的版本。具体迁移步骤留到出现第二个真实格式时再设计。

## 第一性原理

结构写操作会批量改名、修复链接和回收文件。工具只有在确切理解当前格式时，才有资格声称操作后的结构仍然正确。

因此，兼容策略必须优先保护两件事：

1. 旧工具不能猜测一个更新格式，然后用旧规则破坏它；
2. 新工具不能在普通写操作中悄悄迁移整个草稿网络。

`format_version` 应是从 1 开始递增的正整数，表示草稿结构版本，不等同于插件包版本。只有结构读取或写入规则发生不兼容变化时才增加它；修复程序缺陷或发布新 skill 不需要改变该数字。

## 三种路线

### A：只对当前版本开放写入，迁移必须显式执行

- **等于当前版本：** 运行完整结构检查，通过后允许正常写操作。
- **工具认识的旧版本：** 普通写操作拒绝；工具说明需要迁移。Agent 根据 skill 显式调用专用迁移操作后，CLI 按可恢复结构事务执行，最终才更新 `format_version`。
- **高于当前版本或完全未知：** 拒绝写入，也不声称完整结构检查通过；只报告“当前工具过旧或不认识此格式”，提示升级工具。
- **字段缺失、类型错误或非法值：** 在受管理模式下报告客观错误，不从目录内容猜测版本。

这是当前推荐路线。普通讨论命令不会附带隐藏迁移，旧工具也不会对新格式做“尽量兼容”的危险猜测。

### B：普通写操作自动把旧版本迁到当前版本

使用最方便，但一次本来只想移动页面的命令可能先改写整个草稿网络。用户难以预览影响，迁移失败也会和原动作失败混在一起。它违背 D10.5 已确认的“完整变更计划应当可解释”。

### C：对不同版本尽量继续读写

工具忽略不认识的字段或目录，只要常见部分看起来相似就继续工作。这适合宽松的数据交换格式，不适合承担多文件结构修改的维护工具。未知差异恰好可能是新版本必须保护的约束，所谓“尽量兼容”可能造成静默损坏。

## 对抗性审查

- **旧版本为什么不能继续只读检查？** 可以读取登记文件并提供有限诊断，但若旧格式的 Markdown 规则已经不同，工具不能把当前检查器结果说成完整健康证明。它只能运行该旧版本明确受支持的检查或生成迁移计划。
- **新版本是否至少可以让人类继续看 Markdown？** 可以。拒绝的是插件结构写入和虚假的完整验证，不是普通编辑器读取文件。
- **迁移成功前何时更新版本号？** 最后更新。暂存的新结构、链接和恢复信息全部验证通过后，才把登记文件切换到目标版本；不能先改版本再慢慢迁移。
- **每次插件发版都增加版本吗？** 不增加。只有结构协议发生不兼容变化时才增加，普通实现升级与 skill 文案变化不影响它。
- **以后真的出现版本 2 才设计迁移是否太晚？** 现在先固定拒绝和显式迁移边界已经足够。没有真实版本差异时提前设计通用迁移语言，只会猜测未来。

## 当前建议

采用路线 A：只有当前结构版本可以正常写入；已知旧版本只能进入显式、可预览、可恢复的迁移流程；未知或更高版本拒绝写入并提示升级。版本字段非法时不猜测。

## 已确认结论

用户确认路线 A：普通命令绝不自动迁移或猜测兼容。只有当前结构版本允许正常写入；已知旧版本必须进入显式、可预览、可恢复的迁移流程；未知或更高版本拒绝写入并要求先升级工具；版本字段非法时不从目录内容猜测。
