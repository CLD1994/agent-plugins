# D13.3：用户批准怎样绑定到具体变更计划

## 原问题

D13.2 区分了新建、接管和迁移。此前进一步提议建立“只读生成计划、用户批准、按单次计划编号执行”的协议，并继续讨论怎样证明批准者确实是人类。

用户指出这一方向已经进入过度设计。第一版的真实使用方式是：Agent 根据 skill 指导调用 CLI 维护草稿；遇到工具失败、语义不清或需要人类判断的情况，再由 Agent 与人类沟通反馈。

## 为什么原提案没有必要

原提案试图提前解决一个尚未出现的问题：把用户自己部署和使用的主 Agent 当成需要独立防范的恶意调用者。

当前已经存在足够的机械保护：

- `init`、`adopt`、`migrate` 是三个不会自动切换的入口；
- CLI 要求显式草稿根、登记文件和当前结构版本；
- 写入前执行结构与链接检查；
- 多文件操作由 D10.6 的内部变更计划、内容摘要、操作日志和恢复机制保护；
- 删除只能进入可恢复回收流程。

再增加公开计划编号、批准凭证、单次执行协议或独立授权服务，会扩大状态和失败路径，却没有当前用户需求证明其价值。

## 第一版最小边界

- skill 指导 Agent 选择正确的 CLI 命令并理解命令结果；
- CLI 自己完成路径限制、前置检查、内容摘要、崩溃恢复和结果验证；
- CLI 返回实际变更、拒绝原因或恢复状态；
- Agent 在遇到失败、歧义或需要设计判断时向人类说明并取得反馈；
- 是否在某次接管或迁移前先向人类展示影响，由 skill 根据上下文指导，不建立机器审批协议；
- 不实现公开计划编号、批准令牌、计划期限、签名凭证或独立授权服务；
- `--yes` 可以作为普通命令行交互便利与否另行决定，但不把它解释为安全凭证。

D10.6 的“内部变更计划”仍然保留，因为它解决实际的数据一致性和崩溃恢复问题；删除的是包在它外面的用户批准状态机。

## 已关闭结论

第一版不设计专门的批准绑定协议。Agent 按 skill 使用 CLI，CLI 保证机械安全；遇到问题或需要人类判断时，通过正常对话反馈。只有真实使用反馈表明这一边界不足时，才重新打开批准凭证或独立授权机制。
