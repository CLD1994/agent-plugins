# D13：工具如何确认一个目录是受管理草稿网络

## 要解决的问题

D10.4 已确认，新建或正式接管的草稿网络必须是一个自包含目录。D12 又确认了这个目录内部应具备 `index.md`、`conclusions.md`、`pages/` 和一棵可检查的父主题树。

但安全结构工具还需要回答一个更基础的问题：用户传入某个目录时，怎样确认它真的已经选择由插件管理，而不是一个恰好拥有相似文件名的普通文档目录？

这不是“怎样自动搜索草稿”的问题。本轮只决定受管理根目录是否需要一个明确登记事实。

## 第一性原理

结构相似不等于授权。`index.md`、`conclusions.md` 和 `pages/` 都是普通项目可能自然拥有的名字。若工具只凭这些名字认定目录受管理，错误路径仍可能通过结构检查，然后被改名、移动或送入回收站。

另一方面，登记信息不应复制 Markdown 中的讨论状态、父子关系或结论。那些内容事实仍只存在于 Markdown。登记只需要表达两件操作事实：

1. 这个目录已经被用户显式新建或接管；
2. 它采用哪个草稿结构格式，以便未来工具知道能否安全读取或迁移。

## 三种路线

### A：要求一个最小内部登记文件

`init` 或显式 `adopt`（接管；保留英文是为了对应未来命令名）在受保护的内部目录写入类似：

```text
.discussion-notebook/
└── notebook.json
```

第一版只保存结构格式版本，例如：

```json
{
  "format_version": 1
}
```

安全结构工具必须同时满足：调用者显式传入草稿根、登记文件存在且可识别、Markdown 结构检查通过。登记文件不保存标题、状态、父主题、页面清单或结论，因此不是第二份内容真相。

暂不加入永久 `notebook_id`。复制仓库、复制目录或分叉草稿时，复制出的相同 ID 会立即带来“它们到底是同一个草稿还是两个草稿”的新协议；当前没有功能必须依赖这个身份。

### B：只看目录结构，不保存登记

工具要求调用者显式传入根目录，并检查 `index.md`、`conclusions.md`、`pages/` 和全部 D12 规则。实现最少，也没有隐藏元数据。

问题是它只能证明“这个目录长得像草稿网络”，不能证明用户曾经选择让插件管理它。任何恰好满足这些结构特征的普通文档目录都可能被误接管；未来格式变化也只能从内容猜版本。

### C：从当前工作目录向上自动寻找相似目录

它调用方便，但进一步扩大误判：同一项目可能同时有多个草稿网络，当前工作目录也可能嵌套在错误的文档树中。自动向上搜索可以作为只读候选发现，但不应成为结构写操作的授权依据。

## 对抗性审查

- **登记文件是否违背“标准 Markdown 是唯一语法”？** 不违背。标准 Markdown 仍是所有人类内容与关系的唯一语法；JSON 只记录插件管理和格式兼容事实，不参与讨论图。
- **有登记文件就能跳过结构检查吗？** 不能。登记只能证明曾经显式接管，不能证明当前 Markdown 没有损坏。
- **用户手工复制整个草稿目录怎么办？** 复制品仍是一份已采用相同格式的草稿副本，这没有问题。因为第一版不保存全局身份，不会把两个副本错误合并为同一个运行状态。
- **为什么不现在加入稳定 ID？** 当前会话绑定仍可以保存明确路径；目录移动后由用户重新选择。没有跨路径自动追踪需求时，稳定 ID 只会提前引入复制、克隆和分叉语义。
- **能否直接手工创建登记文件？** 文件格式本身不是秘密。真正的 `adopt` 仍需先只读扫描、展示将被管理的范围并由用户确认；工具随后写登记并运行完整检查。

## 已确认结论

用户确认路线 A：新建或显式接管时写入最小 `.discussion-notebook/notebook.json`，第一版只保存 `format_version`。所有写操作仍要求显式草稿根和完整结构检查；不自动向上搜索，不复制 Markdown 内容事实，也不提前引入永久 `notebook_id`。
