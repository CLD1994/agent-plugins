# D13.2：新建、接管和迁移是否应当分开

## 要解决的问题

D13 要求草稿根经过显式登记，D13.1 又要求旧版本通过显式迁移才能写入。由此出现三个看起来相近、实际风险不同的入口：

- `init`（新建）：从零创建一个草稿网络；
- `adopt`（接管）：把已经符合当前结构、但尚未登记的目录交给插件管理；
- `migrate`（迁移）：改变旧布局或旧结构版本，使其符合当前格式。

本轮只决定它们是否必须保持不同操作。具体命令参数、交互确认方式和旧布局迁移算法继续单独讨论。

## 第一性原理

三个动作的真正区别不是命令名称，而是它们对已有内容作出的承诺：

| 操作 | 前置状态 | 是否解释已有内容 | 是否改写已有 Markdown |
|---|---|---|---|
| 新建 | 目标不存在或为空 | 否 | 否，只创建新骨架 |
| 接管 | 已符合当前结构但没有登记 | 只验证 | 否，只在最后写登记文件 |
| 迁移 | 旧布局或已知旧版本 | 是 | 是，可能移动页面和修复链接 |

把不同风险隐藏在一个“自动判断”入口里，会让用户无法在执行前知道工具准备做的是创建一个目录、登记现有内容，还是批量改写历史文件。

## 三种路线

### A：三个显式操作，各自拒绝越界输入

#### 新建 `init`

- 只接受不存在或空的目标目录；
- 一次创建当前版本的 `index.md`、`conclusions.md`、`pages/` 和最小登记文件；
- 目标非空时拒绝，不自动改走接管或迁移。

#### 接管 `adopt`

- 只接受没有登记文件、但已经完整符合当前结构的自包含目录；
- 先以候选模式只读检查，展示将被管理的目录范围；
- Agent 根据 skill 确认接管范围合适后，CLI 最后只写入当前 `format_version` 的登记文件；
- 发现结构错误、旧布局或旧版本时拒绝，不顺手修复或迁移 Markdown。

#### 迁移 `migrate`

- 只处理明确支持的旧布局或已知旧版本；
- 调用者必须显式给出来源格式，命令形态为 `migrate SOURCE --from FORMAT --to ROOT`，工具不根据“缺少登记文件”猜测格式；
- 第一版 `superpowers-sidecar-v0` 只接受不存在或空的新目标根，且目标不能与旧索引或同名子目录重叠；
- CLI 在写入前按 D10.6 生成内部完整变更计划，不在普通检查或写操作中自动触发迁移；
- Agent 根据 skill 显式调用后，CLI 按可恢复多文件操作执行；
- 目标根在迁移完成前不视为受管理草稿本；新结构通过候选模式检查后，最后原子写入当前版本的登记文件。第一版 `superpowers-sidecar-v0` 生成新目标根，不存在“更新旧目标版本”的动作。

第一版虽然没有旧的正式 `format_version`，但已有试点草稿需要一个显式、一次性的旧布局适配器：`superpowers-sidecar-v0`。它只识别“根目录中的 `*.tmp.md` 索引页，加上同名相邻目录中的子页面”这一已知布局。调用者必须明确写 `--from superpowers-sidecar-v0`，迁移器逐项解析已知的状态、字段和关系；遇到无法映射的内容时，在任何写入前停止并报告，不把未知历史格式猜成当前格式。

为保证它真的能够迁移当前试点，而不是只有一个空名字，适配器先让已经符合五个当前前缀或“当前前缀：非空说明”的状态原样通过。旧格式的 `已确认，说明` 和 `已关闭，说明` 把旧逗号规范化为当前全角冒号；三种完整的“历史候选 / 历史方案 / 历史条件方案，第一版不采用”、`未来安全前置条件，第一版不实现` 和 `时间记录，不参与产出` 都映射为带原说明的 `已关闭`。根索引的 `正式设计已生成，等待评审` 映射为 `已关闭`，`conclusions.md` 的 `已迁移为正式设计，等待评审` 映射为 `已确认`。恒等通过要求完整符合当前语法；只有两个已登记旧前缀允许携带任意说明，其他旧值与页面角色必须精确匹配，表外值拒绝迁移。

迁移保留并重写旧页面已有的 `产出` 和其他明确关系，最终按当前五状态和产出完整性规则检查。它不从正文句子推导新关系，也不替未知旧状态决定含义。

普通页面改名、移动、回收和内容维护命令都不能隐式调用这三个入口。

这是当前推荐路线。它让命令名字直接暴露风险等级，也使失败信息可以准确告诉用户“这个目录需要接管”还是“这个格式需要迁移”。

### B：一个 `setup` 自动识别并选择动作

用户只传目录，工具自行判断应该新建、接管还是迁移。入口最简单，但同一命令可能从“创建几个空文件”升级为“批量重写历史草稿”。即使执行前再提示，自动分类错误仍可能把本应只读接管的目录送进迁移流程。

### C：保留一个主命令，通过参数选择模式

例如 `setup --init`、`setup --adopt`、`setup --migrate`。只要模式必须显式选择，安全性可以接近路线 A；但帮助文本、权限说明和错误反馈都围绕一个含义过宽的命令展开。第一版没有共享交互流程必须用单一命令包装，分开更直接。

## 对抗性审查

- **接管时发现一个小断链，为什么不能顺手修？** 因为接管的承诺是“不改内容，只验证并登记”。一旦允许修复，它就变成了没有完整计划的迁移。应先由 Agent 或显式结构工具修好，再重新接管。
- **新建目标恰好已有一个空 `README.md` 怎么办？** 拒绝并让用户选择新目录或明确整理目标。自动忽略“看起来无害”的文件会逐渐形成不可解释的例外。
- **迁移是否一定是原地修改？** 第一版 `superpowers-sidecar-v0` 明确生成新目标根，并在最后写登记文件，不做原地修改。未来若为已经登记的旧 `format_version` 增加适配器，再单独决定它是原地升级还是生成新目标；两者都必须保持内部变更计划、恢复和最终验证边界。
- **接管成功前什么时候写登记文件？** 最后写。否则中途失败会留下“看起来已经受管理、实际结构未通过”的目录。
- **三个命令是否会增加学习成本？** 会增加三个清晰名词，但每个入口的效果单一。相比一个可能暗中切换风险等级的万能命令，这种成本更容易理解。

## 当前建议

采用路线 A：`init`、`adopt`、`migrate` 是三种明确不同的操作，并严格拒绝不符合各自前置条件的输入。普通命令永不隐式触发它们。

## 已确认结论

用户确认路线 A：`init`、`adopt`、`migrate` 是三种明确不同的操作。新建只创建空白结构；接管只验证并登记已经符合当前格式的目录；迁移才允许改写旧布局或旧版本。第一版登记一个明确的 `superpowers-sidecar-v0` 旧布局适配器，但仍要求调用者通过 `--from` 选择，不能自动猜测。三者严格检查自己的前置条件，不能自动互相切换，普通命令也不能隐式触发它们。

[D13.3](13-3-user-approval-plan-binding.md) 随后评审是否还要把用户批准绑定成专门的机器协议。用户认为该方向过度设计，因此第一版只保留 skill 指导、CLI 机械安全和正常的人类反馈，不增加公开计划编号或授权服务。
