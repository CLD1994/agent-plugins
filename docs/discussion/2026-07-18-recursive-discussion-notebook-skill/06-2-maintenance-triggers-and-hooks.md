## 已确认结论

维护由语义变化、结构变化和明确里程碑触发，不在每条消息后全面扫描，也不把上下文压缩当作自动语义整理时机。

1. **重要变化立即局部维护。** 用户确认、推翻或重新打开结论，新反例改变当前提案，问题产生独立分支，下一步变化，或者页面被拆分、移动、取代时，立即更新当前页、父级枢纽和状态受影响页面。
2. **结构变化立即触发机械检查。** 新建、拆分、移动或重命名页面后检查链接和父子导航；改变有效性状态后检查来源链接；达到容量警报值时安排语义拆分审查。
3. **压缩或恢复后只重新绑定 skill。** 生命周期入口注入短重新绑定信封，要求 Agent 确认或重新读取当前 skill；不复制原始转录，不自动整理历史。
4. **关键节点显式执行整体健康检查。** 长期讨论暂停或移交、大规模重组、准备生成迁移清单、发现结构异常，或者恢复长期中断讨论时，再检查整个草稿网络。
5. **已知异常显式恢复。** Agent 或用户知道上次运行异常中断时，只核对当前草稿与最近一小段可用转录；第一版不自动计算未知语义缺口。

不采用固定的按天或按对话轮数维护周期。讨论活动并不均匀，维护由真实变化和明确操作触发。

## 第一版明确不做

- 不注册 `PreCompact`（压缩前事件）钩子；
- 不在压缩前启动或等待专用维护 Agent；
- 不把钩子输入复制到插件待处理区；
- 不维护 `captured_through`、`processed_through`、`updated` 或 `no_change`；
- 不在压缩后自动读取原始历史；
- 不把平台转录镜像成插件自己的会话记录系统。

这些能力只有在未来出现无人值守自动恢复的真实需求时才重新评估。届时必须先建立明确的缺口边界，再讨论同步、异步或独立维护 Agent，不能恢复一个没有输入范围的空钩子。

## 为什么旧的压缩前子 Agent 路线被移除

旧路线试图在上下文被压缩前抢救尚未落盘的语义，因此需要保存增量、启动独立 Agent、等待或排队，并解决并发写入。

后续讨论确认：平台转录不会因为模型上下文压缩而消失；正常语义应在发生时立即写入；主 Agent 不应在压缩后重新加载大量历史；第一版也不承诺自动发现写入前崩溃形成的极短缺口。

在这些边界下，已经没有工作必须赶在压缩前完成。保留压缩前子 Agent 只会增加安装、延迟和故障面。

## 仍然保留的恢复能力

- 多文件结构操作使用耐久操作日志和内容摘要恢复；
- 页面删除先进入插件临时回收区，再移交系统回收站；
- 主 Agent 通过安全 CLI 执行改名、移动、回收和检查；
- 用户可以显式启动独立会话进行整体整理，但它不是压缩生命周期的一部分。
