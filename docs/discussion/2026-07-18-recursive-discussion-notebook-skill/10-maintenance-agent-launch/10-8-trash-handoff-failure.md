# D10.8：系统回收站移交失败的放行边界

## 要解决的问题

D10.7 已确认：删除包在整理期间安全存放于插件临时回收区；结构检查通过后，协调器立即尝试移交系统回收站。

但是系统回收站可能因为容器环境、挂载点权限、桌面服务缺失或平台接口错误而暂时不可用。此时草稿网络已经一致，删除内容也没有丢失，只是删除包还没有离开插件临时回收区。

需要决定这个外部移交失败是否推翻已经完成的草稿维护。

## 三种路线

### A：移交失败则整轮维护失败

只有系统回收站成功接收全部删除包，才写维护完成凭据。

语义最严格，但会把桌面环境故障变成主会话压缩阻塞。重试时还可能错误地重新运行已经完成的 Agent 语义维护，而真正需要重试的只是文件移交流程。

### B：区分“草稿已一致”和“系统移交待重试”

协调器立即尝试移交。失败时：

- 草稿维护仍记录为完成；
- 删除包继续安全保存在插件临时回收区；
- 单独记录 `trash_handoff_pending`（系统回收站移交待处理；保留字段名用于程序状态）；
- 明确警告本次移交失败；
- 允许主会话继续压缩；
- 下一次钩子、会话启动或显式维护时，只重试文件移交，不重新唤醒 Agent 做语义维护；由于系统回收站没有幂等回执，崩溃恢复重试可能产生可识别的重复删除包。

这不会把临时回收区变成长久存储。它只是承认外部系统当前不可用，并持续自动重试。

### C：静默保留，等以后顺便处理

不会阻塞主会话，但用户不知道系统回收站移交失败，临时删除包可能无声积累。它违反“异常必须可见”和“不能把临时区当长期回收站”的边界。

## 已确认结论

采用 B。草稿一致性与系统回收站移交是相邻的两个步骤，但失败影响不同：前者失败意味着维护没有完成；后者失败意味着内容仍安全、外部移交需要重试。

系统回收站移交失败时保留权威删除包并记录 `trash_handoff_pending`，释放草稿写锁，明确警告但不推翻草稿维护结果，也不阻止主会话压缩。后续重试先重新取得同一把草稿写锁，再制作投递副本并重试系统移交，不重新运行 Agent 语义维护。外部接口无法证明恰好一次，因此允许相同 `operation_id` 的重复回收站条目，但绝不拿权威删除包直接试投，也不根据它是否消失猜测成功。

只有这段待移交窗口允许 `restore_page`：工具仍掌握权威删除包、原路径和引用变更日志，因而能够把本次未完成的外部移交撤销为一致的草稿状态。若此前一次投递其实已被系统接收、但成功状态尚未来得及落盘，恢复草稿后系统回收站里可能仍留有同一 `operation_id` 的备份包；这不会改变草稿结构事实。系统回收站移交成功状态已经耐久记录后，`restore_page` 不再适用；用户若从系统回收站手工取回内容，应把它当作普通外部文件，再由 Agent 决定是否以及如何重新纳入草稿网络。
