# D10.13：压缩后由主 Agent 维护草稿

> 影响：[D10.2 Codex 维护会话的显式压缩](10-2-codex-explicit-compaction.md)、[D10.11 待处理任务的占用与安全接管](10-11-task-claim-and-takeover.md)

> 暂缓原因：先确认 [D10.14 压缩前的确定性增量捕获](10-14-deterministic-precompact-capture.md)，明确压缩前是否需要任何 Agent 决策。

> 决定性质疑：[D10.15](10-15-postcompact-context-cost.md) 指出，如果主 Agent 压缩后必须全量读取尚未整理的原始范围，刚释放的上下文会被重新填满。因此本页推荐的“主 Agent 默认维护”路线不能在该质疑解决前确认。

> 第一版结论：[D10.19](10-19-precompact-necessity.md) 已取消压缩前任务和压缩后自动补漏。压缩后的主 Agent 只重新绑定 skill，不自动读取或维护原始历史。

## 用户提出的关键问题

压缩前钩子既然已经把尚未落盘的对话增量耐久保存成任务，为什么还要启动另一个维护 Agent？获得新上下文空间的主 Agent 能否在压缩完成后自己领取任务并整理草稿？

## 原方案的前提已经变化

最初引入专用维护 Agent，是为了避免主 Agent 在上下文即将耗尽时继续读取页面、整理结构，又触发一次压缩。这个理由只在“维护发生于压缩前”时成立。

一旦压缩前钩子的职责缩小为耐久保存任务，压缩后的主 Agent 已经获得新的上下文空间。它能够读取同一份任务、使用同一 skill 和 CLI 完成整理，不再需要为了上下文隔离而默认创建另一个 Agent 会话。

而且主 Agent 比独立维护 Agent 多掌握压缩后的会话摘要、当前用户意图和正在进行的任务。专用维护 Agent 只能依赖交接材料重建这些语义，因此主 Agent 并不天然更差，通常反而更不容易误解确认与质疑的含义。

## 平台入口可行

Codex 与 Claude Code 都能在压缩后触发 `SessionStart`，并用 `compact` 表示这次启动来自上下文压缩。这个入口可以读取待处理任务编号，并把一条很短的指令加入压缩后的主 Agent 上下文：先领取任务 `T17`，完成有界草稿维护，再继续普通工作。

正确性不依赖这条提示永久存在。任务本身在插件数据目录中耐久保存；即使主 Agent 崩溃或暂时没有处理，下次会话启动或下一次草稿 CLI 操作仍能发现它。

## 三种路线

### A：压缩后由主 Agent 默认维护

执行顺序：

1. `PreCompact` 只耐久保存任务 `T17`，不启动模型进程；
2. 平台执行上下文压缩；
3. 压缩后的 `SessionStart` 把 `T17` 作为待处理检查点交给主 Agent；
4. 主 Agent 使用 skill 和 CLI 处理直接受影响页面，并运行完整的 `discussion-notebook check ROOT`；
5. 主 Agent 继续原来的用户任务。

没有第二个写者，因此不需要后台完成通知，也没有“旧维护 Agent 恢复后继续写入”的问题。主 Agent 中途崩溃时，`T17` 仍保持待处理，由下一次主 Agent 运行继续。

代价是草稿维护会占用压缩后的主上下文，并延迟主 Agent 恢复原任务。它不会让维护耗时消失，只会去掉额外 Agent 启动、跨会话交接和并发协调成本。

### B：后台维护 Agent 仍作为默认执行者

它可以让维护与主 Agent 工作并行，理论上响应更快；但必须继续承担后台进程、专用会话、完成通知、并发写入闸门、任务接管和旧执行者失效等机制。

只有真实试用证明主 Agent 维护明显拖慢交互，才值得承担这组复杂度。当前还没有这样的测量结果。

### C：主 Agent 自动判断任务大小，必要时委派

小任务自己处理，大任务自动启动维护 Agent。看似兼顾两者，但第一版必须先准确定义“多大算大”，同时保留 A 和 B 两整套生命周期。没有真实数据前，这只是把不确定性变成配置和分支。

## 推荐的第一版

采用 A，并限制压缩后维护为有界任务：只处理交接材料指出的页面和直接关系，不在这里扫描整个草稿网络或进行大规模重组。大规模整理继续留在长期讨论暂停、显式健康检查或用户明确要求的时机。

若未来真实试用证明有界维护仍经常耗尽新上下文或显著影响响应，再把“显式委派给维护 Agent”作为第二阶段能力。耐久任务格式和共同核心可以继续复用，不需要现在保留后台执行机制。

## 如果确认，可以从第一版删除什么

- 每个草稿网络的专用维护会话；
- 维护会话恢复和会后压缩；
- Codex app-server 的 `thread/compact/start` 接入；
- 压缩前后台工作进程；
- 后台完成通知；
- 专门解决旧维护进程复活的限时任务占用权；
- 仅为独立维护 Agent 提供的 MCP 入口。

仍然保留：耐久任务、主 Agent 使用的 CLI、共同 Python 核心、内容摘要前置条件、结构操作日志、机械检查和可恢复回收站。这些能力保护文件和崩溃恢复，不依赖是否存在专用维护 Agent。

## 需要诚实面对的边界

这条路线减少的是系统复杂度，不一定减少用户看到完整回复前的总等待时间。主 Agent 若在恢复原任务前完成维护，维护时间仍然存在；只是它发生在压缩后，且不再额外启动和管理另一个 Agent。

第一版接受这个代价的理由是：压缩前维护只应是局部补漏，不应承担大规模整理。若局部补漏仍然经常很慢，应先检查日常即时记录是否失效，而不是马上建立后台 Agent 系统。

## 历史待确认项

第一版不再保存压缩前任务，也不让压缩后的主 Agent自动补读历史。本页路线已由 D10.15、D10.18 和 D10.19 取代，不再等待确认。
