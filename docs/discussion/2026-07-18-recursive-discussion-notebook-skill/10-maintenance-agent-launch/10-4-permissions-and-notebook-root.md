## 第一性原理

“只修改草稿”如果只写在提示词里，只是行为建议，不是安全边界。维护 Agent 会读取对话中可能包含的外部内容，也可能因为模型错误生成越界路径，因此平台权限必须让越界写入本身失败。

维护任务实际只需要：

- 读取当前草稿网络；
- 接收协调器传入的有界交接材料；
- 创建、修改、移动草稿网络内部的 Markdown 文件。

它不需要网络、Git、任意 shell、用户凭证、插件数据目录写权限或项目其他源码的写权限。机械检查由协调器在 Agent 结束后运行，不需要把任意命令执行权交给维护 Agent。

## 已确认权限边界

### 允许

- 读取和写入一个明确的草稿根目录及其子目录；
- 使用文件读取、搜索、创建和编辑工具；
- 从标准输入或等价平台输入接收本次耐久任务内容。

### 不允许

- 写入草稿根目录之外；
- 使用网络访问；
- 使用任意 shell 或 Git 命令；
- 读取常见凭证目录和凭证文件；
- 启动其他 Agent；
- 直接改写任务队列、完成凭据或会话登记；这些状态由协调器维护。

这里限制的是 Agent 的普通文件和命令能力。经 D10.5 约束的插件专用结构工具可以持有更窄的能力：管理草稿根目录内的临时删除包，并把验证通过的完整删除包送进系统回收站。这个能力不能接收草稿根目录外的任意源路径，也不能退化为任意文件写入或永久删除。

草稿根目录内的 `.discussion-notebook/` 是结构工具的内部区域。Agent 的普通读取、搜索、创建和编辑工具必须排除该目录；只有插件结构工具可以读写其中的最小 `notebook.json`、跨平台操作锁、`operations/` 恢复材料和临时删除包。`notebook.json` 只证明该目录已经显式接管并保存结构格式版本，不复制 Markdown 内容事实。会话绑定、运行环境和平台诊断日志仍保存在各自平台数据目录；结构操作日志、恢复副本和暂存内容必须随草稿本保存，确保另一平台也能执行 `recover ROOT`。

### 平台落点

- Codex：以草稿根目录作为 `codex exec -C` 的工作根，使用 `workspace-write`，不添加额外可写目录，不使用完全访问模式。
- Claude Code：从草稿根目录启动，使用固定文件工具集合和 `dontAsk`，未列出的工具直接拒绝；同时使用读写路径规则和沙箱约束，不能只依赖 `allowedTools`，因为允许列表本身并不会移除其他工具。

两个平台都应由协调器在任务结束后检查实际变更路径。该检查是发现平台缺陷或配置错误的第二道防线，不能取代平台在执行时阻止越界写入。

## 对草稿物理布局的影响

当前实战草稿采用“同级索引文件 + 子目录”的形状：

```text
docs/superpowers/
├── topic.tmp.md
└── topic/
    ├── 01-page.md
    └── 02-page.md
```

如果把 `docs/superpowers/` 作为工作根，维护 Agent 会获得其他无关设计文档的写权限；如果只把 `topic/` 作为工作根，它又不能更新外面的 `topic.tmp.md`。依赖提示词避免越界并不可靠。

因此，新 skill 创建和正式接管的草稿网络建议改为自包含目录：

```text
topic/
├── index.md
├── conclusions.md
└── pages/
    ├── 01-page.md
    └── 02-page.md
```

这样整个目录恰好就是最小可写边界，也更容易移动、归档、检查和在 Obsidian 中浏览。`index.md` 承担讨论导航，固定 `conclusions.md` 承担扁平结论汇总，`pages/` 保存递归讨论页；所有内容仍位于同一个可写根内。

现有“同级索引 + 子目录”草稿是实战历史，不应在设计讨论中自动迁移。新建 `init`、接管 `adopt` 和迁移 `migrate` 是三个严格分开的入口：新建只处理不存在或空目录，接管只验证并登记已经符合当前格式的目录，迁移才允许转换旧布局或旧版本。三者和普通维护命令都不能自动互相切换。Agent 根据 skill 选择并调用 CLI；失败、歧义或需要设计判断时再向人类反馈，不另建机器审批协议。

## 已确认结论

新 skill 管理的一个草稿网络必须完整位于同一个自包含目录中，该目录是维护 Agent 唯一的可写根。新建或显式接管会在其内部区域写入最小 `notebook.json`，结构工具不能只凭目录形状推断授权。现有历史草稿不自动迁移；只有 Agent 根据 skill 显式调用 `migrate` 才会转换。
