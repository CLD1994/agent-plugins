## 用户提出的根本性质疑

如果已经能够保证 skill 在压缩、恢复和后续讨论中持续存在于 Agent 上下文，是否还需要为每轮讨论维护可靠标记？

这个质疑成立。原提案把“保证 Agent 始终知道维护职责”和“程序自动证明每轮都已处理”混成了一个需求。

## 两件不同的事

### 指令连续性

D10.16 已经解决这件事：钩子根据耐久绑定重新激活 skill，Agent 在当前上下文中始终知道应该即时维护草稿。

它防止的是压缩、恢复或多轮讨论后遗忘工作方法。

### 自动覆盖证明

`processed_through`（已整理位置）解决的是另一件事：即使 Agent 进程突然消失，程序也能自动指出哪段转录没有得到完成声明。

它不让 Agent 更懂语义，不保证 `no_change` 判断正确，也不保护已经开始的多文件写入。它只是给自动崩溃恢复提供一个边界。

因此，skill 持续存在会显著降低可靠标记的必要性，但不能在逻辑上完全替代它。是否需要标记，取决于第一版是否承诺无人值守地发现每一个中断缺口。

## 逐类检查真实故障

- **正常讨论：** skill 指导 Agent 当场维护草稿，不需要额外标记才能工作。
- **压缩后遗忘维护方法：** D10.16 的重新绑定解决，不需要逐轮标记。
- **结构操作执行到一半崩溃：** D10.6 的操作日志和暂存机制解决，逐轮语义标记不能替代它。
- **Agent 错误理解用户意思：** 人工评审和真实场景试用解决；可靠标记只能保存错误声明。
- **收到用户结论后、开始写草稿前崩溃：** 这是可靠标记真正能够帮助自动发现的情况。
- **草稿写完后、标记落盘前崩溃：** 标记会制造一次安全但多余的重复检查。

可靠标记的价值因此很窄：它主要覆盖“语义已经进入对话，但维护还没有完成”的意外中断窗口。

## 三种路线

### A：第一版不保存语义完成位置

不维护 `processed_through`，也不要求每轮提交 `updated` 或 `no_change`。

正常路径只依靠：

- skill 在上下文新鲜时立即维护草稿；
- D10.16 在压缩和恢复后重新激活 skill；
- D10.6 保护已经开始的多文件结构操作；
- 已知发生异常中断时，显式检查当前草稿和转录末尾的小范围内容。

同一会话恢复时，最近的未完成交流通常仍在平台转录中，可以显式核对。真正的新会话只把草稿视为上次已完成的状态；若旧会话在写入前突然崩溃，第一版不承诺自动发现这条遗漏。

这是当前推荐路线。项目仍在开发阶段，没有真实用户，先为罕见崩溃窗口建立每轮协议不符合最小化原则。

### B：保存一个累计的已整理位置

若未来要求无人值守恢复，保存一个不断前进的位置就够了，不需要永久逐轮账本。Agent 每轮提交 `updated` 或 `no_change`，缺少结果的范围交给显式或独立维护流程。

它换来自动缺口检测，但会给每轮讨论增加一次协议动作，还要处理最终答复与转录边界怎样配对。

这应在真实故障、自动移交或无人值守运行出现后增加。

### C：永久保存每轮回执

它增加存储、清理和隐私成本，却仍然不能证明语义判断正确。即使未来采用路线 B，也没有理由默认升级到这条路线。

## 一个具体反例

用户说：“接受 D10.17。”随后 Agent 进程立即崩溃，尚未修改任何草稿。

- 有累计标记：程序发现转录末尾超过已整理位置，可以自动报告缺口。
- 没有累计标记：同一会话恢复后，Agent 可以从最近交流发现并补写；但若用户直接建立全新会话，程序无法仅凭草稿证明那句“接受”曾经出现过。

这就是删除标记真正放弃的能力。它不是日常维护能力，而是跨会话自动发现极短崩溃窗口的能力。

## 对抗性结论

“skill 一直在上下文”不能严格推出“可靠标记毫无价值”，因为进程可能在执行 skill 前崩溃。

但反过来，“存在这种崩溃可能”也不能自动推出“第一版必须给每轮建立协议”。如果产品尚不承诺无人值守、零遗漏恢复，原始转录仍可在已知异常时人工或显式核对，那么累计标记是可以推迟的可靠性增强，不是草稿维护的基础条件。

## 修正后的当前建议

第一版采用路线 A：取消 `processed_through`、`updated` 和 `no_change` 的逐轮要求。保留即时维护、skill 重新绑定、结构操作日志和显式异常恢复。

未来出现以下任一真实需求时，再增加路线 B：

- Agent 长期无人值守运行；
- 需要自动把未维护范围交给独立维护上下文；
- 频繁跨会话移交且不能接受最后一轮遗漏；
- 真实试用中观察到崩溃导致决定丢失。

即使升级，也只增加累计位置，不建立永久逐轮回执账本。

## 已确认结论

用户确认：第一版完全取消逐轮可靠标记，只依靠即时维护、skill 重新绑定、结构操作恢复和显式异常核对；等出现无人值守自动恢复的真实需求后，再增加累计已整理位置。
