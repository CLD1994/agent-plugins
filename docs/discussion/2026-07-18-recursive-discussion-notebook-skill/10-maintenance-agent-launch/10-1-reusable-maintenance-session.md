# D10.1：复用专用维护会话

> 状态：`历史条件方案，第一版不采用`
>

> 第一版结论：[D10.19](10-19-precompact-necessity.md) 已移除压缩前自动维护；第一版不建立专用维护会话。本页只保留为未来无人值守或显式委派方案的条件设计。

## 当时确认的条件结论

每个草稿网络、每个平台维护一个可恢复但可替换的专用维护会话。维护任务串行执行；会话失效时自动新建；草稿和耐久任务记录始终是事实来源。

维护会话的作用是保存维护习惯和近期结构认知，减少每次从零理解草稿的成本。它不是另一份权威记忆，也不能取代草稿文件。

## 复用范围

- Codex 和 Claude Code 分别维护自己的会话，不能跨平台恢复。
- 不同草稿网络不能共享会话，避免无关项目和讨论互相污染。
- 第一版可以使用“规范化草稿根路径 + 平台”定位会话。草稿移动后创建新会话即可；因为会话不是事实来源，不需要为了保住它而提前引入永久草稿标识。
- 会话标识和最近一次成功状态保存在平台自己的插件数据目录中，不写入用户的草稿正文。

## 串行执行与失效恢复

同一维护会话一次只处理一个任务。新的压缩触发如果发现该会话正在运行，应进入同一草稿网络的待处理队列，不能并发恢复同一个会话。

恢复失败、会话文件被清理、版本升级导致不兼容或会话状态损坏时：

1. 保留原耐久任务；
2. 放弃旧会话标识；
3. 创建新维护会话；
4. 依据草稿和任务输入继续维护。

会话重建是性能退化，不是数据丢失。

## 任务结束与会话压缩

每次维护必须先更新草稿、运行所需检查并写入完成凭据。之后协调器再请求平台压缩维护会话，并验证平台返回的压缩完成事件。

压缩失败不能推翻已经完成的草稿维护。此时记录“维护已完成、会话尚未压缩”，下次继续尝试或依赖平台自动压缩。

压缩控制不依赖 Agent 在自然语言任务中“记得自行压缩”。Claude Agent SDK 正式支持恢复会话后发送 `/compact`；Codex 的确定性压缩方式由 [D10.2](10-2-codex-explicit-compaction.md) 继续评审。

## 为什么仍要以文件为准

压缩摘要会舍弃细节，也可能保留已经过时的理解。下一次任务中，维护 Agent 可以利用会话快速定位，但当会话记忆与当前草稿冲突时必须以磁盘文件和新任务事实为准。
