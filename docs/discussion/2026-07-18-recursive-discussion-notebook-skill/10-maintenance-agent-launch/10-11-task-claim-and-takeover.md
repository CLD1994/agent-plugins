## 要解决的问题

D10.10 已确认主 Agent 可以通过 CLI 接续维护 Agent 未完成的任务。但“未完成”不等于“原执行者已经死亡”。维护 Agent 可能只是卡住、网络很慢，或者协调器失去了对它的等待结果；主 Agent 接管以后，旧维护 Agent 仍可能恢复并继续调用工具。

单写者文件锁只能防止两者在同一瞬间写文件，不能回答“锁释放后谁还有资格继续这个任务”。如果主 Agent 写完并释放锁，旧维护 Agent 随后拿到锁，它仍可能根据过时上下文覆盖新结果。

可以把它理解成旅馆房间的钥匙：门锁只能保证一次进一个人，却不能保证旧房客退房后手里的旧钥匙失效。安全接管还需要让旧钥匙失效。

## 三种路线

### A：只依赖单写者文件锁

实现最少，但只能防止同时写入，不能防止旧执行者稍后写入，因此不够。

### B：任务一旦被占用，就永久属于原执行者

旧执行者不会和接管者冲突，但进程崩溃会让任务永久卡住，只能由人手工解除。它违背了自动恢复目标。

### C：使用限时任务占用权

任务被执行者领取时，核心签发一份限时任务占用权 `lease`（经典并发控制中通用的字段用语，因此字段和协议中保留英文）。它至少包含：

- `task_id`：正在处理哪个耐久任务；
- `attempt_id`：这是该任务的第几次具体执行身份；
- `owner_id`：谁领取了任务；
- `lease_expires_at`：这份占用权何时失效。

任务只需要三个主要状态：

- `pending`：尚未被有效执行者占用；
- `active`：存在尚未过期的占用权；
- `completed`：已经保存完成凭据。

每次修改操作都必须同时携带 `task_id` 和 `attempt_id`。共同核心在真正写文件前检查这次执行仍持有有效占用权；旧执行者即使后来恢复，其旧 `attempt_id` 也会被拒绝。

## 接管过程

以任务 `T17` 为例：

1. 维护 Agent 领取 `T17`，得到执行身份 `A1`，开始整理。
2. 它完成两步后卡住。协调器超时，先尽力终止对应子进程，不再续期 `A1`。
3. 主 Agent 查看任务时，如果 `A1` 仍在有效期内，只能看到“仍被占用”，不能强行并发接管。
4. `A1` 到期后，主 Agent 通过 CLI 领取同一任务，得到新的执行身份 `A2`。
5. 主 Agent 根据共同操作日志跳过已完成步骤，继续剩余工作。
6. 原维护 Agent 即使稍后恢复并尝试以 `A1` 写入，共同核心也会拒绝，因为 `A1` 已经过期且已被 `A2` 取代。

占用权的续期应由确定性的协调器或 MCP 服务在维护进程正常存活时完成，不让语言模型靠文字记得“续租”。领取、续期和完成状态变更都必须在任务存储中原子完成；文件写入仍另外经过 D10.6 的单写者锁、内容摘要前置条件和操作日志。

## 为什么第一版不需要更重的方案

第一版的协调器、CLI、MCP 和草稿都在同一台机器上运行。我们不需要为多机服务建立分布式共识；一个耐久任务文件或本地数据库，加上短时间持有的文件锁，就足以原子地签发和更新限时占用权。

限时占用权解决“谁现在有资格继续任务”，单写者锁解决“谁现在能改文件”，内容摘要解决“文件是否还是我读取时的版本”。三者职责不同，不能互相替代。

## 当前建议

采用 C。正常情况下只有维护 Agent 持有占用权；维护失败后，主 Agent 必须等旧占用权失效或被协调器安全撤销，才能领取新的 `attempt_id`。任何旧执行身份都不得继续修改草稿。

## 历史待确认项

第一版没有后台任务或多个自动写者，不评审这项规则。未来若重新引入异步维护，再从“限时任务占用权 + 每次执行独立 `attempt_id` + 旧执行身份写入必被拒绝”继续评审。
