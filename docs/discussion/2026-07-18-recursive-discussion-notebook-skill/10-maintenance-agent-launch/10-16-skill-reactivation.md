## 用户提出的问题

D10.15 要求主 Agent 在讨论过程中持续按照 skill 即时维护草稿。随着会话不断压缩、恢复或迁移，Agent 是否会失去 skill 指令？skill 是否会在多轮压缩后逐渐失效？

这里不讨论现代模型能否遵循清楚的指令，只讨论指令是否仍然被可靠地放进当前上下文。

## 平台事实

### Claude Code

Claude Code 在会话开始时提供 skill 的名称和说明，调用时才加载完整 `SKILL.md`。压缩后会重新附加已调用 skill 的最近一次内容，但存在明确预算：每个 skill 最多保留前 5,000 token，所有重新附加的 skill 合计最多 25,000 token，并从最近调用的 skill 开始分配；调用过多时，较旧 skill 可能完全不再附加。

因此 Claude Code 的原生行为已经提供较强连续性，但不能把“完整 skill 永远都在”当作无条件保证。关键规则必须放在 `SKILL.md` 前部，正文也应保持精炼。

### Codex

Codex 同样采用渐进加载：初始上下文提供 skill 的名称、说明和路径，完整 `SKILL.md` 只在选择该 skill 时读取。Codex 的压缩后 `SessionStart` 支持 `source: compact`，并允许命令钩子注入额外上下文。

当前官方资料没有明确承诺“已调用 skill 的完整正文在每次压缩后都会自动重新附加”。跨平台共同协议因此不能依赖这项未声明行为，应利用压缩后入口明确恢复活动 skill。

## 第一性原理

要保证连续性，不需要让 Agent 永久记住整份 skill。只需要保证三个耐久事实存在：

1. 哪个草稿网络正在由当前会话维护；
2. 该草稿网络要求使用哪个 skill 及哪个版本；
3. 每次上下文重建后，平台都会再次提示 Agent 检查并加载这个 skill。

skill 文件是耐久的程序资源，草稿网络绑定是插件状态，生命周期钩子负责重新引入。压缩摘要不承担保存 skill 指令的责任。

## 三种路线

### A：完全依赖平台原生压缩行为

Claude Code 通常能够重新附加最近调用的 skill；Codex 也保留 skill 发现信息。但 Claude Code 有明确预算和淘汰规则，Codex 又没有公开完整正文重附加保证。

这条路线平台差异大，无法作为共同正确性边界。

### B：每次压缩后把完整 `SKILL.md` 注入上下文

它最直接，但会重复占用大量上下文；多轮压缩后反复注入完整正文，还可能挤压真正需要的草稿状态。skill 更新、引用文件和平台差异也会让注入器变成第二套 skill 加载器。

这条路线解决得过重，不应采用。

### C：压缩后注入短重新绑定指令，按需重读 skill

插件保存会话与草稿网络的绑定。每次 `compact`、`resume` 和适用的 `startup` 发生时，普通命令钩子只注入一个很短的重新绑定信封：

- 活动草稿网络标识和根目录；
- 必须使用的 skill 名称；
- 期望的 skill 版本或内容摘要；
- 根索引页和可选的 `last_page_hint`（上次页面提示；保留字段名用于程序状态）；
- 触发原因：压缩、恢复或会话移交；
- 要求在继续受管理讨论前确认当前 skill 已加载，缺失或版本不符时重新读取。

它不复制完整 skill，不复制对话历史，也不重复总结草稿内容。Agent 通过平台原生 skill 机制读取当前版本，随后以草稿索引和页面作为外部讨论记忆。

这是当前推荐路线。

`last_page_hint` 不是“Agent 当前正在看哪页”的权威游标。普通翻页不要求重写绑定，否则阅读行为会制造没有必要的持久写入；页面可能已改名、移动或讨论焦点已在当前对话中改变。重新绑定时它只作为快速定位提示：根索引和当前对话事实优先，提示过期或不存在时直接忽略。

绑定键必须同时包含明确的平台身份和该平台的会话标识。钩子薄入口从宿主事件取得这些值，并显式调用绑定核心；CLI 不通过探测环境变量决定自己正在为 Codex 还是 Claude Code 工作。Codex 入口只使用 `PLUGIN_DATA`，Claude Code 插件入口只使用 `CLAUDE_PLUGIN_DATA`；Tavern 孵化期由 setup 固定使用 `.claude/discussion-notebook-data/`。概念命令形态为 `bind ROOT --platform PLATFORM --session SESSION_ID [--last-page-hint PAGE]` 和 `unbind --platform PLATFORM --session SESSION_ID`，其中可选提示写入 `last_page_hint`。平台入口负责把已经确定的数据目录交给核心，目录来源不明确时拒绝操作。

## 多轮压缩为什么不会累积失效

重新绑定不是依赖上一次压缩摘要继续传递，而是每次都重新读取两个耐久来源：插件保存的活动绑定，以及安装目录里的 skill。

因此第十次压缩与第一次压缩执行的是同一条幂等流程：

1. 平台完成上下文重建；
2. `SessionStart(compact)` 再次触发；
3. 钩子用显式平台身份和会话标识从插件状态读取活动绑定；
4. 注入短重新绑定信封；
5. Agent 确认或重新加载当前 skill；
6. 从草稿索引和当前页继续讨论。

中间任何一次压缩摘要写得不好，都不会永久破坏后续 skill 激活。下一次生命周期入口仍从磁盘和插件状态重新开始。

## 压缩、恢复与真正的新会话不同

- **同一会话压缩：** 沿用已有会话与草稿网络绑定，自动重新绑定 skill。
- **恢复同一会话：** 通过会话标识找回绑定，自动重新绑定 skill。
- **迁移到全新会话：** 新会话标识与旧绑定没有天然关系，必须通过显式移交记录、启动参数或一次明确的草稿网络选择建立新绑定。若同时存在多个草稿网络，程序不能根据工作目录擅自猜测。

新会话怎样取得绑定是下一层移交协议，不应和压缩后的自动重载混成一个问题。

## 失败边界

- skill 文件缺失或版本不符：停止自动维护并明确报告，不凭压缩摘要模仿旧指令；
- 生命周期钩子未安装、未启用或未获信任：不能承诺自动连续维护，允许用户显式调用 skill 恢复；
- 草稿网络绑定不存在或有多个候选：要求明确选择，不自动猜测；
- Claude Code 原生重新附加内容被截断：短重新绑定信封要求重新读取完整当前 skill；skill 的核心规则仍应位于文件前部；
- 重新绑定重复执行：结果应相同，不重复创建草稿任务或修改页面。

## 当前建议

不依赖 Agent 记忆、压缩摘要或某个平台是否碰巧保留完整 skill。插件把“活动草稿网络使用哪个 skill”保存为耐久绑定，并在每次压缩和恢复后的 `SessionStart` 注入短重新绑定指令。完整 skill 始终通过平台原生机制按需读取。

## 已确认结论

用户确认：每次压缩或恢复后由钩子注入短重新绑定信封，要求 Agent 确认或重新读取当前 skill；不把完整 skill 塞进钩子输出，也不依赖压缩摘要保存指令。
