## 用户提出的问题

压缩前钩子通过命令启动维护 Agent 时，维护过程究竟应当阻塞压缩，还是在后台继续？

完整阻塞会把“维护 Agent 用时”和“上下文压缩用时”串行相加。后台执行允许两者重叠，但压缩后的主 Agent 可能在维护完成前开始新一轮工作，因此必须说明：怎样避免覆盖、怎样保存新讨论事实，以及维护完成后主 Agent 怎样得知结果。

## 先区分两个过程

压缩前钩子需要完成的事情并不等于草稿维护本身：

1. **交接保存：** 把即将从上下文中消失的对话增量、任务编号和草稿位置耐久保存。这一步不完成就放行压缩，可能真正丢失信息。
2. **语义维护：** 唤醒维护 Agent，让它阅读交接材料、判断页面关系并修改草稿。这一步已经有耐久输入，可以晚于压缩完成。

从第一性原理看，只有第一步与压缩存在强制先后关系。第二步操作外部草稿文件，压缩操作主会话上下文；只要并发写入被隔离，两者没有必要默认串行。

## 当前平台事实

### Codex

Codex 命令钩子当前默认同步等待。配置中的 `async`（异步）虽然能被解析，但异步处理器会被跳过。因此 Codex 若要后台维护，只能由同步协调器先耐久保存任务，再启动与自身生命周期分离的工作进程，然后尽快退出钩子。

### Claude Code

Claude Code 的命令钩子默认同步等待，也支持 `async: true` 后台运行。后台钩子的普通结果会在后续对话轮次交付，但这种平台专有通知不能作为跨平台正确性的基础。

两个平台都提供压缩后的生命周期入口，可以在压缩结束时快速检查维护状态；但维护可能仍未完成，因此该检查只能提示状态，不能代替耐久任务和完成凭据。

## 三种路线

### A：完整阻塞

压缩前协调器等待维护 Agent、草稿写入、机械检查和完成凭据全部结束，再放行压缩。

优点是压缩后的主 Agent 一定面对已经整理好的草稿，不需要处理并发状态。缺点是最慢；模型限流、网络波动或较大拆分都会直接延长压缩等待，最终仍需要超时退路。

### B：完全后台执行，不限制主 Agent

钩子启动后台维护后立即放行，主 Agent 可以同时直接读写草稿。

等待最少，但不成立。内容摘要只能让冲突写入失败，不能避免主 Agent 根据正在变化的页面做出过时判断，也不能保证新的讨论事实被维护任务看见。

### C：同步保存交接，后台维护，草稿入口设闸

压缩前协调器只同步完成以下最小动作：

1. 耐久保存本次对话增量和任务；
2. 启动后台维护工作进程；
3. 确认工作进程已经取得任务或任务仍可被后续重试；
4. 返回并允许上下文压缩。

维护 Agent 与上下文压缩随后并行。压缩后的主 Agent 不需要等待才能继续普通讨论或其他工作，但所有受管理草稿的读写都先经过共同核心：

- 维护已经完成：返回完成凭据和新的草稿版本，主 Agent 刷新后继续；
- 维护仍在进行：不允许主 Agent 直接修改正在整理的草稿；
- 新讨论产生了重要事实：先追加到独立的待处理增量，形成排在当前任务之后的新任务，不与后台 Agent 争写草稿；
- 主 Agent 的当前工作确实依赖最新草稿：只在这个局部位置等待维护完成，或在 D10.11 定义的安全条件下接管。

这不是让整个主 Agent 停止工作，而是只冻结受管理草稿的直接修改入口。新的讨论事实仍能耐久保存，不会因为后台维护尚未完成而丢失。

## 维护完成怎样通知主 Agent

不能假设一个后台进程可以随时打断正在生成的主 Agent。跨平台的权威通知采用“主 Agent 下次接触草稿时必然看到”，而不是“后台进程必须立刻向对话插话”：

1. 维护完成后写入耐久完成凭据和新的草稿版本；
2. 压缩后快速检查、平台通知或界面提示可以尽力告知，但它们只改善体验；
3. 下一次 CLI 或 MCP 草稿操作必须先返回未读的完成状态，并要求刷新相关页面；
4. 如果主 Agent 从未再接触草稿，它也不需要为正确性立即知道维护已经完成。

如果维护在压缩完成前结束，压缩后检查可以立刻带回完成状态。如果维护较慢，主 Agent 先看到“维护进行中”，之后在第一次草稿访问时看到完成凭据。即使所有即时提示都丢失，耐久状态仍不会丢失。

## 当前建议

采用 C，并修正 D10.3：正常路径不再同步等待整个维护 Agent，只同步等待交接材料耐久保存和后台任务可靠启动。完整阻塞降为用户显式要求“压缩后草稿必须已经整理完成”时的可选模式，不作为默认行为。

这也把 skill 与工具的职责分开：skill 指导主 Agent 遇到进行中任务时怎样继续讨论；共同核心强制禁止并发修改，并负责把新事实追加成后续任务。正确性不依赖 Agent 是否记住一段提示词。

## 历史待确认项

第一版没有压缩前交接或后台维护，不评审同步与异步时序。未来若重新引入自动维护，再决定是否采用“同步保存交接、后台维护、草稿入口设闸”的路线。
