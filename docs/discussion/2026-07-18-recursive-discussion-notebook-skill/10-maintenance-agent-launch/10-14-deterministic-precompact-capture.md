## 最初的问题

压缩前“保存任务”是否需要 Agent 判断，还是普通程序就能完成？

最初提案把“保存任务”拆成两件事：程序复制尚未处理的完整对话证据，压缩后由 Agent 判断这些证据怎样改变草稿。这个拆分正确地区分了机械工作与语义工作，却仍然隐含了一个未经证明的前提：压缩会让程序也失去原始对话。

## 用户提出的决定性质疑

压缩完成后，程序需要的事实似乎仍然存在：

- 平台仍保存会话转录；
- 压缩后的钩子仍能获得会话标识和 `transcript_path`（转录文件路径，保留字段名以对应平台输入）；
- 草稿网络绑定、当前页和父枢纽本来就是插件已经保存的状态；
- 上次整理到哪里也可以由插件单独保存。

如果这些事实压缩后仍可读取，压缩前再复制一次完整增量就没有创造新的可恢复性，只是制造第二份数据、第二个位置和一套清理规则。

## 第一性原理修正

上下文压缩改变的是“下一次模型调用直接看得到什么”，不是自动删除平台保存的会话记录。

因此需要保护的事实应分成两类：

1. **平台已经耐久保存的事实。** 完整会话转录属于这一类。只要压缩后仍能读取，就应直接复用，不重复复制。
2. **插件自己拥有的事实。** 草稿网络绑定、上次成功整理的位置和未完成结构操作属于这一类，应由插件保存，因为平台不会替插件维护它们。

原提案中的 `captured_through`（已捕获位置）不再必要。它只回答“第二份副本复制到了哪里”，而修正后的设计不建立第二份副本。

若要求程序自动检测语义维护缺口，只需要 `processed_through`（已整理位置）：它表示某个 Agent 已经解释到转录的哪个位置，并把相应结论写入草稿。当前转录末尾高于已整理位置，只能说明存在尚未确认完成语义维护的范围。

这个范围是恢复和审计边界，不等于应该把其中的原始记录全部重新装入压缩后的主 Agent。那会抵消上下文压缩的收益。具体由谁承担语义阅读成本，转入 [D10.15](10-15-postcompact-context-cost.md) 评审。

## 若保留自动缺口检测的流程

1. 日常讨论仍在重要变化发生时立即局部维护草稿，压缩钩子只负责补漏。
2. 平台完成压缩。
3. 压缩后的 `SessionStart`，以及以后每次启动或恢复会话时，程序读取草稿网络绑定、`transcript_path` 和已整理位置。
4. 程序比较已整理位置与当前转录末尾；没有差距就不创建工作。
5. 有差距时，程序只记录“存在尚未完成语义维护的范围”，不能默认把原始记录注入压缩后的主 Agent。
6. 由另一个独立上下文处理、显式维护，还是依靠讨论过程中已经完成的即时维护，属于 D10.15 的决策。
7. 无论由谁处理，所有修改成功落盘后才能推进已整理位置。

如果主 Agent 在第 5 至第 7 步之间崩溃，已整理位置不会前进。下一次启动或恢复时，程序用同一份平台转录重新派生出相同的待整理范围，不需要预先保存一个独立任务对象。

这里的“待整理任务”是由“会话转录末尾减去已整理位置”计算出来的视图，不必默认成为另一份耐久事实。结构修改已经开始后的操作日志仍然需要耐久保存；那是在保护多文件写入一致性，不是复制对话历史。

## 三种路线

### A：压缩前复制全部未捕获增量

它可以让插件不再依赖平台转录的后续可用性，但要维护第二份对话数据、已捕获位置、保留期限和清理逻辑。只要平台转录压缩后仍然存在，这些成本没有换来额外正确性。

### B：压缩后从平台转录派生待整理范围

插件只保存草稿网络绑定和已整理位置。程序从平台转录计算差值，但不决定由哪个 Agent 读取，也不把完整差值自动加入主上下文。崩溃恢复仍然可以再次计算差值。

这是当前推荐的证据定位路线，符合“已有事实不重复拥有”的最小化原则；它本身不解决语义阅读成本。

### C：插件持续镜像整段会话

若某个平台根本不提供持久转录，或用户明确关闭会话持久化，插件只能在每轮事件发生时自行记录，而不是等到压缩前才补救。压缩前钩子只拿到转录路径和少量元信息，并不能凭空恢复从未落盘的模型上下文。

这会让插件变成另一个会话记录系统，带来隐私、存储和平台适配成本。第一版不应为了尚未出现的宿主限制承担这项能力。

## 平台事实与不稳定边界

Codex 和 Claude Code 当前都在钩子公共输入中提供 `transcript_path`，也都能在压缩后触发相应钩子。Claude Code 还明确说明本地转录默认保存为 JSONL，Codex 与 Claude Code 都警告转录内部格式可能随版本变化。

这说明“压缩后仍有原始证据”当前成立，但“可以永远绑定某个内部 JSON 字段”不成立。平台适配层应负责读取和定位转录，共同核心只接收规范化的对话记录。适配失败时不得猜测已经处理成功。

第一版可以把“宿主提供可读的持久转录”声明为自动压缩补漏的前置条件：

- 压缩后路径可读：按正常流程派生待整理范围；
- 路径为空、文件不可读或格式不受支持：不推进已整理位置，明确警告自动补漏暂不可用；
- 继续依靠日常即时写入的草稿事实，不声称压缩历史已经完整整理；
- 等出现真实平台需求后，再评估官方导出接口、适配器升级或持续镜像，而不是现在默认复制所有历史。

复制同一份不稳定格式并不能解决格式不稳定；它只把无法解析的字节换了存放位置。

## 关于不复制转录的建议

第一版不在压缩前复制对话增量，也不维护 `captured_through`。如果以后保留自动缺口检测，程序可以在压缩后以及会话恢复时，从平台转录和插件保存的 `processed_through` 派生待整理范围，但不能默认要求压缩后的主 Agent 全量读取。

其中“不复制平台已有转录”的结论不依赖 `processed_through`。是否保存 `processed_through` 属于另一项自动缺口检测能力，正在 D10.18 重新评审。

`PreCompact`（压缩前事件）因此不再是保存原始证据的必需入口。`SessionStart(source=compact)`（压缩后主会话重新开始的事件；保留字面量以对应平台匹配器）足以发现缺口，普通 `startup` 和 `resume` 也可以负责崩溃后的再次发现。发现不等于应该由主 Agent 读取；后续处理见 D10.15。

## 已确认结论

第一版不在压缩前复制或持续镜像平台已经保存的转录，不维护 `captured_through` 或 `processed_through`，也不自动解析转录寻找语义缺口。平台转录只在已知异常和显式恢复时作为原始证据。
