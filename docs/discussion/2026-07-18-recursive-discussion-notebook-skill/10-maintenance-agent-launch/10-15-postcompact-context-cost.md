## 用户提出的决定性质疑

压缩后的程序即使能算出尚未整理的转录范围，主 Agent 接下来能做什么？如果它必须重新读取这段原始历史才能维护草稿，就会把刚刚释放的上下文再次填满，压缩近似白做。

这个质疑成立。D10.14 只证明原始证据仍然可恢复，没有证明语义提炼不再消耗上下文。

## 第一性原理

把一段自然语言讨论提炼成结论、质疑、依赖和下一步，必须由具备语义理解能力的 Agent 阅读相应信息。无论信息存放在当前上下文、平台转录还是插件副本中，这部分阅读和推理成本都不会消失。

上下文压缩的价值是让主 Agent 不再携带全部旧细节。如果压缩后立即把旧细节完整读回主 Agent，就只是先清空再装回，既增加延迟，又没有获得有效上下文空间。

因此必须区分：

- **证据可恢复：** 原始转录仍在，必要时可以查证；
- **证据默认装载：** 把整段原始转录重新放入主 Agent；
- **草稿已经维护：** 重要语义已在上下文仍然新鲜时写入外部草稿。

第一项是保险，第二项应避免，第三项才是正常路径。

## 三条路线

### A：压缩后主 Agent 全量读取尚未整理范围

实现最简单，也没有第二个写者，但直接抵消压缩收益。尚未整理范围稍大时，主 Agent 可能再次触发压缩，并延迟原任务恢复。

这条路线应否定，不能作为自动正常路径。

### B：独立维护 Agent 读取尚未整理范围

独立维护 Agent 在自己的上下文中读取原始范围，更新草稿；压缩后的主 Agent只读取维护完成后的短摘要或草稿页面。

它确实保住了主 Agent 的新上下文空间，也解释了专用维护 Agent 的真实价值：不是因为原始记录只能在压缩前取得，而是因为语义整理成本需要放到另一个上下文。

代价仍然存在：额外模型用量、启动延迟、写入协调，以及同步等待和异步并发之间的选择。是否同步或异步属于 D10.12 的执行时序问题。

### C：讨论过程中即时维护，独立上下文只处理异常缺口

用户确认、否定、提出决定性反例、打开分支或改变下一步时，主 Agent 已经在当前上下文中理解了含义。此时立即更新当前页、父枢纽和直接受影响页面，几乎不需要重新阅读历史。

压缩发生时：

- 已有明确维护完成凭据：不读取历史，不启动维护 Agent；
- 仍有未完成的语义维护范围：不交给压缩后的主 Agent全量读取，而由独立维护上下文处理，或进入显式维护流程；
- 范围异常庞大：视为日常维护已经失效，不把它自动灌入任何正在继续用户任务的主上下文。

这是当前推荐路线。它沿用已经确认的“重要变化立即局部维护”，把压缩钩子降为补漏和恢复机制。

## 一个具体例子

假设讨论到第 100 轮即将压缩：

- 第 96 轮用户否定旧方案时，主 Agent 当场更新了当前页；
- 第 98 轮打开新分支时，主 Agent 当场创建子页并更新父级索引；
- 第 100 轮只是继续解释，没有形成新的草稿事实。

那么压缩后不需要读取第 1 至 100 轮，甚至不需要读取第 96 至 100 轮。主 Agent 只使用平台压缩摘要和已经维护好的草稿继续工作。

若第 98 轮应该创建子页，但主 Agent 在落盘前崩溃，则原始转录提供恢复证据。恢复阅读应由独立维护上下文承担，范围只从最后一次明确完成维护的位置开始，而不是让压缩后的主 Agent把历史重新装回来。

## 新出现的协议边界

> 本节是当时提出的候选协议，不是 D10.15 已确认结论。其必要性正在 D10.18 重新评审。

程序无法从“草稿文件没有变化”判断这一轮是真的不需要更新，还是 Agent 忘记更新。因此每个受管理讨论回合最终必须留下两类结果之一：

- 已完成所需草稿修改；
- Agent 明确判断本轮没有需要写入的草稿变化。

这两者都属于语义结果，不能由关键词或文件时间戳代替。工具可以保存结果凭据和对应的转录位置，但结果本身必须来自已经理解本轮对话的 Agent。

具体是否要求每轮显式调用 CLI、怎样减少无变化回合的操作成本，是下一层协议问题，本页先不提前决定。

## 当前建议

否定“压缩后主 Agent读取完整待整理范围”。正常路径是在讨论过程中即时维护草稿。平台转录只作为异常恢复证据；确有缺口时，由独立维护上下文或显式维护流程承担重新阅读成本。是否还要为每轮保存完成结果，转由 D10.18 决定。

## 已确认结论

用户已确认：压缩后的主 Agent不自动重读原始历史；草稿语义维护以讨论过程中的即时写入为正常路径，未完成缺口才交给独立维护上下文。
