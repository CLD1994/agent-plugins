## 要解决的问题

把一个页面改名，可能同时修改页面本身、父级索引和十几个引用它的页面。单个文件可以通过“写临时文件后替换”避免只写入半截内容，但普通文件系统不能把十几个文件包装成一个真正的数据库事务。

如果工具改到第五个文件时崩溃，只依靠事后检查会留下一个改了一半的草稿网络。恢复机制必须在第一次写入之前就准备好。

## 三种路线

### A：直接逐个修改，失败后重新扫描

实现最简单，但重新扫描只能发现损坏，无法可靠知道哪些改动属于本次操作、原内容是什么，以及应该继续还是撤销。它不满足自动恢复目标。

### B：复制整个草稿目录，完成后整体替换

先在临时目录生成完整新版本，通过检查后一次性替换整个草稿根目录。概念直观，但跨平台整体替换非空目录并不稳定；Obsidian 或其他编辑器打开文件时也可能阻止替换。草稿很大时还会反复复制全部历史，并可能覆盖人类刚刚保存的并发修改。

### C：变更计划、暂存文件与耐久操作日志

工具先在草稿根的 `.discussion-notebook/operations/<operation-id>/` 建立耐久日志，再计算完整计划，把每个旧文件的内容摘要、恢复副本、预期新内容和执行步骤写入同一操作目录。所有新内容先写入暂存文件并检查通过，然后才逐项替换正式文件。

操作日志记录每一步是否完成。进程重启后，工具先读取未完成日志：能够证明文件仍处于预期状态时继续完成；无法继续但能够证明文件没有被外部修改时自动回滚；发现人类或其他程序并发修改时停止，不覆盖未知内容，并报告冲突。

## 建议流程

1. 先验证显式草稿根路径和登记版本；如果已有 `operation.lock`，在读取可能处于中间态的 Markdown 前拒绝普通写操作并提示恢复；
2. 生成 `operation_id`，创建 `.discussion-notebook/operations/<operation-id>/journal.json`，初始阶段为 `allocating`，此时不修改受管理 Markdown；
3. 使用排他创建取得 `.discussion-notebook/operation.lock`，锁内至少记录 `operation_id`；若竞争失败则不开始写入；
4. 取得锁后再完整检查当前结构、扫描链接图并生成完整变更计划；
5. 在同一操作目录记录旧内容摘要、恢复副本和全部暂存新文件；
6. 把日志阶段耐久更新为 `prepared`，再次核对正式文件摘要，确认计划生成后没有被外部修改；
7. 使用单文件原子替换逐项提交，并在每一步后耐久更新日志；
8. 完成后运行链接和结构检查；
9. 检查通过后写完成状态并释放锁；无需继续恢复的副本可以清理，回收站权威删除包保留到外部适配器成功返回且成功状态已经耐久记录；
10. 失败或重启时，`recover ROOT` 只根据草稿内的锁和日志继续完成或回滚，不读取平台数据目录，也不重新猜测。

锁、操作日志、恢复副本和暂存文件必须全部位于草稿网络自身。否则 Codex 与 Claude Code 虽然能看到同一把锁，却可能读不到对方平台数据目录中的恢复材料。平台持久数据目录只保存运行环境、会话绑定和诊断日志，不参与结构操作正确性。

锁不能仅凭经过时间判定为陈旧。锁指向合法操作日志时按日志恢复；锁指向缺失或损坏日志时报告客观损坏并保留现场，不能擅自解锁。没有锁的 `allocating` 目录还没有取得写权限，可以作为未开始操作清理；没有锁却声称已经进入 `prepared` 或写入阶段的日志属于矛盾状态，必须停止检查。

## 对抗性边界

这套机制不能假装解决所有并发问题。Obsidian 或文本编辑器不会遵守插件的单写者锁，所以还必须使用内容摘要检测外部修改。

如果某个已经由工具写过的文件随后又被人编辑，它既不等于旧版本，也不等于工具计划的新版本。此时自动回滚会覆盖人的新内容，自动继续也可能误合并，因此必须停止并留下明确冲突。这属于真实的并发语义冲突，不是把普通维护工作推给人类。

恢复优先顺序建议为：能够证明安全时继续完成；不能继续但能够证明没有外部变化时回滚；两者都不能证明时停止保护现场。

## 已确认结论

采用 C。它不是让多个文件瞬间同时变化，而是保证任何中间状态都有记录、能够识别，并在没有外部冲突时自动收敛到“全部完成”或“全部撤销”。

操作日志、恢复副本和暂存文件由插件在草稿根内部管理。它们不使用 Git 的暂存区或提交，不要求草稿目录位于 Git 仓库，也不执行 `git add`、`git commit`、`git reset` 等会干扰用户工作流的操作。

如果草稿本来位于 Git 仓库中，Git 历史可以作为额外保险，但不是插件正确性的前提或组成部分。
