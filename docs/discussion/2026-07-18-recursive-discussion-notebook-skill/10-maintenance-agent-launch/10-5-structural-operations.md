# D10.5：草稿结构变化如何安全落盘

## 要解决的问题

D6.3 允许维护 Agent 在依据明确时创建、拆分、改名、移动或删除讨论页。D10.4 又确认它不应获得任意 shell 或无边界的文件操作能力。

因此，不能只在提示词里要求 Agent “小心执行”。高风险结构变化必须由确定性工具完成路径限制、引用修复、冲突检查和结果验证；Agent 负责判断应该发生什么，工具负责保证操作不会机械地破坏草稿网络。

## 已否定路线：用旧转向页代替完善的改名

此前建议第一版不物理移动或删除文件：改名时创建新页面，把旧页面留下作为转向页；长期清理由用户显式执行。

用户否定了这条路线，原因成立：

- 它把自动维护没有做完的工作转嫁给人类；
- 转向页会持续制造文件噪声；
- 它回避了引用更新和操作校验，而不是解决问题；
- 只要工具能够可靠地修复并验证引用，物理改名本身并不应该被禁止。

## 已明确的新边界

- Agent 应自主完成整次维护流程，不以“以后由人清理”为正常终点；
- 改名和移动必须通过专用工具完成，不能依赖通用 shell；
- 专用工具负责更新受影响的 Markdown 链接并运行机械校验；
- 删除被允许，但只能送入可恢复的回收站，不能调用 `rm`、`unlink` 或等价永久删除；
- 回收站不可用或操作失败时，保留原文件并报告失败，绝不静默退化为永久删除。

## 改名与移动工具需要保证什么

暂称工具为 `move_page`（移动页面；目标路径可以只改变文件名，也可以改变所在目录）。一次操作至少需要完成：

1. 把来源和目标转换为草稿根目录内的规范相对路径；
2. 拒绝绝对路径、`..` 越界、符号链接逃逸、非 Markdown 文件和目标冲突；
3. 扫描整个草稿网络，找出所有指向来源页面的本地 Markdown 链接；
4. 重新计算并更新入站链接；如果页面所在目录变化，也要更新被移动页面中的相对出站链接；
5. 先生成完整变更计划和恢复日志，再开始改文件；
6. 操作后运行链接和结构检查，证明没有新增断链或父子导航损坏；
7. 只有全部成功才返回完成结果；中途崩溃时根据恢复日志继续完成或回滚。

这里不能只做文本搜索替换。相同文件名、相对路径、带锚点链接、引用式 Markdown 链接以及代码块中的示例文本，都可能使盲目替换改错内容。

## 回收站工具需要保证什么

暂称工具为 `trash_page`（把页面送入回收站）。它至少需要：

1. 执行与 `move_page` 相同的草稿根目录和路径逃逸检查；
2. 禁止删除草稿根 `index.md` 等必须存在的结构文件；
3. 自动解除父页导航中由父子关系确定的入口；除此之外，发现仍然指向该页的有效入站关系或正文链接时拒绝操作，让 Agent 先决定删除、改写还是重定向这些语义引用；
4. 先把页面和恢复元数据原子移动到草稿根目录内的插件临时回收区；
5. 整轮整理完成且结构检查通过后，保留临时删除包作为权威副本，只把它的完整投递副本交给操作系统回收站；
6. 系统回收站不可用或投递结果尚未耐久记录时保留权威删除包，等待协调器重试；不得使用永久删除兜底。

Python 的 [Send2Trash](https://pypi.org/project/Send2Trash/) 已经提供 Windows、macOS 和 Linux 的原生回收站适配，并声明支持 Python 3.14。它适合作为第二阶段移交操作系统回收站的候选依赖，不需要自行重写三套平台协议；第一阶段的一致性和恢复由插件临时回收区保证。最终仍需用 Windows、macOS、普通 Linux、WSL 和开发容器真实验证失败行为。

## 工具怎样交给 Agent

### A：允许 Agent 通过 shell 调用专用命令

命令本身可以严格校验，但为了调用它而开放 shell，仍会把大量无关能力交给 Agent，不符合 D10.4。

### B：Agent 写操作清单，结束后由协调器执行

协调器读取结构化清单并执行工具，不需要给 Agent shell。安全边界清楚，但 Agent 在当前维护轮次内看不到操作失败，也就无法立即修正引用冲突；通常还要再启动一轮维护。

### C：通过本地 MCP 服务暴露窄工具

插件只向维护 Agent 暴露 `move_page`、`trash_page` 等带结构化参数的工具。Agent 能同步看到校验结果并继续处理，MCP 服务则独立验证每个路径，不提供任意文件操作。

Codex CLI 可以作为 MCP 客户端连接本地服务；Claude Code 插件也能捆绑并自动启动 MCP 服务。因此 C 能使用一份 Python 运行核心服务两个平台，而不需要给 Agent 通用 shell。[Codex MCP 支持](https://github.com/openai/codex/blob/main/codex-rs/README.md#model-context-protocol-support)、[Claude Code 插件 MCP 文档](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers)

## 已确认结论，经 D10.20 修正

路径限制、引用修复、冲突检查、可恢复日志和操作后校验仍然是结构操作的硬性要求。第一版把这些能力收口在共同 Python 核心中，并通过 CLI 暴露改名、移动、回收、枢纽升格和枢纽降级等窄命令；不创建 MCP 服务。

这里必须区分两类“引用修复”：改名和移动不改变页面语义，所以工具自动重写所有可证明等价的链接；回收会让一个语义对象消失，工具只能自动解除由父子结构决定的导航入口。其他入站关系或正文链接怎样处理不是字符串问题，而是内容判断，必须由 Agent 先解决，工具随后验证已经没有悬空引用。

页面升格为枢纽和空枢纽降级也不能靠手工组合普通移动命令。CLI 需要提供独立操作：升格把 `page.md` 变成 `page/index.md`，并在同一事务式文件操作中至少改挂一个已有子页；降级把已经为空的非根 `page/index.md` 变回 `page.md`。移走最后一个子页的普通移动或回收操作则自动调用同一个降级原语，避免留下非法空枢纽。

如果未来引入权限受限的独立维护 Agent，MCP 可以作为调用同一核心的薄适配层，并成为该执行者唯一的文件能力。这个未来边界不改变第一版采用 CLI 的交付决定。
