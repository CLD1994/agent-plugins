## 要解决的问题

正常路径希望主会话在压缩前等待维护完成，但辅助插件不能因为认证失败、网络异常、模型限流或自身错误永久卡住宿主。需要明确什么状态允许压缩继续，以及超时后任务处于什么状态。

## 原已确认方案

本页原先确认“正常路径同步等待完整维护，失败或超时才转为耐久待处理任务”。用户随后指出：维护 Agent 的模型调用可能显著增加压缩等待时间，而上下文压缩本身已经需要时间；如果两者没有必须串行的因果关系，就不应默认把耗时相加。

因此，下面方案作为历史推理保留。耐久保存、失败放行和不能锁死宿主等边界只在未来重新采用压缩前自动维护时才需要；当前第一版没有这条执行路径。

压缩前协调器始终先耐久保存维护任务，再启动或恢复维护 Agent。平台的压缩流程同步等待协调器，但协调器必须拥有比平台钩子超时更短的内部期限，确保自己有时间记录状态并正常退出。

### 完成并放行

满足以下事实后立即放行主会话压缩：

- 维护 Agent 已处理对应任务标识；
- 草稿修改已经落盘；
- 必需的机械检查没有客观错误；
- 完成凭据已经耐久保存。

语义审查提醒不等于客观错误，不应仅因存在提醒就把任务判为失败。

维护会话自己的后续压缩不属于以上完成条件。它失败只影响下次恢复成本，不影响这次草稿已经维护成功的事实。

### 未完成但安全放行

出现认证失败、限流、进程崩溃、内部期限到达或检查发现客观错误时：

- 不写完成凭据；
- 保留任务为待处理状态，并保存已知错误；
- 明确提示“交接材料已保存，语义维护尚未完成”；
- 正常退出压缩前钩子，让主会话继续压缩；
- 后续可靠时机重新处理同一个任务标识，不创建重复任务。

### 连耐久保存也失败

沿用 D9 的最终边界：发出高可见警告，但仍允许压缩。辅助插件不能永久锁死宿主；此路径必须明确表示存在丢失风险，不能伪装成延迟处理成功。

## 为什么不靠钩子的强制阻止

钩子进程本身运行时，平台已经在同步等待。只有在维护成功后正常退出，或者在超时前保存失败状态并正常退出，才有可预测行为。

若在自动压缩已经用于恢复上下文极限错误时继续强制阻止，Claude Code 会让原始上下文错误直接暴露，当前请求失败。对于已经耐久保存的维护任务，这种强制阻止没有增加信息安全，只增加宿主不可用风险。

## 尚未决定的数值

本页先确认语义边界，不凭空确定等待秒数。实现前应通过两个平台的真实场景试用测量一次典型局部维护和一次较大拆分的耗时，再选择默认内部期限，并保留用户可调整入口。
