## 要解决的问题

D10.4 最初允许维护 Agent 使用平台提供的普通文件读取、搜索、创建和编辑工具，只把工作根限制在草稿目录。D10.7 后来又在这个根目录内加入 `.discussion-notebook/`，其中保存尚未移交系统回收站的删除包。

如果 Agent 仍能任意写整个草稿根目录，它就可以绕过 `trash_page`：直接改写或删除临时删除包、伪造内部状态，或者把普通页面写进内部目录。即使提示词要求它不要这样做，也不是安全边界。

## 三种路线

### A：保留通用文件工具，用提示词要求忽略内部目录

实现最简单，但不能阻止模型错误、提示注入或错误路径。它使“只有结构工具可以处理删除包”的声明不成立。

### B：保留通用内容工具，依赖平台配置排除内部子目录

如果平台能够对同一个工作根表达“允许 `index.md` 和 `pages/`，拒绝 `.discussion-notebook/`”，可以继续使用原生文件工具。

问题是两个平台的权限表达和工具行为并不完全一致；只要其中一个平台不能强制排除子目录，共同安全模型就会退化为提示词约束。

### C：插件工具成为唯一草稿文件入口

维护 Agent 不获得通用 shell 或任意文件写权限。短生命周期本地 MCP 服务提供受限操作，例如：

- `list_pages`：只列出讨论页；
- `read_page`：只读取 `index.md` 和 `pages/`；
- `search_pages`：搜索讨论内容，自动排除内部目录；
- `apply_page_changes`：按预期内容摘要创建或修改普通页面；
- `move_page`、`trash_page`、`restore_page`：执行已经确认的结构操作。

每个工具都在服务端重新规范化路径，拒绝绝对路径、`..`、符号链接逃逸和 `.discussion-notebook/` 直接访问。Agent 只能通过语义明确的工具影响草稿，内部目录仍由同一个服务私有管理。

代价是插件需要提供基础的读取、搜索和编辑工具，而不只是结构工具。好处是 Codex 与 Claude Code 使用同一套真实权限边界，安全性不再依赖两套平台文件工具恰好具有相同配置能力。

## 已确认的未来安全边界

采用 C。这里增加工具不是为了抽象整洁，而是因为 D10.7 已经产生了必须对 Agent 隐藏的恢复状态。只给 MCP 服务文件能力，可以同时落实“不使用任意 shell”“不能写草稿根外”和“不能绕过回收站协议”。

工具数量仍应保持最小：普通内容修改尽量收口为一个带内容摘要前置条件的 `apply_page_changes`，不为每种 Markdown 修改建立独立工具。

未来维护 Agent 的所有草稿文件访问都必须经过插件 MCP 工具，不得直接使用平台的通用 shell 或文件工具。第一版主 Agent 使用 CLI；CLI 为结构操作提供确定性保护，但不伪装成主 Agent 的权限沙箱。
