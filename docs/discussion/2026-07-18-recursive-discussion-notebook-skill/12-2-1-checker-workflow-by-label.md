## 本页目的

本页用具体例子解释检查器怎样处理当前提议的标签：`状态`、`父主题`、`依赖`、`取代`、`被取代`、`质疑`、`被质疑`、`产出`。

这不是为每个标签建立一套语义判断。检查器仍然只证明文件结构事实，不判断结论是否正确、状态措辞是否合适或质疑是否成立。

## 完整工作流程

检查器分成两遍。

### 第一遍：逐页读取

对每个受管理页面：

1. 找到页面唯一的一级标题；
2. 读取紧跟一级标题的连续 Markdown 引用块；
3. 识别已确认的结构标签；
4. 检查标签是否缺失、重复、写空或链接格式损坏；
5. 收集正文中的普通 Markdown 链接，但忽略代码围栏里的示例链接；
6. 不解释正文自然语言，也不尝试从正文猜关系。

这一遍得到的是“每个页面自己声明了什么”。

### 第二遍：检查整张关系图

所有页面读完后：

1. 解析本地相对路径并确认目标是否存在；
2. 根据每个子页面的 `父主题` 建立父子树；
3. 检查父页面是否提供返回子页面的可见导航；
4. 建立依赖、取代、质疑和产出关系；
5. 检查 `取代 / 被取代`、`质疑 / 被质疑` 是否成对一致；
6. 推导 `子主题`、`被依赖`、`来源于` 等不落盘的反向查询结果；
7. 检查重复、自指和明确禁止的环；
8. 输出客观错误与审查提醒，不修改任何文件。

这一遍回答的是“各页面的声明合在一起是否自洽”。

### 独立检查与结构操作中的检查

用户直接运行检查命令时，检查器只读当前文件并报告结果。

安全改名、移动或回收页面时，共同核心会在操作前确认起始结构可解释，在暂存后的新结构上运行同一套检查，再决定是否完成操作。检查失败时由结构操作保留日志并恢复或保护现场；检查器本身仍不自动修复内容。

## 1. `状态`

### 普通例子

```markdown
# D12.1：最少必须有哪些结构字段

> 状态：`已确认`
```

### 检查器能确定什么

- 每个页面必须恰好有一个 `状态`；
- 状态值必须使用 `待讨论`、`当前提案`、`已确认`、`已取代`、`已关闭` 五个前缀之一；
- 状态行必须位于顶部结构引用块；
- 前缀后可以用全角冒号补充非空自由说明，例如 `已关闭：历史条件方案，第一版不采用`。

### 检查器不能确定什么

- 页面内容是否真的已经确认；
- 冒号后的“历史方案”等说明是否准确；
- 用户是否确实批准了迁移；
- 状态是否应该发生变化。

这些都需要 Agent 根据对话判断，并由用户掌握最终确认权。检查器只能识别生命周期类别，不能替 Agent 选择类别。

`状态` 不保存取代或质疑的来源。页面受到这些关系影响时，分别使用 `被取代` 或 `被质疑` 标签；因此不需要 `状态依据`，检查器也不必从状态说明中猜关系目标。

## 2. `父主题`

### 子页面例子

```markdown
# D12.2：正式关系由哪一侧声明

> 状态：`当前提案`
>
> 父主题：[D12 最小机器可识别结构](12-minimal-structure-syntax.md)
```

### 对应父页面例子

```markdown
## 子主题

- [D12.2 正式关系由哪一侧声明](12-2-canonical-relation-direction.md)
```

### 检查器怎样处理

1. 除根 `index.md` 外，每个页面必须恰好有一个 `父主题`；
2. `父主题` 必须恰好指向一个受管理页面；
3. 目标不能是自己、内部管理目录或草稿网络外的文件；
4. 根 `index.md` 不能声明父主题；
5. 根据 [D12.8](12-8-parent-rooted-tree.md)，父主题链不能形成环，并且最终必须回到唯一根索引；
6. 父页面正文必须存在一个返回该子页面的普通 Markdown 链接。

最后一项只验证导航存在。父页面中的普通链接不会反过来自动建立子关系；机器仍以子页面的 `父主题` 为权威。

## 3. `依赖`

### 例子

```markdown
> 依赖：[D5 链接格式与反向查找](05-links-and-backlinks.md)
```

它表示：理解或修改当前页面前，必须先理解目标页面。

### 检查器怎样处理

- `依赖` 是可选标签；没有依赖时不写；
- 链接目标必须存在，并且应是同一草稿网络中的受管理页面；
- 页面不能依赖自己；
- 同一依赖关系不能重复；
- 目标页面不需要写 `被依赖`，反向结果由查询推导；
- 依赖不会自动改变目标页面的有效性，所以目标页面不需要增加状态提示。

[D12.7](12-7-dependency-cycles.md) 已确认任何长度的依赖环都属于客观结构错误。若两个问题实际上共同演化，应使用共同父主题或普通链接表达；若两页无法独立理解，应合并页面或抽出共同前提，而不是互相声明前置条件。

## 4. `取代`

### 新页面例子

```markdown
# 新的维护方案

> 状态：`已确认`
>
> 取代：[旧的维护方案](old-maintenance-plan.md)
```

### 旧页面例子

```markdown
# 旧的维护方案

> 状态：`历史方案，第一版不采用`
>
> 被取代：[新的维护方案](new-maintenance-plan.md)
```

### 检查器怎样处理

1. 从新页面读取 `取代`，从旧页面读取对应的 `被取代`；
2. 检查两个标签互相指向，任何单边出现都报客观错误；
3. 检查目标存在、不是自己、没有重复关系；
4. 检查取代链不存在 A 取代 B、B 又取代 A 之类的环。

检查器不会判断新方案是否真的更好，也不会因为新页写了 `已确认` 就自行接受取代关系。关系必须由 Agent 根据用户已经明确确认的事实写入。

添加或删除取代关系会同时影响两个页面，因此安全工具应把 `取代` 和 `被取代` 作为同一次可恢复的多文件结构操作。

## 5. `质疑`

### 质疑页面例子

```markdown
# 并发下的反例

> 状态：`当前提案`
>
> 质疑：[当前发布方案](current-publish-plan.md)
```

### 受到质疑的页面例子

```markdown
# 当前发布方案

> 状态：`当前提案`
>
> 被质疑：[并发下的反例](concurrency-challenge.md)
```

### 检查器怎样处理

1. 从质疑页面读取 `质疑`，从目标页面读取对应的 `被质疑`；
2. 检查两个标签互相指向，任何单边出现都报客观错误；
3. 检查目标存在、不是自己、没有重复关系。

按照 D4 的定义，正式 `质疑 / 被质疑` 只表示“尚未解决并且正在威胁当前方案或已确认结论”的反例。质疑解决后，Agent 依据用户确认同时移除两个标签，但可以在正文或讨论日志中保留普通历史链接。这样检查器不需要从状态说明猜测关系，就能区分当前质疑和历史质疑。

两个页面互相质疑不一定是结构错误，因为它可能真实表达两个方案彼此的反例；检查器不应像处理取代环那样机械禁止。

目标页面也可以同时使用 `已确认` 和 `被质疑`：这表示结论当前仍有效，但存在尚未解决的挑战。检查器分别验证质疑关系和该页面的产出完整性，不把这种组合判为冲突。若用户决定挑战已经撤销结论的当前效力，Agent 才把状态改回 `当前提案` 并移除 `产出`。

## 6. `产出`

### 例子

```markdown
> 产出：[结论汇总](../conclusions.md)
```

它表示当前页面的结论已经确认、当前未被取代，并已纳入草稿网络内的结论汇总产出页。产出页仍是临时草稿，不是正式设计。

### 检查器能确定什么

- 除 `conclusions.md` 自身外，`产出` 对 `已确认` 页面是必需标签，对其他状态禁止；
- 同一产出关系不能重复；
- 目标必须是草稿根级唯一固定的 `conclusions.md`；
- 产出页正文必须包含来源页的结论摘要和 Markdown 返回链接；
- `已取代` 与 `被取代` 必须一致，任何被取代页面都不能继续产出；
- `已确认 + 被质疑` 仍然需要产出，检查器不把它当作状态冲突；
- 反向的“来源于”由查询推导，不要求产出页重复保存标签。

### 检查器不能自动证明什么

检查器能够识别状态前缀，因此能发现“已经写成 `已确认` 却漏写 `产出`”以及其他状态错误声明 `产出`。它仍不能证明 Agent 是否应该把某页标为 `已确认`。

正常维护流程需要 Agent：

- 在用户明确确认结论时把状态改为 `已确认`、添加 `产出` 并更新产出页；
- 在来源页后来被取代时移除旧 `产出` 和旧汇总条目；
- 判断页面是否在语义上真的达到确认、关闭或取代状态。

检查器负责验证状态前缀与产出集合、产出页正文回链以及取代关系是否一致。摘要是否准确、状态是否选对，仍由 Agent 判断、用户评审。

## 哪些词不是文件标签

`子主题`、`被依赖`、`来源于` 不是文件中需要维护的标签。它们由工具根据正式标签和导航关系推导；其中产出页仍需在正文显式链接来源，供人类和后续流程渐进阅读。

`被取代` 和 `被质疑` 则是必须写入目标页面的标签，因为它们直接改变该页面的当前理解。

父页面正文里的子页面导航虽然必须存在，但也是普通 Markdown 链接，不是 `子主题` 机器标签。

## 一次检查的通俗例子

假设有一个根索引和两个子页面，并存在以下结构事实：

1. 根索引链接“当前方案”和“并发反例”；
2. “当前方案”的 `父主题` 指向根索引；
3. “并发反例”的 `父主题` 也指向根索引，并通过 `质疑` 指向“当前方案”；
4. “当前方案”通过 `被质疑` 链接“并发反例”。

检查器会这样工作：

1. 先确认三个页面各自的状态和父主题格式；
2. 再确认两个子页面都能回到根索引；
3. 再确认根索引正文确实链接两个子页面；
4. 再读取“并发反例”发出的质疑；
5. 最后确认 `质疑` 和 `被质疑` 两个标签互相对应。

如果缺少第 4 项，检查器报告“`质疑` 缺少对应的 `被质疑`”这一客观结构错误，不会自行补写标签，也不会判断质疑是否正确。
