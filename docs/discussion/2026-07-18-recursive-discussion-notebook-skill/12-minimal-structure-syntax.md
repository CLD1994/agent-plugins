## 要解决的问题

D11 已确认检查器只检查明确声明的结构事实。程序要可靠识别状态、父主题和正式关系，页面必须提供一个极小的机器可识别区域。

这不等于建立整页模板。本页只选择结构区域使用哪种语法；哪些字段必需、关系方向和链接范围继续逐项确认。

## 第一性原理

合适的结构区域需要同时满足：

- 使用普通 Markdown 阅读器和 Obsidian 都能自然显示；
- 人类打开页面时能立即看到当前状态和上级入口；
- 程序不必猜测正文句子；
- 改名工具能可靠找到需要修复的关系链接；
- 不要求固定正文标题、章节顺序或自然语言措辞；
- 不把同一事实复制到 Markdown 与另一份权威文件。

## 三种路线

### A：YAML front matter

页面顶部使用 YAML front matter（YAML 前置元数据；保留英文名称以对应生态中的固定叫法）：

```markdown
---
status: confirmed
parent: pages/01-parent.md
---
```

它结构清楚、解析成熟，Obsidian 也支持。但它不是 Markdown 核心语法，字段值对人类阅读较冷，需要在路径和显示标题之间另外取舍。若正文还要显示状态和父主题，就会复制事实。

### B：页面顶部的标准 Markdown 引用块

页面标题之后放一个连续的引用块：

```markdown
# 示例问题

> 状态：`当前提案`
>
> 父主题：[链接格式与反向查找](05-links-and-backlinks.md)
```

引用块本身是标准 Markdown，在 Obsidian 中直接可读。程序只解析页面开头这一小块；正文其余部分完全按普通 Markdown 处理。

本页最初只确认状态保留人类可读形式，没有在这一层决定类别集合；D12.1 后续把它收口为五个机器可识别前缀加可选自由说明。正式关系仍使用标准 Markdown 链接，改名工具可以复用同一链接解析逻辑。

这是当前推荐路线，也与现有讨论草稿已经形成的书写习惯一致。

### C：HTML 注释或旁置 JSON 文件

HTML 注释对人类不可见，容易让状态与页面显示脱节。旁置 JSON 会产生第二份需要同步的权威状态，页面移动、复制或人工编辑时更容易漂移。

这两种方式都违背“Markdown 是可独立阅读的事实来源”，不应采用。

## 推荐路线的最小边界

本轮若确认路线 B，只确认以下内容：

- 机器可识别区域位于一级标题之后、正文之前；
- 该区域使用一个连续的标准 Markdown 引用块；
- 检查器只解析这个引用块中的已确认结构标签和 Markdown 链接；
- 引用块可以包含额外的人类提示；检查器忽略不具有标签形状的普通文字，但“标签名：值”形状必须使用已知标签；
- 引用块结束后的标题、段落和章节顺序不属于机器协议。

本轮不确认：状态是否采用枚举、哪些标签必需、同一关系怎样列出多个目标、关系的规范方向，以及哪些链接可以指向草稿网络外。

## 对抗性审查

- **引用块是否仍然约束文字？** 它只约束少数结构标签和链接位置。正文不受影响；D12.1 后续只约束状态的生命周期前缀，说明仍可自由书写。
- **用户把普通说明也写进引用块怎么办？** 允许不具有标签形状的普通句子。若写成“标签名：值”，就进入结构解析，未知标签按 D12.4 报错。
- **引用块被移动到页面中间怎么办？** 人类仍能阅读，但检查器报告缺少顶部结构区域；状态与父主题必须打开页面就能看到。
- **为什么不直接搜索全文中的“父主题”？** 全文搜索会把例子、历史引用和正文讨论误当成当前结构，无法安全改名。
- **现有历史草稿是否立即迁移？** 不自动迁移。只有新建或用户显式接管的自包含草稿网络采用这套语法。

## 当前建议

采用页面一级标题后的连续 Markdown 引用块作为唯一机器可识别结构区域。正文不使用固定模板；检查器忽略不具有标签形状的普通引用文字，但不会静默忽略未知标签。

## 已确认结论

用户确认路线 B：使用一级标题后的标准 Markdown 引用块保存最小结构信息，不使用 YAML front matter、HTML 注释或旁置 JSON。
