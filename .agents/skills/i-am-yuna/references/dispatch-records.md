# 调度记录、补充说明与恢复

在写任务单、发送补充说明、接收结果、恢复切片、记录失败或准备清理时阅读。本文件是这些产物、状态和模板的唯一权威位置。

本文中的“当前层级调度者”是创建该任务单并直接负责其子树的 agent；根级 Main Agent 还负责整个会话的全局事项。嵌套调度者继承父任务的目标、授权、范围、起始基线和共享约束，只能在继承范围内建立局部记录、委派下级和处理子树结果；需要改变继承内容时向父级报告。

## 目录和产物

一次会话首次实际委派时，建立调度记录并使用一个稳定且人类可读的会话名。每个调度者把本层记录放在自己当前工作区的 `tmp/agents/<会话名>/`。subagent 使用独立工作区时，发起调度的 agent 在联系它之前，直接在目标工作区的 `tmp/agents/<会话名>/<任务名>/` 写好自包含任务单；该 subagent 的消息、checkpoint 和报告也写在这里。没有独立工作区时，在当前工作区为任务建立独立目录。任务单及其中列出的必读权威来源共同构成该切片的完整任务上下文，接收任务的 subagent 不自行编写或补建。

每个任务使用稳定且人类可读的名称；回合和 checkpoint 编号从 001 起递增。以下示例中，根级 Main 在主工作区记录全局调度，执行任务在自己的 linked worktree 中保存本切片记录：

    <主工作区>/
      tmp/agents/2026-09-03-api-migration/
        dispatch-record.md
      .worktrees/schema-audit/
        tmp/agents/2026-09-03-api-migration/schema-audit/
          task.md
          main-001.md
          subagent-002.md
          checkpoints/001.md
          execution-result-001.md

每个任务目录的消息回合是本切片自己的单调序列，且只用于排列该切片的消息文件。不同切片的回合号不需要相同。

|产物|写入者|读取者|权威内容与最小字段|
|-|-|-|-|
|调度记录|根级 Main 或当前层级调度者|创建者及其恢复者；下级不读取父级过程记录|根级记录保留会话的调度事实；嵌套记录只保留自己子树的任务说明版本、起始基线、模型映射、切片、角色、层级、隔离、共享约束、本层补充、失败连续性、门禁、评审处置、局部采用和临时资源状态，不覆盖父级记录。|
|subagent 任务单|当前层级调度者|指定 subagent 及其恢复者|该切片唯一可执行授权：具体交付物、工作角色、下级管理权限、任务工作目录、起始基线和任务说明版本、继承的目标与授权边界、本层范围、共享约束及初始状态、必读权威来源、按需辅助来源、允许修改范围、验收与已知验证、停止条件、checkpoint/结果/评审/提交位置、已批准计划与标为建议的实现预估、禁止加载的 skill。|
|补充说明|当前层级调度者|指定 subagent|原样消息和版本化变化：本地消息回合、本层补充版本、影响的切片、共享约束版本或“未改变共享约束”、变化本身、既有失败记录保留或作废的判断及理由。|
|subagent checkpoint|该 subagent|同一切片的恢复者和直接父级；其他切片不读取|该切片当前仍有效的可恢复状态、补充事件、证据、未完成项和下一动作。完整字段见“checkpoint 模板”。|
|执行结果报告|执行 subagent|直接父级和指定独立评审者|候选声明或停止报告、范围、起始基线、产物或提交、已运行门禁与结果、验收证据、已知未覆盖项、停止或完成的依据、临时资源；最终结果分类由负责该切片的调度者写入本层记录。|
|评审报告|独立评审 subagent|负责该范围的调度者；调度者决定后向修复任务提供需要的部分|独立结论和可执行修复要求。完整字段见“评审报告模板”。|
|整合报告|整合 subagent|负责该范围的调度者和最终评审者|固定输入、已整合产物、接缝、端到端门禁、冲突与该层级提交。|
|清理指引|当前层级调度者或执行级清理 subagent|负责该范围的调度者和执行清理的人类|每个任务工作区的路径、分支、一句状态概述、查看状态的命令，以及确认安全时可供人类执行的非强制清理命令。它不授权删除。|
|Yuna 调度经验|根级 Main|后续根级 Main|有具体证据的调度、切分和上下文压缩经验；单次事件只形成窄结论。|
|Yuna 模型难度记录|身份揭示前已固定结论的独立评估者|后续根级 Main|匿名比较的模型难度结论、匿名证据和最低完整通过层级。|

直接处理任务不建立 Yuna 调度记录或任务单；其他项目规则要求的记录仍然保留。已经发生委派后，任务也不必然生成表中的所有文件：只读事实核对不生成执行提交；没有独立评审需求时不生成评审报告；没有写入切片或临时资源时不生成整合或清理产物。负责该范围的调度者在已有调度记录中写明每个未生成产物的触发条件不成立。

顾问分析角色的产物是分析、风险和证据报告，不是执行候选；它不归入“已完成但评审未通过”，也不消耗任何执行失败连续性。顾问级模型按 [匿名模型比较](anonymous-comparison.md) 另行承担执行角色时，才按普通执行结果和失败连续性记录。

所有文件链接都相对包含该链接的 Markdown 文件解析；任务工作目录另行明确，不能用进程当前目录猜测链接目标。没有辅助来源时省略该字段。任务单中未给出“已批准”的实现安排只是建议，subagent 可以在不改变可观察行为的前提下调整它。普通任务单未列出的来源不属于该切片的任务上下文；需要新增来源时停止相关工作并向直接父级报告。任务单不授权阅读其他切片、父级过程记录或未列出的计划、checkpoint、结果或推理。

顾问分析任务是来源边界的例外：初始输入仍是冻结的共同输入和指定评审结论，任务单同时授权它在继承范围内自行选择并在报告中记录补充证据。新增证据不改写既有执行失败连续性。

## 补充说明、共享约束和失败连续性

补充说明同时维护三种独立编号或状态：

|名称|谁的范围|何时变化|作用|
|-|-|-|-|
|本地消息回合|一个切片|该切片产生下一条主从消息时|只决定该切片消息文件顺序|
|本层补充版本|一个调度范围|该范围的调度者发出任一补充时单调递增|审计该范围内补充的投递顺序；根级范围的序列覆盖整个会话，嵌套范围的序列只覆盖自己的子树|
|共享约束版本|当前层级所有受影响切片|共享约束实际改变时单调递增|表示受影响切片共同遵守的约束；父级继承约束在下层保持只读|

同一共享补充投递给多个切片时，每个切片使用自己的下一个本地消息回合，但携带相同的本层补充版本和共享约束版本。当前层级调度记录必须保存这个版本到各切片本地消息路径的映射。只影响一个切片的非共享补充仍有本层补充版本，但不改变其他切片的当前版本、共享约束或处置。嵌套调度者不能用本层补充改变父级约束；需要改变父级约束时向父级报告，由根级 Main 或任务单/补充按 [SKILL.md](../SKILL.md) 的窄授权规则明确指定的父级产生跨层更新。

每段失败连续性开始时，负责该范围的调度者在调度记录中固定共同输入：原始任务单中的交付结果、已确认的行为和授权、范围、共享约束、验收与停止条件和已批准计划，以及同一版本的必读权威来源和按需辅助来源、相同起始基线和适用的项目规则。新的同级执行者和升级后的执行者都从这份共同输入开始。工作角色、下级管理权限、工作目录、worktree、分支和交付路径是当次运行信息，由有权调度者按隔离路线和执行阶段设置，但不得改变任务语义或证据可得性。补充可以按顺序累积，不能以“任务单文字必须逐字不变”为理由重启工作；负责该范围的调度者在每份补充中判断既有失败记录是否仍有效并说明理由：

|补充实际改变的内容|失败连续性和既有评审|
|-|-|
|只补充证据位置、澄清原意，或给出修复建议，且不改变既有结论前提|保留受影响切片的失败连续性；已有评审仍按其范围有效|
|可观察行为、用户授权、起始基线、核心约束、验收条件，或足以改变既有评审结论的前提|作废受影响记录和评审；受影响切片开始新的失败连续性|
|只影响某一切片且不改变共享约束|只更新该切片；其他切片保留自己的有效状态和失败连续性|
|共享约束改变|所有受影响切片接收同一共享约束版本，作废原失败连续性并从执行级开始；若改变继承约束，先由父级处理|

本层补充版本只表示审计顺序，不能单独决定失败是否连续。负责该范围的调度者对每个切片维护人类可读的失败连续性：只要核心任务和仍有效的行为、授权、起始基线、核心约束、验收条件等价，新的“已完成但评审未通过”结果继续累计，即使其间有新的本层补充版本。每次有效失败记录当时已应用的本层补充版本、所属连续性、评审报告路径，以及保留或作废理由。同层级换人不清零；任务说明发生足以改变上述状态的变化才新建受影响切片的连续性。

只给当前尝试的证据位置、原意澄清或修复建议不进入冻结的共同输入。原 subagent 可以据此继续当前尝试；换同级执行者或升级时仍使用冻结的共同输入。若后续执行者必须收到某项补充才能正确完成任务，说明共同输入不完整；负责该范围的调度者更新任务说明，作废原失败连续性并从执行级重新开始。

subagent 在收到补充后判断它对已完成和当前工作的影响，选择保留当前工作、重新验证，或停止并报告。负责该范围的调度者认为可以继续，不能取消 subagent 的停止报告权。补充不要求立即写 checkpoint；下一份 checkpoint 必须说明已应用到哪个版本。

同一模型层级内，负责该范围的调度者根据 checkpoint 是否可用、错误做法是否会形成锚定、上下文压缩次数和复用成本，决定由原 subagent 继续当前尝试，还是由新的同级 subagent 从冻结的共同输入开始新尝试。subagent 可以报告无法继续，但不能自行安排替代者。

## checkpoint 模板与恢复

出现可恢复的状态变化才写 checkpoint，不按固定时间或工具调用次数写。触发点是：完成可单独证明的子结果、准备切换上下文、准备报告或等待、结束当前回合、系统上下文压缩、发现范围变化、权威冲突或停止条件。编号递增且保留旧文件；恢复时默认读取编号最大的 checkpoint。UTC 时间可记录审计，但不用于恢复排序。

    # checkpoint {编号}

    - 任务与任务说明版本：
    - 固定起始基线：
    - 任务工作目录：[任务工作区](相对路径)
    - worktree、分支和当前提交状态：
    - 本切片发生的系统上下文压缩次数：
    - 上一份 checkpoint：[checkpoint](相对路径)

    ## 当前仍有效的状态

    - 当前已应用的本层补充版本及来源（根级为会话全局版本）：
    - 当前共享约束版本及来源，或“无共享约束”：
    - 恢复所需的本切片来源：
      - [含义明确的名称](相对路径)
    - 当前处置：保留当前工作、重新验证、停止并报告，或其他明确状态：
    - 已完成结果及精确证据位置：
    - 尚未完成的工作：
    - 阻塞或未决事项：
    - 下一项具体动作：

    ## 自上一份 checkpoint 以来的补充事件

    - 本层补充版本：
      - 本切片消息路径：
      - 已应用、未应用或被后续版本取代：
      - 未应用或取代的理由：
      - 已应用后选择保留当前工作、重新验证或停止并报告：
      - 共享约束版本（仅在该补充改变共享约束时）：

“未收到补充”“收到但未应用”“无共享约束”“最近补充未改变共享约束”和“保留当前工作”是不同状态，必须分别写出。非共享补充不能擦除仍有效的共享约束或既有处置。写 checkpoint 前连续收到多条补充时，每条都在事件列表中保留；被后续版本取代但没有应用的版本也写明由哪一版本取代。未应用补充不能覆盖“当前已应用”的本层版本，也不能覆盖父级继承版本。

恢复同一次尚未完成尝试的 agent 只读取编号最大的 checkpoint、该文件列出的本切片来源和任务单，就能恢复当前有效状态和待处理补充；不扫描旧 checkpoint、其他切片文件或父级调度记录。完成后评审未通过而开始的新尝试，以及模型层级升级，不属于恢复，必须从冻结的共同输入开始。checkpoint 不复制完整提示、完整来源、长日志或长篇推理；最终报告汇总 checkpoint，不能替代过程中应保存的事实。

上下文压缩按切片计数。发生第 4 次压缩时，subagent 立即写 checkpoint 并通知负责该切片的调度者，默认依靠 checkpoint 继续；该调度者检查切片是否过宽、初始材料是否过长、任务是否扩张或输出是否过量，并可向父级报告或在授权范围内中断后重新切分。压缩不是模型失败。独立评审者若因上下文长度不能继续，写 checkpoint 并报告负责该范围的调度者，不自行更换评审者。

## 结果、评审和整合报告模板

每个 subagent 的终结报告都列出自己创建的 worktree、分支、临时文件和证据文件；没有创建时明确写“无”。执行结果报告交给直接父级，并至少写明：

    - 任务、任务说明版本、起始基线和当前共享约束：
    - 执行者声明：交付候选，或停止并报告：
    - 候选产物、worktree、分支和提交；只读任务给证据文件：
    - 已运行门禁及结果：
    - 每项验收条件的证据：
    - 尚未验证的前提、未覆盖范围和临时资源：
    - 停止或声明完成的具体依据：

独立评审报告必须自包含，至少写明：

    - 被要求回答的问题和范围；
    - 通过或不通过；
    - 事实及精确位置；
    - 事实如何支持结论；
    - 尚未验证的前提和未覆盖范围；
    - 每个缺陷各自的修复要求；
    - 受影响的既有评审；
    - 修复后需要复查的范围。

负责该范围的调度者在调度记录中把执行者声明和评审结论归入唯一最终结果分类，并对每份评审报告逐项记录采用、驳回或继续取证及理由。修复只作废受影响的评审；共享约束或接缝变化时，相关评审都重做。原评审者能够继续时由其复查，否则报告负责该范围的调度者，由其重新调度；影响父级条件时向父级报告。

整合报告至少写明固定输入、采用的切片提交或产物、共享约束、已知接缝、端到端验收、门禁结果、冲突、保留项和整合提交。Git worktree、对应任务分支和会话临时记录的清理指引按 [Git worktree 隔离与清理](git-worktrees.md) 编写。

## 状态模型验证例

以下例子检验上述完整规则，不替代它们：

- 执行者证明现有条件不可能通过门禁时，结果是“停止并报告”，不是模型失败；负责该范围的调度者只有在记录有意义变化及成功机会后才能重派。
- 执行者已经声明完成且独立评审不通过时，结果是“已完成但评审未通过”；若核心任务仍等价，按当前模型层级的失败连续性记一次有效失败。
- “目录核对”和“接口核对”收到同一共享更新时，前者可以使用本地消息回合 005，后者使用 008，但二者记录相同的本层补充版本和共享约束版本。随后只给“目录核对”的非共享补充不会改变“接口核对”的当前已应用本层版本、共享约束或处置；两份最大编号 checkpoint 各自保存自己的当前版本、共享约束和处置，因此可以独立恢复。
- “目录核对”在写 checkpoint 前先收到本层补充版本 6、再收到版本 7：checkpoint 分别记录两条事件。若版本 6 已应用而版本 7 尚未应用，当前已应用版本仍为 6；若版本 7 被版本 8 取代而未应用，事件中保留“版本 7 由版本 8 取代”，不能把版本 8 写成当前有效状态。
- 某切片已有两次有效失败后，只给当前执行者补充证据位置，下一次评审不通过仍是第三次有效失败并触发升级；升级后的执行者仍从冻结的共同输入开始。随后若输出协议改变，受影响切片开始新的失败连续性；未受影响切片保留原连续性。
- 一个切片第 4 次上下文压缩时立即写 checkpoint、通知负责该切片的调度者并继续依靠 checkpoint；该事件不增加模型失败次数。
- 同一核心任务下思考级累计三次有效失败时，负责该切片的调度者先核对连续性，再把冻结的共同输入和支撑三次失败的全部评审结论交给新的顾问分析 agent。
