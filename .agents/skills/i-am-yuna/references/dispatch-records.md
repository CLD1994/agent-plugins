# 调度记录与恢复

实际派遣、发送补充、恢复任务、记录失败或编写结果与评审报告时阅读。本文件是这些临时产物和状态的权威说明。

## 先区分版本与记录

参与者、固定起点、候选和 checkpoint 的含义见[参与者协议](participant-protocol.md#先区分材料与职责)。本文件另区分三个编号：

- **任务内容版本**：目标、行为、授权、范围、基线和验收这组条件的版本。
- **共同规则版本**：多个任务需要同时遵守的约定的版本。
- **任务消息序号**：单个任务内消息的先后顺序，不表示任务条件一定发生了变化。

先判断变的是哪一项，再更新相应记录。收到新消息不等于新任务，修改文件路径也不一定改变行为；后面的变更表用于判断是否影响已有结论与失败计数。

## 目录和产物

主工作区是当前仓库的主要工作目录；Git worktree（关联工作树）是同一仓库另行检出的目录。先确定产物属于哪个工作区，再建立记录：这样记录中的路径与真正被测、被修改的内容才指向同一处。

首次实际委派时，调度者在当前工作区的 `tmp/agents/<会话名>/` 建立 `dispatch-record.md`。会话名和任务名应稳定、简短且便于人类辨认。

使用独立 worktree 时，调度者在联系 subagent 前，把任务说明写到目标工作区的 `tmp/agents/<会话名>/<任务名>/task.md`；该任务的 checkpoint、结果和评审也保存在该目录。没有独立 worktree 时，在当前工作区建立同样的任务目录。

    <主工作区>/
      tmp/agents/2026-09-05-api-migration/
        dispatch-record.md
      .worktrees/schema-audit/
        tmp/agents/2026-09-05-api-migration/schema-audit/
          task.md
          checkpoints/001.md
          execution-result-001.md

只记录实际产生的产物、缺失的必需产物和仍需保留的临时资源。可选产物没有触发时，无需逐一解释为何不存在。

|产物|写入者|用途|
|-|-|-|
|调度记录|调度者|模型映射、切片、任务内容版本、共同规则版本、分配、尝试次数、结果、评审处理和临时资源|
|任务说明|调度者|subagent 当前唯一需要执行的目标、权限、范围、来源和验收|
|消息文件|发送者|仅在环境适配文档要求留档时，按任务保存不可变的完整消息|
|checkpoint|承担任务的 agent|同一次未完成尝试的可恢复状态|
|执行、评审或整合报告|完成相应角色的 agent|候选与证据、独立结论或整合结果|
|诊断报告|根因分析者|失败历史、证据和根因；不交给干净执行者|
|清理指引|检查清理状态的 agent|供人类查看和执行的状态概述与命令，不授权删除|

调度记录不向下级暴露。subagent 的固定行为来自[参与者协议](participant-protocol.md)，本次目标来自任务说明；恢复时读取同次尝试的 checkpoint 和新消息。

## 任务说明

任务说明只表达当前有效状态，不写授权沿革、旧版本、失败历史、模型升级原因或前一名执行者身份。没有内容的可选字段直接省略。

填写前先检查：哪些内容是参与者每次都遵守的规则，哪些内容只有本次任务才不同。前者引用固定协议，后者才写入任务说明，避免改一份任务时无意生成另一套通用规则。

固定行为通过参与者协议及其必需参考的绝对路径、版本定位直接提供：可使用固定提交中的只读工作树，或保存协议及其逐层引用的必需文件的不可变快照，不能只指向会继续修改的技能目录。调度者先核验可读与完整性，subagent 实际读取；更新协议时按下方任务内容规则明确处理，不静默替换在途版本。

首次派遣将工作目录、任务路径和固定协议路径及版本定位作为同一启动信息交付；恢复沿用所固定版本。参与者的读取顺序统一按[协议的启动与恢复表](participant-protocol.md#开始与停止)。

临时调度文件及交接消息中的文件和目录引用统一使用绝对路径，包括工作目录、来源、执行计划、产物、命令参数和 Markdown 链接目标。同一目标使用同一个已核对的绝对路径；调度者在派遣前解析并核对来源与目标工作区，执行者可以直接使用这些路径。工作目录仍须明确，用于设置命令执行环境。跨工作区读取时，路径明确指向实际拥有该文件的工作区。

下列模板中的路径占位符在生成任务文件时替换为本次运行的绝对路径。技能自身及仓库长期文档的链接保持可移植的相对写法。

## 任务内容、共同规则和消息顺序

调度者按本文开头定义的三个编号分别维护记录。

不同任务各自保存消息顺序，不需要全局同步。任务内容和共同规则分别变更；不建立跨任务的消息编号映射，也不把这些版本沿革暴露给需要干净上下文的执行者。

补充信息后，调度者根据实际含义处理：

|变化|处理|
|-|-|
|只补充证据位置、澄清原意或提供不改变契约的实现建议|保留当前任务内容版本和已有失败记录；subagent 判断当前工作是否需要重新验证，并在下一个必要 checkpoint 中记录|
|改变可观察行为、授权、范围、起始基线、核心约束或验收条件|更新任务内容；相关失败和评审失效，从执行级开始新的流程|
|改变多个任务共同遵守的规则|更新共同规则版本并通知所有受影响任务；是否使已有结果失效取决于该变化是否改变原结论前提|

调度者认为可以继续，不取消 subagent 的停止报告权。subagent 发现补充与现状冲突或无法安全应用时，应保存证据并报告。

## 固定任务材料和失败次数

“固定任务材料”是用于比较不同尝试的相同输入条件。只有条件相同，失败次数才能说明同一层级在这项任务上的表现；更换了行为或起点后，旧失败不能直接证明新任务仍需升级。

需要比较多次尝试或升级模型层级时，调度者固定以下材料：当前任务内容、同一修订的权威来源、起始基线、适用的项目规则、参与者协议及必需参考、验收条件。工作目录、分支、交付路径、模型身份和当次运行编号属于运行信息，不属于固定任务材料。

只有执行者已经声明完成并交付完整候选，随后正式评审判定不通过，才算一次有效失败。执行中自行发现设计冲突、条件不足、环境问题或门禁不可能通过并停止报告，不算失败。同一模型层级换人不会清零；固定任务材料发生实质变化时，旧失败不再用于升级。

调度者可以让原执行者根据评审指导继续下一次尝试，也可以在旧做法可能形成锚定或现有上下文已过长时，换一名同级执行者作干净尝试。新的同级执行者和升级后的执行者只收到相同的固定任务材料，不读取旧候选、旧评审、修复建议、checkpoint 或执行者身份。若新执行者必须依赖旧尝试中的某项信息才能正确执行，说明固定任务材料不完整；应修正任务内容并从执行级重新开始，而不是升级模型。

## 升级和根因分析

模型能力升级按以下顺序进行：

1. 执行级在相同固定任务材料下累计三次有效失败后，派新的思考级执行者从相同材料重新执行。
2. 思考级也累计三次有效失败后，派顾问级根因分析者。它读取固定任务材料、三次候选和评审，以及相关修复指导、验证和环境证据；可以自行选择分析方法、补充调查和组织证据。
3. 根因分析者按任务中指定的两个不同位置交付文件：`diagnosis.md` 解释历史、证据和根因，供调度者读取；全新执行任务目录中的 `task.md` 只写当前正确目标、完整上下文和验收。后者不能覆盖根因分析者收到的任务说明。
4. 调度者检查 `task.md` 是否擅自改变行为、扩大权限或代替用户作产品与风险决定，并确认基线、来源和验收完整。通过后直接引用，不重新调查或转写。
5. 新的思考级执行者只收到中性的任务说明链接（目标为 `task.md` 的绝对路径）和本次运行信息。它不知道任务说明的来源，也不读取 `diagnosis.md`、历史候选、评审、checkpoint 或身份信息。
6. 同一名思考级执行者可以完成最多三次候选尝试；同一名根因分析者评审每次已声明完成的候选，并可把当前缺陷作为下一次尝试的指导。每次“声明完成且根因分析者评审不通过”计一次有效失败。

如果根因分析者的 `task.md` 被发现实质改变了行为、基线、范围或验收，停止自动重试并请用户处理；仅补全不改变原意的来源位置不构成实质变化。

三次顾问评审仍未通过后，调度者记录事实并请实际用户介入，不能用父任务中的一般授权跳过。用户给出修正方向或新的任务说明时，从执行级开始；用户确认任务说明正确且认为问题在模型能力时，申请用户批准匿名比较。批准后，顾问级可以在比较中承担执行角色。

## checkpoint、证据与角色报告

参与者直接按[参与者协议](participant-protocol.md)保存 checkpoint、候选与验证证据，并交付对应角色报告。调度者维护本任务的路径与版本，不转写这些固定行为。

## 交接检查

先回答三个问题：内容能否取回、是否就是被检查的版本、是否允许进入下一阶段。提交存在只能帮助回答第一个问题，测试通过只能回答部分第二个问题；权限和未决事项仍须独立核对。因此，以下检查分别设置在交接发生之前，而不是等到采用时补查。

以下检查由直接调度者负责，不能用参与者的完成声明代替。候选保存条件以[参与者协议](participant-protocol.md#候选保存)为准。

| 时点 | 检查与放行条件 |
| --- | --- |
| 派遣前 | 固定协议及必需参考可读取、版本可恢复；任务权威、权限和验收明确；起点完整可恢复。给出命名候选分支及本地保存授权，或已经批准并验证的替代保存方式。 |
| 接收交付 | 候选提交或快照确实存在，范围与任务一致，必要新增文件没有遗漏；报告与证据绑定实际输入，必需的非 Git 材料已完整保存。缺项交补齐或停止，不宣称完成。 |
| 发起评审 | 给评审者固定候选与证据位置；评审期间候选不变，更改后必须明确新输入并重核受影响结论。 |
| 批准下一轮修改 | 上一交付及证据已永久保存；本轮输入明确，固定任务起点继续保留。只保留哈希但找不到内容时停止，不以当前工作树替代历史输入。 |
| 重试或升级 | 核验原固定任务材料仍可恢复，按本文件的隔离和计数规则派遣；新任务材料包含所固定的协议版本。 |
| 采用 | 必需评审、验证和未决事项已处理，明确采用的准确候选；候选分支有提交不表示已获合并授权。 |

Git 检查优先使用现成命令：用 `git cat-file -e '<commit>^{commit}'` 确认提交存在，`git diff <base> <candidate> --name-status` 核对提交范围，`git status --short --untracked-files=all` 核对遗漏，`git show <candidate>:<path>` 核对必要文件确实入库。用实际提交和路径替换占位符；提交存在不证明工作树一致，状态干净也不证明被忽略的证据已保存，两者分别核验。替代快照按恢复步骤实际重建并核验清单。

调度者阅读全部评审结论，记录采用、驳回或继续取证的理由；确认修复内容未改变既定行为、授权、范围和验收后，直接引用评审者的建议或计划，不另写一份。原评审者无法继续或上下文过长时，由调度者决定是否重新切分或更换。
