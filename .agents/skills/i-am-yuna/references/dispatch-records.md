# 调度记录、补充说明与恢复

在写任务单、发送补充说明、接收结果、恢复切片、记录失败或准备清理时阅读。本文件是这些产物、状态和模板的唯一权威位置。

## 目录和产物

每次会话使用一个稳定且人类可读的会话名。每个 subagent 任务使用一个稳定且人类可读的任务名；回合和 checkpoint 编号从 001 起递增。以下是完整示例：

    /tmp/agents/2026-09-03-api-migration/
      dispatch-record.md
      subagent/schema-audit/
        task.md
        main-001.md
        subagent-002.md
        checkpoints/001.md
        execution-result-001.md
      subagent/review-schema-audit/
        task.md
        main-001.md
        review-report-001.md
      subagent/integrate-api-migration/
        task.md
        integration-report-001.md
      subagent/cleanup-api-migration/
        task.md
        cleanup-list-001.md

每个任务目录的消息回合是本切片自己的单调序列，且只用于排列该切片的消息文件。不同切片的回合号不需要相同。

|产物|写入者|读取者|权威内容与最小字段|
|-|-|-|-|
|Main 调度记录|Main|Main 及其恢复者；subagent 不读取|会话的调度事实：用户任务、任务说明版本、起始基线、当前模型映射及来源、切片、角色、模型层级、worktree 与分支、共享约束和版本、全局补充到本地消息路径的映射、每个切片的失败连续性及有效失败次数、门禁、最终结果分类、评审处置、采用决定、临时资源与清理状态。|
|subagent 任务单|Main|指定 subagent 及其恢复者|该切片唯一可执行授权：具体交付物、起始基线和任务说明版本、行为和授权边界、共享约束及初始状态、允许读取的权威路径、允许修改范围、验收与已知验证、停止条件、checkpoint/结果/评审/提交位置、已批准计划与标为建议的实现预估、禁止加载的 skill。|
|补充说明|Main|指定 subagent|原样消息和版本化变化：本地消息回合、全局补充版本、影响的切片、共享约束版本或“未改变共享约束”、变化本身、既有失败记录保留或作废的判断及理由。|
|subagent checkpoint|该 subagent|同一切片的恢复者和 Main；其他切片不读取|该切片当前仍有效的可恢复状态、补充事件、证据、未完成项和下一动作。完整字段见“checkpoint 模板”。|
|执行结果报告|执行 subagent|Main 和指定独立评审者|候选声明或停止报告、范围、起始基线、产物或提交、已运行门禁与结果、验收证据、已知未覆盖项、停止或完成的依据、临时资源；最终结果分类由 Main 写入调度记录。|
|评审报告|独立评审 subagent|Main；Main 决定后向修复任务提供需要的部分|独立结论和可执行修复要求。完整字段见“评审报告模板”。|
|整合报告|整合 subagent|Main 和最终评审者|固定输入、已整合产物、接缝、端到端门禁、冲突与提交。|
|清理清单|执行级清理 subagent|Main|可删除项、必须保留项、脏文件、未合并独有内容、证据、删除的前提和不可逆风险。它不授权删除。|
|Yuna 调度经验|Main|后续 Main|有具体证据的调度、切分和上下文压缩经验；单次事件只形成窄结论。|
|Yuna 模型难度记录|身份揭示前已固定结论的独立评估者|后续 Main|匿名比较的模型难度结论、匿名证据和最低完整通过层级。|

任务并不必然生成表中的所有文件。只读事实核对不生成执行提交；没有独立评审需求时不生成评审报告；没有写入切片或临时资源时不生成整合或清理产物。Main 在调度记录中写明每个未生成产物的触发条件不成立。

## 补充说明、共享约束和失败连续性

补充说明同时维护三种独立编号或状态：

|名称|谁的范围|何时变化|作用|
|-|-|-|-|
|本地消息回合|一个切片|该切片产生下一条主从消息时|只决定该切片消息文件顺序|
|全局补充版本|Main 会话|Main 发出任一补充时单调递增|审计补充的投递顺序|
|共享约束版本|所有受影响切片|共享约束实际改变时单调递增|表示受影响切片共同遵守的约束|

同一共享补充投递给多个切片时，每个切片使用自己的下一个本地消息回合，但携带相同的全局补充版本和共享约束版本。Main 调度记录必须保存这个全局版本到各切片本地消息路径的映射。只影响一个切片的非共享补充仍有全局补充版本，但不改变其他切片的当前版本、共享约束或处置。

补充可以按顺序累积，不能以“任务单文字必须逐字不变”为理由重启工作。Main 在每份补充中判断既有失败记录是否仍有效并说明理由：

|补充实际改变的内容|失败连续性和既有评审|
|-|-|
|只补充证据位置、澄清原意，或给出修复建议，且不改变既有结论前提|保留受影响切片的失败连续性；已有评审仍按其范围有效|
|可观察行为、用户授权、起始基线、核心约束、验收条件，或足以改变既有评审结论的前提|作废受影响记录和评审；受影响切片开始新的失败连续性|
|只影响某一切片且不改变共享约束|只更新该切片；其他切片保留自己的有效状态和失败连续性|
|共享约束改变|所有受影响切片接收同一共享约束版本；Main 对它们记录相同的失败连续性保留或新建决定|

全局补充版本只表示审计顺序，不能单独决定失败是否连续。Main 对每个切片维护人类可读的失败连续性：只要核心任务和仍有效的行为、授权、起始基线、核心约束、验收条件等价，新的“已完成但评审未通过”结果继续累计，即使其间有新的全局补充版本。每次有效失败记录当时已应用的全局补充版本、所属连续性、评审报告路径，以及保留或作废理由。同层级换人不清零；任务说明发生足以改变上述状态的变化才新建受影响切片的连续性。

subagent 在收到补充后判断它对已完成和当前工作的影响，选择保留当前工作、重新验证，或停止并报告。Main 认为可以继续，不能取消 subagent 的停止报告权。补充不要求立即写 checkpoint；下一份 checkpoint 必须说明已应用到哪个版本。

同一模型层级内，Main 根据 checkpoint 是否可用、错误做法是否会形成锚定、上下文压缩次数和复用成本，决定由原 subagent 修复还是换同层级的新 subagent。subagent 可以报告无法继续，但不能自行安排替代者。

## checkpoint 模板与恢复

出现可恢复的状态变化才写 checkpoint，不按固定时间或工具调用次数写。触发点是：完成可单独证明的子结果、准备切换上下文、准备报告或等待、结束当前回合、系统上下文压缩、发现范围变化、权威冲突或停止条件。编号递增且保留旧文件；恢复时默认读取编号最大的 checkpoint。UTC 时间可记录审计，但不用于恢复排序。

    # checkpoint {编号}

    - 任务与任务说明版本：
    - 固定起始基线：
    - worktree、分支和当前提交状态：
    - 本切片发生的系统上下文压缩次数：
    - 上一份 checkpoint 路径：

    ## 当前仍有效的状态

    - 当前已应用的全局补充版本及来源：
    - 当前共享约束版本及来源，或“无共享约束”：
    - 恢复所需的本切片来源绝对路径：
    - 当前处置：保留当前工作、重新验证、停止并报告，或其他明确状态：
    - 已完成结果及精确证据位置：
    - 尚未完成的工作：
    - 阻塞或未决事项：
    - 下一项具体动作：

    ## 自上一份 checkpoint 以来的补充事件

    - 全局补充版本：
      - 本切片消息路径：
      - 已应用、未应用或被后续版本取代：
      - 未应用或取代的理由：
      - 已应用后选择保留当前工作、重新验证或停止并报告：
      - 共享约束版本（仅在该补充改变共享约束时）：

“未收到补充”“收到但未应用”“无共享约束”“最近补充未改变共享约束”和“保留当前工作”是不同状态，必须分别写出。非共享补充不能擦除仍有效的共享约束或既有处置。写 checkpoint 前连续收到多条补充时，每条都在事件列表中保留；被后续版本取代但没有应用的版本也写明由哪一版本取代。未应用补充不能覆盖“当前已应用”的全局版本。

恢复者只读取编号最大的 checkpoint、该文件列出的本切片来源绝对路径和任务单，就能恢复当前有效状态和待处理补充；不扫描旧 checkpoint、其他切片文件或 Main 调度记录。checkpoint 不复制完整提示、完整来源、长日志或长篇推理；最终报告汇总 checkpoint，不能替代过程中应保存的事实。

上下文压缩按切片计数。发生第 4 次压缩时，subagent 立即写 checkpoint 并通知 Main，默认依靠 checkpoint 继续；Main 检查切片是否过宽、初始材料是否过长、任务是否扩张或输出是否过量，并可中断后重新切分。压缩不是模型失败。独立评审者若因上下文长度不能继续，写 checkpoint 并报告 Main，不自行更换评审者。

## 结果、评审和整合报告模板

每个 subagent 的终结报告都列出自己创建的 worktree、分支、临时文件和证据文件；没有创建时明确写“无”。执行结果报告至少写明：

    - 任务、任务说明版本、起始基线和当前共享约束：
    - 执行者声明：交付候选，或停止并报告：
    - 候选产物、worktree、分支和提交；只读任务给证据文件：
    - 已运行门禁及结果：
    - 每项验收条件的证据：
    - 尚未验证的前提、未覆盖范围和临时资源：
    - 停止或声明完成的具体依据：

独立评审报告必须自包含，至少写明：

    - 被要求回答的问题和范围；
    - 通过或不通过；
    - 事实及精确位置；
    - 事实如何支持结论；
    - 尚未验证的前提和未覆盖范围；
    - 每个缺陷各自的修复要求；
    - 受影响的既有评审；
    - 修复后需要复查的范围。

Main 在调度记录中把执行者声明和评审结论归入唯一最终结果分类。Main 对每份评审报告逐项记录采用、驳回或继续取证及理由。修复只作废受影响的评审；共享约束或接缝变化时，相关评审都重做。原评审者能够继续时由其复查，否则报告 Main，由 Main 重新调度。

整合报告至少写明固定输入、采用的切片提交或产物、共享约束、已知接缝、端到端验收、门禁结果、冲突、保留项和整合提交。清理清单至少写明每项资源的路径、状态、删除或保留建议、证据、脏文件或独有内容、所需授权和不可逆风险。

## 状态模型验证例

以下例子检验上述完整规则，不替代它们：

- 执行者证明现有条件不可能通过门禁时，结果是“停止并报告”，不是模型失败；Main 只有在记录有意义变化及成功机会后才能重派。
- 执行者已经声明完成且独立评审不通过时，结果是“已完成但评审未通过”；若核心任务仍等价，按当前模型层级的失败连续性记一次有效失败。
- “目录核对”和“接口核对”收到同一共享更新时，前者可以使用本地消息回合 005，后者使用 008，但二者记录相同的全局补充版本和共享约束版本。随后只给“目录核对”的非共享补充不会改变“接口核对”的当前已应用全局版本、共享约束或处置；两份最大编号 checkpoint 各自保存自己的当前版本、共享约束和处置，因此可以独立恢复。
- “目录核对”在写 checkpoint 前先收到全局补充版本 6、再收到版本 7：checkpoint 分别记录两条事件。若版本 6 已应用而版本 7 尚未应用，当前已应用版本仍为 6；若版本 7 被版本 8 取代而未应用，事件中保留“版本 7 由版本 8 取代”，不能把版本 8 写成当前有效状态。
- 某切片已有两次有效失败后，只补充证据路径并产生新的全局补充版本，下一次评审不通过仍是第三次有效失败并触发升级。随后若输出协议改变，受影响切片开始新的失败连续性；未受影响切片保留原连续性。
- 一个切片第 4 次上下文压缩时立即写 checkpoint、通知 Main 并继续依靠 checkpoint；该事件不增加模型失败次数。
- 同一核心任务下思考级累计三次有效失败时，Main 先核对连续性，再派新的顾问分析 agent；它只读取当前任务说明和思考级评审结论。
