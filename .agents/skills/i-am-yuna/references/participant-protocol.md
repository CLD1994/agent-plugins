# 参与者协议

本协议写给接收并承担子任务的 agent，称为“参与者”或 subagent。派发该任务并接收结果的 agent 是它的“直接调度者”；最上层、面向用户负责整个任务的调度者称为根级 Main。一个参与者若获准继续管理下级，也会成为嵌套调度者；只完成当前任务而不管理下级的参与者称为纯执行者。

## 先区分材料与职责

| 概念 | 本文含义 |
| --- | --- |
| 参与者协议与任务说明 | 协议定义跨任务复用的行为；任务说明只填写本次目标、角色、权限、范围、起点、依据、验收和输出位置。 |
| 固定版本 | 已保存完整内容、可以独立取回的特定版本。提交 ID 或快照清单用来定位和核验它，版本标识本身不代替内容。 |
| 起点与候选 | 起点是本任务开始时的输入；候选是一次准备交付检查的产物。后续修复的输入可以是已保存的候选，但不因此改写原固定起点。 |
| 快照与哈希 | 快照保存某一时刻的完整内容；哈希是内容的校验值，只能检查一致性。 |
| 工作树 | 当前正在编辑的目录及其文件状态，可能包含任务开始后的变化，不能替代任务固定输入。Git worktree 是另行检出的关联工作树，其隔离规则见对应参考。 |
| checkpoint（检查点） | 同一次未完成尝试的进度记录，说明做到哪里、证据在哪以及下一步；它与源码快照分别保存。 |
| 压缩恢复与干净重试 | 压缩恢复是在上下文被精简后接续同一次尝试；干净重试是另开执行上下文，只从指定的固定材料重新开始。 |
| 权威来源与验收门禁 | 权威来源定义任务已确认的行为；验收门禁是允许声明完成前必须满足的检查条件。建议或调查观察不能自行成为权威。 |
| 工作角色与模型层级 | 角色说明本次交付什么，见下方角色表；层级是调度者按已确认映射填写的能力与成本类别，取值为执行级、思考级、顾问级。角色为“执行”不等于层级为“执行级”。 |
| 环境适配 | 特定运行环境的工具调用与消息传递规则，本文在 Codex 中使用对应适配文件。 |

本协议是固定参与者行为的唯一来源；任务说明引用其固定版本。调度者也读取本协议检查交付。纯执行者无需加载调度技能正文；符合下方管理资格且确需管理下级时，另外加载 [调度规范](../SKILL.md)。

## 如何判断适用范围与冲突

保存、验证和权限解决的是不同问题：保存回答“能否取回产物”，验证回答“行为是否正确”，权限回答“是否允许做这个动作”。前两项成立不能替代第三项。

遇到看似冲突的要求，先核对它们是否约束同一对象、同一阶段和同一动作，再检查权限和指令优先级。例如，“保存候选”与“尚未允许合并”约束不同动作，可以同时满足；“必须提交候选”与用户“禁止提交”约束同一动作，需要停下处理。

因此，真正冲突时停止相关动作，列出冲突、优先级和受影响范围，向直接调度者报告；独立且已授权的工作可继续。本文的判断依据用于识别适用条件，不授权参与者自行降低保存或验收要求，也不改变更高优先级指令。

## 开始与停止

先判断现在是首次执行、同次恢复还是干净重试，再确认应该读取哪个版本。这样可以避免把当前工作树的新规则当作旧任务的依据，也避免把已完成的副作用重复执行。下表规定的是开始任务动作前的读取顺序；读取材料本身不表示获得执行授权。

派遣启动信息必须同时提供工作目录、任务说明绝对路径、固定协议绝对路径及版本定位。协议及其必需参考的完整内容须可读取；只收到任务路径、可变目录链接或缺失快照时，停止任务动作，请直接调度者补齐，不能猜测同名协议版本。

| 进入状态 | 实际读取顺序与放行条件 |
| --- | --- |
| 首次执行或干净重试 | 启动信息指定的固定协议 → 适用的环境适配 → 本次任务说明 → 任务必需权威；核验输入后开始。干净重试只读取本次指定的固定材料。 |
| 同一次尝试压缩恢复，有 checkpoint | 固定协议 → 环境适配 → 当前任务说明 → 编号最大的 checkpoint → 其已处理序号之后的消息，按序读取 → 尚未实际读取的必要权威；核对更新后继续。已处理消息不重复执行，每个新动作完成后推进已处理位置。 |
| 同一次尝试压缩恢复，无 checkpoint | 固定协议 → 环境适配 → 当前任务说明 → 已保存的本次消息、报告与源码；先重建状态并新建补救 checkpoint，无法确认是否已执行的副作用先核验，不直接重放。 |
| 固定协议、任务或必需输入缺失/冲突 | 停止依赖该输入的动作并报告；已有 checkpoint 或当前工作树中的新技能不能替代缺失输入。 |

上述顺序是恢复的统一顺序。新消息改变范围、权限、起点或验收时，先报告并取得明确的任务更新；更新协议时须重新给出完整固定版本。主工作树中的技能更新不自动改变本次输入。

执行前核对任务给出的协议版本、工作目录、角色、可否管理下级，以及必须读取的来源。固定输入须有可读取的完整内容；保存与核验方式见[候选保存](#候选保存)。只有哈希、失效路径或无法重建的差异时，停止依赖该输入的工作并报告。

任务列出的权威来源与调查入口不是读取白名单，可以读取授权范围内新发现的相关来源。遇到权威冲突、未定义行为、需要改变范围或无法满足验收时，保存证据并报告；由有权者决定，不以实现便利补全语义。明确的隔离禁读范围继续有效。

继续派遣需要分别回答“本任务是否允许管理下级”和“被分配的层级是否具备管理资格”。两者不是同一条件，较强的模型不自动获得更大权限。因此，管理资格以任务说明中可见的“可否管理下级”和“模型层级”判断，不读取隐藏调度记录或猜测自己的模型身份。模型层级由直接调度者按已确认映射填写，与工作角色分别记录。

| 任务管理授权 | 任务模型层级 | 参与者动作 |
| --- | --- | --- |
| 不允许 | 任意 | 仅完成当前任务，不委派。 |
| 允许 | 执行级 | 不委派，向直接调度者报告资格冲突。 |
| 允许 | 思考级或顾问级 | 加载固定版调度规范，再判断是否值得委派；资格不等于必须派遣。 |
| 缺失、未知，或允许但层级缺失/未知 | 未确认 | 不委派，请直接调度者补齐；不妨碍独立且已授权的当前任务。 |

全局采用、合并和清理由根级 Main 决定，除非已有针对命名对象和动作的明确授权。

## 按角色工作

角色划分用于明确谁实现、谁独立检查、谁负责交接，避免把完成声明当成评审结论。以下角色只规定当前职责，不授予超出任务范围的动作。

| 角色 | 主体工作与交付边界 |
| --- | --- |
| 执行 | 按已批准任务或计划实现，选择未被固定的局部做法；逐项提交产物与验证。不编写或改写任务级计划，发现计划不足先报告。 |
| 事实核对 | 交付事实、来源位置、验证方法及未知项；只读候选，不把观察结果变成产品决定。 |
| 独立评审 | 不参与被评候选的实现；核验实际产物和证据，逐问题提供自包含修复建议。涉及状态、恢复或跨组件依赖时，交付顺序、契约、反例与阶段门禁明确的修复计划。 |
| 整合 | 只读取固定基线、已采用切片、共同规则与接缝验收；验证组合行为，发现冲突报告，不读取未采用候选的历史来补全契约。 |
| 根因分析 | 分别交付诊断报告与只表达当前目标的完整任务说明；不扩大权限或代替用户选择行为，不直接派遣执行者。 |

评审的每个发现分别写明触发场景、根因、被违反的不变量、修复边界、验证方式和未核验前提。后续评审区分回归、未完整修复、潜伏缺陷和验收缺口；同一不变量反复失败时补齐状态与反例矩阵。修复计划交调度者核对后再执行。

## 候选保存

先问下一位执行者能否取回与本次检查完全相同的输入，再选择保存方式。本地 Git 提交保存纳入提交的文件版本，候选分支保留这些提交。未纳入提交的文件仍需另行保存。即使工作树当前没有改动，也不能据此判断被忽略的验证材料已被保存。

因此，保存的目标是可恢复，而不是制造一个“已完成”的标识；有授权且可用 Git 时按下表提交，不能提交时落实经授权的等价保存方式。

写入型任务的起点、每次交付候选和后续修复都须能独立恢复。检查范围包括任务所需的代码、测试、配置、新增文件及验证脚本；哈希用于核验完整性，不保存内容。

| 对象与状态 | 保存与放行条件 |
| --- | --- |
| Git 中的写入型任务起点 | 调度者在派遣前固定完整起点提交；已有未提交输入先按授权保存到命名候选分支，核验后才派遣。 |
| 写入型候选交付 | 执行者在指定候选分支创建本地提交，明确提交范围并包含必要新增文件；核验任务范围内没有遗漏的暂存、未暂存或未跟踪产物，再报告完整提交 ID。 |
| 评审后继续修复 | 先确认上一候选已保存；新增提交保留先前交付，不改写已交付历史。固定任务起点与本轮修复输入分别记录。 |
| 中断或主动停止，产物未完成 | 保存可恢复的进行中提交和 checkpoint，并明确未完成、未验证项；保存不意味着声明完成。突发退出只能按实际留存材料恢复，无法恢复的部分明确列出。 |
| 用户禁止提交或环境无 Git | 停止需要保存的写入步骤，请调度者落实经授权的替代方式：完整快照，或已保留基线加包含新增/二进制文件的完整差异；须有清单、内容、校验值，并在隔离位置验证可恢复。仅记录哈希或工作区路径不足以放行。 |
| 只读调查或评审 | 保留独立报告和证据，不为交付制造候选代码提交。 |

本地候选提交不表示测试通过、评审通过、主线采用或允许推送。提交只包含本任务授权产物；共享工作区的无关改动不纳入。需要隔离写入或清理指引时读取 [Git worktree 规则](git-worktrees.md)。

被忽略的任务说明、报告、原始日志和临时验证脚本，按版本保存完整文件，供对应输入独立重放；无需强制加入源码提交。已交付文件保持不可变，修订另建编号并链接原件。必要的非 Git 输入随证据保存完整快照与清单，不能只在源码提交外留下一个会继续变化的脚本。保密材料按授权存储，不能为留证提交密钥或无关用户数据。

## 验证与交付状态

判断一条验证结论时，依次核对：实际测了哪个输入、运行了什么命令、原始结果是否留存、它覆盖哪项验收条件。任何一项缺失，都要缩小结论，而不是从“现在通过”推断“过去失败过”。红测指测试实际失败的运行，绿测指测试实际通过的运行。

每组验收证据绑定实际输入版本、精确命令、工作目录、结果与原始输出位置。输入版本使用完整提交 ID；测试时尚未提交的输入须在后续修改前保存可恢复内容，确认与被测内容一致。红测与绿测分别绑定各自输入，不能用最后的代码提交代表两次运行。

| 证据状态 | 报告方式 |
| --- | --- |
| 实际执行且原始结果保留 | 链接输入、命令、退出码和输出，说明证明的验收分区。 |
| 当前补充测试通过 | 只证明当前覆盖，不反推历史失败。 |
| 未运行、日志丢失或输入不可恢复 | 明确未验证或证据缺失；若影响必需门禁，停止该门禁并交调度者处理。 |
| 检查失败 | 保留失败结果、定位原因，区分候选缺陷、既有问题和环境限制；不得静默排除或记录为通过。 |

执行报告写明固定起点、本轮输入、候选提交或快照、实际修改范围、逐项验收证据、未覆盖项、停止原因及临时资源。评审报告绑定被评候选，给出独立结论和逐项修复依据；整合报告绑定被采用输入及端到端证据。每轮报告独立保存。

交付时明确选择“候选完成，等待必要评审”或“停止并报告”。源码已保存与任务已完成分别判断；缺少必需产物、验证或决策时不声明完成。执行者的完成声明不替代独立评审或 Main 的采用决定。

## checkpoint 与恢复

恢复需要分别知道“代码是什么”和“工作做到哪里”：源码版本回答前者，checkpoint 回答后者，消息记录补充其后的更新。运行环境 Harness（承载 agent 会话与上下文的程序）可能突然中断，不能假设总有机会在退出前补写。

checkpoint 保存同一次未完成尝试的工作状态，不替代源码快照或结果报告。完成可恢复的阶段、准备等待或切换任务时，若有新的重要状态则递增新建；没有变化不重复写。普通进度消息不充当 checkpoint。

checkpoint 至少包括：任务与协议固定版本、工作目录、起点和当前保存的代码版本、分支与未提交状态、已完成结果及证据、未完成项、阻塞、下一步；启用消息留档时加已处理序号和待处理消息。

checkpoint 从 `001` 递增，最新指编号最大者，旧文件保持不变。Harness 明确显示压缩时按[启动与恢复表](#开始与停止)读取，不用有损摘要覆盖原件。仅计 Harness 明示的压缩次数，第四次时通知调度者检查任务宽度。

## 环境交互

在 Codex 接收、回复或恢复任务时，完整读取 [Codex 交互规则](codex-subagent.md)，按其条件决定消息留档。通信适配只定义工具与文件交互，不改变本协议的角色、权限和交付规则。
