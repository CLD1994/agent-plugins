# Git worktree 隔离与清理

需要隔离多个写入者、为写入任务保留独立基线，或需要检查、保留、归档或清理任务工作区时阅读。本文件说明 Git worktree 方案和无 Git 时的处理方式；任务单、checkpoint 和报告的字段仍以 [调度记录、补充说明与恢复](dispatch-records.md) 为准。

## 判断是否需要 Git

只有多个任务会写入同一份可变状态，或写入任务需要独立基线时，才建立 linked worktree。只读任务和单一写入者不因使用 subagent 自动增加 worktree。

需要隔离写入但当前环境没有 Git，或当前工作区不是 Git 仓库时，先向用户说明采用 Git 的收益以及安装或初始化、忽略规则和首个提交会产生的变化。用户同意后按其明确选择执行，不自动把现有全部文件加入首个提交。用户拒绝 Git 后，列出当前环境实际支持的隔离方案及各自影响，由用户决定；没有获准且可靠的隔离方式时，不并行安排会写入同一状态的任务。

## 工作区和临时目录

工作区位置按以下顺序确定：

1. 使用用户或项目已经规定的目录；
2. 没有约定时，使用 Git 主工作区的 `.worktrees/`；
3. 所有 linked worktree 都作为该目录的直接子目录，不在 linked worktree 中继续嵌套 `.worktrees/`。

当前工作区本身是 linked worktree 时，通过 `git worktree list --porcelain` 查询主工作区，不根据当前路径猜测。没有可写的主工作区时，向用户请求工作区存放位置。每个工作区使用稳定且人类可读的名称，并在自己的 `tmp/agents/` 下保存本工作区的任务单、消息、checkpoint 和报告。

创建 linked worktree 前，在主工作区用 `git check-ignore` 验证候选的 `.worktrees/<任务名>/` 和仓库根目录 `tmp/agents/<会话名>/` 都会被忽略，并确认规则来自项目的 `.gitignore` 或等价共享配置。linked worktree 创建后，再在该工作区验证其 `tmp/agents/<会话名>/`。现有项目规则没有覆盖目标目录时，向用户申请在 `.gitignore` 中加入根目录规则：

```gitignore
/.worktrees/
/tmp/
```

项目已有等价或更合适的规则时沿用，不重复添加。用户批准后，先让忽略规则进入将用于创建 linked worktree 的固定基线，再创建任务工作区；用户不批准时，请用户指定另一个已经忽略的位置。

发起调度的 agent 在目标工作区创建任务目录并写好任务单后，才联系 subagent。任务单明确给出任务工作目录的 Markdown 链接；其他文件链接相对包含链接的 Markdown 文件解析。如何让命令在该目录运行，由当前 Harness 的适配文档规定。

## 清理指引

Git worktree、对应任务分支和 `tmp/agents/<会话名>/` 默认由人类决定并执行清理。agent 检查实际状态后，只为每个工作区提供：

- 路径、分支和一句状态概述；
- 查看详细状态的命令；
- 没有未提交改动或未采用的独有提交时，可供人类执行的非强制清理命令；
- 存在风险时，一句明确警告，不默认提供强制删除命令。

优先使用 `git worktree remove` 和普通分支删除，不用直接递归删除目录代替 Git 的工作区管理。`git worktree prune` 也默认只作为人类清理指引，不由 agent 自动执行。删除 linked worktree 会同时删除其中未跟踪的任务记录；清理指引提醒这一结果，不自动复制或归档记录。主工作区中的会话记录不会随 linked worktree 消失，任务完成时报告其位置并给出一条只针对该命名目录的清理命令。

用户明确要求 agent 代为清理命名 worktree、对应分支或会话记录时，以该指令为准。执行前解析并核对准确目标；状态干净且相关提交已经采用时使用非强制命令。存在未提交改动、未采用的独有提交或状态不明时先报告，只有用户明确确认丢弃这些具体内容后，才能使用 `--force`、`-D` 或等价操作。
