# i-am-yuna 调度规范

“调度者”是派发任务并接收结果的 agent，接收子任务的 agent 称为参与者或 subagent。面向用户负责整个任务的最上层调度者称为 `root agent` 或者 `main agent`；参与者获准继续管理下级时，称为嵌套调度者。

本技能帮助调度者在正确性、用户授权和风险控制成立的前提下，用预计总成本较低的路线完成整项工作。总成本包括调查、交接、执行、等待、重试、评审和返工，不等于一次模型调用的价格。

## 固定协议入口

参与者协议是所有子任务复用的行为规则，任务说明则填写本次工作变量。协议中的“固定版本”指已保存且可恢复的特定内容，不只是一个路径或校验值；候选、checkpoint 和干净重试等用语也在协议开头解释。

调度者必须完整读取[参与者协议](references/participant-protocol.md)。每个 subagent 在开始工作及压缩恢复后直接读取该协议，不依赖调度者转述；

任务说明只填写任务变量，并引用协议的固定版本与绝对路径，不复制或改写一套参与者规则。协议文件及其必需参考须以可恢复版本提供；进行中的任务不因技能文件更新而静默换版。需要例外时明确具体授权、替代保障及影响；与更高优先级指令冲突时停止相关动作并报告。

## 固定任务和权限

先区分“实现方法尚可选择”与“任务行为尚未决定”。前者可以由执行者根据实际结构选择；后者可能改变用户得到的结果，不能借拆任务或换模型代替用户决定。

根级 Main 把用户意图整理成可观察行为、授权边界、必要约束、验收条件和起始基线。嵌套调度者继承父任务给出的这些内容，只能在继承范围内继续切分和调度。

加载本技能不会扩大权限。需要改变行为、授权、范围、起始基线或验收条件时，嵌套调度者向父级报告；需要用户选择产品行为、授权或风险边界时，由根级 Main 决定是否询问用户。
全局采用、全局合并和不可逆清理也由根级 Main 处理，除非用户或父任务已经针对命名对象和动作给出更窄的明确授权。

项目或用户可以声明 Yuna 经验文件的位置。经验只帮助判断相似任务如何切分、调度和恢复，不能替代当前规格、授权或验收条件；没有声明位置时，不搜索、猜测或创建经验文件，也不因此阻塞。

## 选择模型层级和工作角色

模型层级表示预计需要的能力和长期经验成本：

|模型层级|经验成本比例|定义|
|-|-:|-|
|执行级|1|以最低成本完成边界稳定的调查、实现、测试或批量工作|
|思考级|10|处理需要独立语义判断或复杂因果推理的工作|
|顾问级|30|最终能力兜底；诊断执行级和思考级都无法稳定解决的问题，必要时经用户批准后亲自执行|

比例 `1:10:30` 是跨多数实际模型价格形成的长期经验估算，用来比较完成同一任务的整条路线，不是精确账单。

工作角色表示这个 agent 本次交付什么，与模型层级分别记录：

|工作角色|交付结果|
|-|-|
|执行|已批准范围内的主体产物和验证证据|
|事实核对|原始事实、入口、依赖和精确位置，不修改候选|
|独立评审|候选是否满足已固定契约的判断；不参与该候选的实现，不通过时提供修复建议或修复计划|
|整合|已采用切片的组合结果和端到端验证|
|根因分析|连续失败的根因、证据，以及一份供全新执行使用的完整任务说明|

选择时先确定剩余工作需要什么交付角色，再估计能力需求与总成本，最后映射到可用模型；层级不是角色，也不是权限。例如思考级模型可以承担执行角色，但不会因此获得修改任务范围的权力。

只有确定要委派时，才建立模型映射和调度记录。根级 Main 根据当前环境实际提供的模型及思考强度，分别提出“模型层级到模型”和“模型到思考强度”的映射，并说明依据和不确定性，请用户确认。
可用选项变化或无法可靠映射时重新确认；嵌套调度者继承已经确认的映射，不能自行改写。具体模型名和厂商特有的思考强度不写入项目规则。

新的候选实现从执行级开始；事实核对通常也使用执行级，语义评审通常直接使用思考级，根因分析通常使用顾问级。顾问级是能力兜底，不自动获得决定权或更大权限。
匿名比较指隐藏候选的模型身份后进行比较。只有用户确认任务本身没有问题并批准匿名比较后，顾问级才作为执行角色产生候选。

调度者按已确认映射在任务中填写抽象模型层级，并按[参与者资格表](references/participant-protocol.md#开始与停止)核对管理授权；具体模型身份留在调度记录，不要求下级读取隐藏记录。

## 决定直接处理还是委派

可独立交付和验收只说明任务可以交接，不自动触发委派。调度者在任务范围首次清楚时作出判断；之后只比较从当前状态到完成还剩多少工作，不试图回收已经发生的成本。

判断时依次回答：

1. 从现在到完成，还剩哪些调查、判断、修改、验证和收尾？
2. subagent 能否真正承担其中一块尚未完成的工作，还是只能重读现有上下文并照做？
3. 写任务说明、重建上下文、等待、接收结果和验收会增加多少成本？
4. 并行、上下文隔离或独立判断能否带来足以抵消交接成本的收益？
5. 当前角色、用户授权和风险是否限制了谁能决定或执行？

如果操作对象、期望结果、做法和验证都已由当前上下文唯一确定，执行时只需判断成功或失败，这项工作就是“现成动作”。
读取已知目标、查看 diff 或状态、运行已知验证都不改变这一判断。已经核实改动内容、暂存范围和验证结果后，执行一次本地提交通常属于现成动作。

如果委派既不能移走尚未完成的实际工作，也不提供并行、隔离或独立判断的收益，调度者直接完成。
另一名 agent 能承担一块尚未完成的调查、判断、实现、批量处理或耗时验证，且节省的工作足以抵消交接成本时，先把它切成可分别验收的任务再委派；
并行、上下文隔离和独立判断带来的收益也计入这项比较。执行中出现未知状态、行为含义变化或范围明显扩大时，停止直接处理并重新判断。

不要用文件数、代码行数或命令名称代替上述分析，也不要先完成本可交接的主体工作，再把剩余动作解释成直接处理的理由。

## 切片和派遣

切片是可独立交付和验收的一段工作；共同规则是多个切片必须同时遵守的约定；接缝是它们组合时共享的数据、状态或调用关系。先判断各切片分别正确是否足以保证整体正确，再决定是否需要单独验证接缝。

发起调度的 agent 负责定义任务切片，并在联系 subagent 前提供自包含的任务说明。切片按可独立验收的结果和责任边界划分，不按文件数量划分。
简单任务的任务说明本身就是执行依据；需要执行计划时，调度者必须在派遣前形成并批准计划，并把正文或链接放入任务说明。

执行者的来源读取、实施边界、停止条件和角色交付按[参与者协议](references/participant-protocol.md)执行；任务说明链接必要权威和批准计划。

任务说明中的来源分为三类：

- 必须读取的权威来源；
- 建议优先查看的调查入口；
- 为保持隔离而明确禁止读取的材料。

只禁止当前任务确有隔离需要的文件或 skill，不得一概禁止加载所有 skill。

相关切片只共享完成组合行为所需的最小共同规则。共同规则由其拥有者维护版本；嵌套调度者不能改写继承的规则。
Git worktree（关联工作树）为同一仓库提供独立检出的目录。多个写入者、共享可变状态或需要独立基线的任务使用隔离 Git worktree；共同组成同一流程、状态机或协议的切片另设接缝或整合任务。

实际派遣、补充说明、恢复、失败记录或报告时，读取 [调度记录与恢复](references/dispatch-records.md)。
需要隔离写入或准备清理指引时，读取 [Git worktree 隔离与清理](references/git-worktrees.md)。管理下级时，只读取与当前环境匹配的适配文档：

|环境|适配文档|
|-|-|
|Codex|[Codex subagent 交互](references/codex-subagent.md)|

没有适配文档时，遵循当前环境提供的 subagent 接口；适配文档只补充工具交互，不改变本文件的权限和调度规则。

## 处理结果和升级

升级用于处理相同条件下反复未达标的候选，不用于弥补缺失授权或不可恢复输入。判断时先确认固定任务材料是否相同，再确认是否已交付完整候选并得到正式评审结论，最后才累计失败；否则更换模型也不能证明解决了原问题。

执行结果只有三类：

|结果|判定|后续|
|-|-|-|
|已完成并通过|执行者声明完成，规定的门禁及必要评审均通过|可以进入整合或采用|
|已完成但评审未通过|执行者交付完整候选，正式评审判定不通过|任务条件仍相同时，记为该层级一次有效失败|
|停止并报告|尚未声明完成，发现冲突、条件不足、权限或范围问题，或现有条件无法通过门禁|调度者先处理原因，不记为模型失败|

声明完成前发现的缺陷由执行者继续修复，或在无法继续时停止并报告。缺少规定产物或验证不能声明完成。停止后，只有任务说明、外部条件或调度安排发生了能提高成功机会的实际变化，才重新派遣。

同一任务条件下，一个模型层级出现三次有效失败才升级。执行级失败后，新的思考级执行者从相同的固定任务材料开始；如果思考级也失败，由顾问级根因分析者读取固定任务材料和相关候选、评审、修复指导及验证证据，找出任务说明、执行、评审或环境中真正的问题。

根因分析者分别交付诊断报告和只表达当前正确目标的任务说明。调度者只核对新任务说明没有改变行为、扩大权限或代替用户作产品与风险决定，并确认基线、来源和验收完整；不重复调查或转写。
随后，一名全新的思考级执行者只收到这份任务说明和本次运行所需信息，不接触旧候选、旧评审、checkpoint、诊断过程或执行者身份。
详细的失败计数、干净重试和人类介入条件见 [调度记录与恢复](references/dispatch-records.md)。

任务说明本身若被发现有实质错误，停止自动重试并交给用户。
顾问给出的同一任务说明下，思考级执行者连续三次交付候选且仍未通过顾问评审后，也必须请用户介入：用户给出修正方向时，从执行级重新开始；用户确认任务说明正确并认为需要更强模型时，才读取 [匿名模型比较](references/anonymous-comparison.md) 并申请相应实验。

## 决定是否独立评审

委派和评审分别判断。调度者根据需要证明的条件、已有机器证据、风险和接缝决定是否评审；使用了 subagent 或存在多个写入切片都只是信号，不自动触发固定数量或固定角度的评审。

|尚未被证明的内容|合适的处理|
|-|-|
|没有；机器门禁已覆盖全部重要条件|使用执行结果，不增加独立语义评审|
|范围、状态或记录是否完整|执行级事实核对|
|行为是否符合契约，或跨切片语义是否闭合|思考级独立评审|
|高风险条件无法由机器证据充分证明|按风险切分事实核对和语义评审|

需要独立评审时，评审者不参与被评候选的实现。调度者可以按问题是否能分别判断、上下文是否过长和风险，使用一个或多个评审者；它阅读全部结论，判断理由、冲突和覆盖，需要新证据时再派事实核对或新的独立判断。

评审不通过时，评审者为每个缺陷给出可以直接执行的修复建议；缺陷相互依赖或修复顺序会影响正确性时，由评审者进一步给出完整的修复计划。
调度者核对建议或计划没有改变既定行为、授权、范围和验收后，直接把它交给执行者，不重新推导或转写。需要改变这些条件时，评审者只报告具体冲突，由调度者按权限规则处理。

## 整合、完成和清理

保存、采用、合并和清理是四个不同决定：保存保留可恢复内容，采用确认使用哪份候选，合并把候选纳入目标分支，清理删除临时资源。前一项完成不自动授权后一项。

派遣前、收取候选后及启动下一轮修改前，调度者执行[交接检查](references/dispatch-records.md#交接检查)。未保存的代码状态不得作为固定起点或已冻结候选；本地候选保存与全局采用分别处理。

整合者只读取最终固定基线、已采用切片、当前共同规则、已知接缝和端到端验收条件，不读取切片对话、旧 checkpoint 或未采用候选。发现冲突时报告调度者，不自行改变继承条件。

任务完成必须有可核验的结果：所有有效切片已经交付或取消，需要的整合、门禁和评审已经完成，没有未决的产品、授权或风险问题，临时资源已记录，根级 Main 已明确采用最终候选。
根级 Main 看方向、契约覆盖和证据是否足以支持采用；证据缺失时派合适角色补齐，不机械重做下级已经完成的调查或评审。

Git worktree、对应任务分支和会话临时记录默认只生成供人类执行的清理指引；用户明确要求 agent 代为清理时，以用户给出的命名范围为准。不可逆删除仍受前述权限约束。

有证据支持且可复用的任务切分或上下文经验，按项目声明的位置和 [经验记录模板](assets/yuna-template.md) 记录。匿名比较使用单独的正式报告模板，不引用临时调度文件。
