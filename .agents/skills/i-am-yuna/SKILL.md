## Harness subagent 使用指南

- 如果当前是 Codex Harness, 会话开始时必须阅读 [codex-subagent.md](references/codex-subagent.md)

## 调度与模型升级

### 目标与职责

以尽可能低的预计总成本完成任务

- Main Agent 负责理解整体工作流程、判断任务复杂度、与用户澄清需求和授权边界、选择模型层级、整合跨任务结果并作出最终判断
- Main Agent 可以自行执行单次工具调用即可完成的简单操作，例如直接编辑一个文件。具体的任务则调度 subagent 完成
- 边界明确，有明确执行计划的任务通常先交由一个执行级模型驱动的 `subagent` 完成
- 调度前先从当前上下文确认可用模型及其智力层级，否则主动询问用户，不猜测模型名称、智力排序或成本关系
- subagent 的计划、规格、任务单和评审结论由完成该项工作的 subagent 直接写入项目既有约定的位置；Main Agent 不得让另一名 subagent 转写主体内容
- 并行任务必须彼此独立。读取、探索、测试和日志分析可以优先并行；多个 subagent 会写入相同文件、共享可变状态或依赖彼此前序结论时，应改为使用隔离工作区(`git worktree`)。
- 负责的评审 subagent 必须独立于负责的执行 subagent，固定并声明基线、范围、规格来源和标准来源。
- Main Agent 必须维护调度 subagent 的可复核记录，包括任务概述、起始基线、有效尝试次数。该记录存放在 `/tmp/agents/<session>/subagent/dispatch_record.md`，这是模型层次升级的依据之一
- 不得将调度 subagent 产生的元数据传递给 subagent。

### 经验沉淀

`yuna.md` 是 Main Agent 的经验记录，包含了对不同任务的难度评估、模型层级选择和升级决策。

每次会话开始前都必须阅读该文件。

当工作区中没有发现 `yuna.md` 时，向用户询问在哪里创建，然后使用 [yuna-template.md](assets/yuna-template.md) 新建 `yuna.md` 。

### 模型层级与成本

成本是长期使用形成的经验估值，表示不同层级执行同一个任务并最终成功所消耗的总成本，不是单次调用或 token 单价。

|层级|经验成本|适用工作|
|-|-:|-|
|执行者级(低智力层级)|1|明确指令、稳定边界、工具调用和机械执行|
|思考者级(中智力层级)|10|因果推理、复杂状态|
|顾问级(高智力层级)|30|任务反复执行失败后的顾问、解决最难的问题|

**注意：执行者级级价格低廉，如果 Harness 允许指定思考等级，直接使用最高等级**
**注意：低智力层级是相对于高智力层级而言，不意味着笨拙愚蠢。**

#### 基线与尝试

开始执行前固定两个权威输入：

- `B0`：任务开始前的代码、数据和环境基线。
- `C0`：任务提示、行为契约、授权边界和验收条件组成的上下文。

任务按产物边界分为两类：

- **执行任务**会修改仓库状态并交付可合入的代码、文档或配置。调度这类 subagent 前保持 Git 工作区干净，并要求其在产物完成且验证通过后提交。只有这类任务的提交问题无法处理时，才升级给顾问或人类。
- **只读任务**只进行调查、探索、测试、日志分析或证据整理，不修改仓库状态，也不要求提交。其结果必须写入指定证据文件，或通过约定的结果文件交接。

同一委派同时包含两类工作时，分别适用对应规则；不得为了满足提交要求给只读任务制造仓库变更。

执行任务的一次有效尝试是指：

1. 负责执行任务的 subagent 接受指示开始执行任务
2. 负责执行任务的 subagent 汇报执行完成
3. 负责评审的 subagent 对任务结果进行评审
4. 如果评审通过，则该尝试被认为是有效的。否则，负责评审的 subagent 需要记录评审结论并给出具体的执行计划，供下一轮尝试使用。

只读任务不使用上述提交型尝试计数；完成依据是指定范围已覆盖、证据定位完整、结果文件已交接，并在任务要求时完成独立核验。

一个模型层级最多连续尝试三次；同一层级内，后一次可以根据本层级前一次的结果、验证证据和评审意见继续修正。

三次尝试之后，若满足以下任一条件，视为失败：

- 重复违反同一行为契约或不变量；
- 修复一个缺陷后引入另一个缺陷，结果始终不能向验收条件收敛；
- 只减少部分表象，但仍不能满足行为契约和验收条件。

**注意：不得仅以缺陷数量减少认定任务已经完成。**

#### 提升模型层级

|状态|判定条件|下一步|
|-|-|-|
|执行者级成功|三次内满足验收条件|采用结果|
|执行者级失败|三次后仍有同类问题|升级到思考者级|
|思考者级成功|从 `B0` 和 `C0` 重新开始，三次内满足验收条件|采用结果，并请顾问级评估者记录难度|
|思考者级失败|重新开始后的三次仍有同类问题|请求顾问级评审者对当前评审者的评审结论和执行计划进行修订|
|顾问级完成指导|已完成评审结论和执行计划的修订|向用户申请启动匿名对照评估流程|

**注意：顾问级评审者修订完评审结论和执行计划后，`C0` 需要被视为 `C0 = C0 + 修订内容`**

**注意: 模型层级的失败次数只统计在正确、完整的权威任务上下文中完成且经独立评审失败的尝试。若规格、设计文档、执行计划或其他权威输入被顾问或人类修正，Main Agent 必须固定修订后的上下文并让当前层级从第一次尝试重新开始；此前由错误或缺失上下文导致的失败不得作为升级依据。只有在同一修订上下文下连续三次未能满足验收，才允许提升模型层级。**

### 匿名对照评估流程

#### 申请条件

满足以下条件时必须主动申请开启匿名对照评估流程：

- 当无法可靠地判断应采用的模型层级或者提升模时
- 当模型层级常规升级失败并取得顾问指导后

**注意： `yuna.md` 没有匹配的任务经验记录不是申请的理由。**

#### 申请内容

申请必须完整说明任务上下文、无法可靠判断的原因、拟采用的模型层级、经验成本、隔离和匿名方案及评估目的，并取得用户明确同意。

- 初步判断难度较高，但无法区分执行层级与中等智力层级时，同时比较这两个层级。
- 初步判断极难，且无法判断是否需要高等智力层级时，同时比较执行、中等和高等三个层级。
- 即使初步判断极难，也必须保留执行层级；不得预设执行层级一定失败，也不得预设高等智力层级必须亲自执行。

#### 匿名性要求

使用中性编号替换模型层级、worktree 路径、分支名、提交作者、日志身份和其他来源元数据。
文件名、展示顺序和描述也不得泄露任务执行者的身份。
在进行评估之前，务必保证对照组评估者不会获得关于任务执行者的任何信息。

#### 对照组执行流程

1. 分别派遣三个由不同模型层级驱动的 `subagent` 从 `B0`、`C0` 开始执行任务。
   代码任务中，每组使用从同一 `B0` 创建的独立 Git worktree；其他任务使用具有同等隔离性的环境。各组不得读取其他组的产物或共享可变状态。
   每个 `subagent` 独立完成任务，同样最多进行三次尝试。
2. 每当一个 `subagent` 宣布完成执行，则派遣对应的评审 `subagent` 对其结果进行评审，如果评审不通过，则递交评审记录和执行计划的路径给该层级的 `subagent` 阅读并进行下一轮尝试。
3. 将每个 `subagent` 的尝试状态记录到 `docs/comparison.tmp.md` 中，直到所有负责执行的 `subagent` 都结束其尝试（完成或尝试三次后失败）。执行状态或结果无法判断时，请求人类介入。
4. 派遣一个新的对照组评估者 `subagent` 对每个负责执行任务的 `subagent` 的执行的最终结果进行评估，评估者不得修改、综合或重新实现任务产物。
5. 对照组评估者需要在 `docs/comparison.tmp.md` 中记录每个 worktree 的最终结果、评审结论和执行计划，并对任务难度进行判定。
6. 对照组评估者完成评估后，向 `Main Agent` 索要 worktree 对应的任务执行者的身份信息，并维护 `yuna.md`。

**注意：匿名对照组的评估者是 `yuna.md` 的唯一写入者，且只在匿名评判固定后写入记录。**

**注意：`Main Agent` 必须给对照组评估者 `subagent` 提供详细的流程指导，因为 `subagent` 不一定会加载该 skill**

**注意：流程中的执行和评审 `subagent` 不得复用任何流程启动之前的 `subagent`， 必须重新创建**

#### 对照后的状态转换

|对照结果|后续动作|
|-|-|
|执行者级或思考者级满足验收条件|维护完 `yuna.md` 后评估流程结束|
|执行者级和思考者级均失败，顾问级参加且成功|维护完 `yuna.md` 后评估流程结束|
|执行者级和思考者级均失败，顾问级未参加|由顾问级从 `B0` 和 `C0` 亲自执行，三轮机会重新计数|
|执行者级和思考者级均失败，顾问级参加且三轮均失败|请求人类介入|
|任何结果无法可靠判断|请求人类介入|

**注意：负责执行的顾问级 `subagent` 必须重新派遣，不得混用可能存在的任何顾问级评审者。
