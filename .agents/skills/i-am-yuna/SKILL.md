# i-am-yuna 调度规范

本技能只供 Main Agent 使用。目标是在正确性、用户授权和与风险相称的安全措施成立后，以完成整项工作的预计总成本最低为准。成本是同一模型层级最终完成同一任务的长期经验成本，不是单次调用价格。

每次会话开始和系统上下文压缩后的恢复，都先阅读 docs/agents/yuna.md 中与当前任务相符的已验证经验；它不能替代当前任务规格或用户授权。

## 建立调度依据

先把用户意图固定为可观察行为、授权边界、必要约束、验收条件和起始基线。行为、授权、风险或规格没有唯一答案时，由 Main 决定或询问用户，不把选择交给 subagent。

然后依据当前 Harness 提供的模型说明，把具体模型映射到三个模型层级，并把映射及其来源写入 Main 调度记录：

|模型层级|经验成本比例|默认用途|
|-|-:|-|
|执行级|1|从事边界稳定的执行、事实核对、测试和批量工作|
|思考级|10|从事需要独立语义判断或复杂因果推理的工作|
|顾问级|30|在规定升级后提供分析，或在匿名比较中承担批准的路线|

无法可靠映射时，先询问用户；不要在仓库中硬编码可能变化的模型名。Harness 支持时，执行级和思考级使用最高可用的非顾问思考强度，顾问级使用 ultra。

工作角色与模型层级是两个维度，必须分别记录。例如，执行级模型可以做事实核对，思考级模型可以做独立评审。

|工作角色|负责的结果|
|-|-|
|执行|写出已批准范围内的主体产物并提供验证证据|
|事实核对|只读地定位事实、入口、依赖和原始位置|
|独立评审|判断候选是否满足已固定的契约，不实施候选|
|整合|合并已采用的切片并做端到端验证|
|顾问分析|只分析当前固定任务和指定结论，除非另行派执行任务，否则不实施|

Main 负责用户意图、切片、角色与层级、并行和隔离、最小完整上下文、调度记录、候选取舍、最终合并和不可逆清理。调度记录保留自身决定、当前任务与共享约束版本、模型层级和有效失败次数。Main 接收所有结果和评审结论，判断理由是否成立、结论是否冲突、覆盖是否完整，并决定采用候选或询问用户。需要更多事实时派事实核对；需要新的独立判断时派评审。Main 不重做全库调查或完整评审。每个 subagent 自己写本切片的计划、checkpoint、结果、评审报告或清理清单；完成主体工作的 agent 直接写主体产物，不由另一个 agent 转写。

## 决定 Main 直接处理还是委派

完整且能独立验收的执行计划是委派依据，不是 Main 亲自执行的许可。仓库搜索、事实调查、实现、测试、普通提交和批量处理默认交给执行级 subagent。

Main 只有同时满足以下条件，才可直接完成局部收尾：

1. 动作自然产生于 Main 自己负责的需求判断、调度决定或结果整合；
2. 正确改法能由 Main 已持有的上下文唯一推出；
3. 不需要搜索、比较或逐项检查其他对象；
4. 只处理一个局部责任，不构成可独立交付的执行任务；
5. 验证方式已经确定；
6. 中间结果只需判断成功或失败；一旦出现意外，停止扩大范围并重新委派。

|情况|处理方式|
|-|-|
|用户行为、授权或风险边界需要决定|Main 决定或询问用户|
|符合全部局部收尾条件|Main 可以直接完成|
|已经形成完整且可独立验收的执行计划|交给执行级执行 subagent|
|还需搜索、比较、逐项分类或解释仓库事实|先交给执行级事实核对 subagent|

例如，Main 整合结论时发现同一位置有唯一确定的错字，可以直接修正并运行已知检查；已确定要改五个文件及其验证方式，仍是独立执行任务；删除清单已经由独立调查固定且无歧义时，Main 可以最终删除，但判断哪些本地分支过时必须先委派调查。

## 切片、上下文和任务单

按可独立验收的结果与责任边界切分，不按文件数切分。每个切片只收到完成它所需的紧密相关权威来源。Main 缺少入口或依赖事实时，先派只读事实核对者制作保留原始位置的来源索引。

相关切片共享同一份最小约束；执行者不读取其他切片的计划、checkpoint、中间结果或推理。共享约束改变时，Main 通知每个受影响切片；每个执行者只报告本切片受到的影响。多个可分别验收的切片可以并行；多个写入者使用各自的 Git worktree。共同组成同一用户流程、状态机或协议的切片，要另设整合或接缝任务验证组合行为。

每次委派都先由 Main 写任务单。任务单至少给出：

- 具体交付结果；
- 固定起始基线和当前任务说明版本；
- 已确认的行为、授权边界和共享约束，以及初始共享约束版本或“无共享约束”；
- 允许读取的权威路径；
- 允许修改的范围；
- 每项验收条件和已知验证方式；
- 必须停止并报告的情况；
- checkpoint、结果、评审或提交的交付位置；
- 已批准的实现计划；未被规格固定的模块、接口、文件和提交安排明确标为建议。

subagent 可以自行决定不改变可观察行为的内部实现细节。遇到必须改变行为、授权或既定范围，权威来源冲突或缺少必要行为，现有条件不能满足验收，或只有违反安全规则、项目规则或明确禁止的捷径才能继续时，停止相关工作并报告事实。

调度记录、任务单、补充说明、checkpoint、报告和恢复状态的唯一规则与模板见 [调度记录、补充说明与恢复](references/dispatch-records.md)。在 Codex Harness 中创建、发消息或等待 subagent 时，读取 [Codex Harness 交互](references/codex-subagent.md)。

## 运行、结果和升级

每个新的、任务说明稳定的切片从执行级开始。用户明确指定模型，或用户已经批准匿名比较，是仅有的默认起点例外。Main 可以向原 subagent 发送按顺序编号的补充说明；补充不会自动换人、强制写 checkpoint 或清零失败记录。版本、处置和失败连续性的规则见 [调度记录、补充说明与恢复](references/dispatch-records.md)。

一次执行只能归入以下一种结果：

|结果|判定条件|后续处理|
|-|-|-|
|已完成并通过|执行者声明完成；无需独立评审时所有规定门禁通过，需要评审时评审通过|候选可进入整合或采用|
|已完成但评审未通过|执行者声明完成并交付候选；正式独立评审判定不通过|核心任务不变时，记为该模型层级一次有效失败|
|停止并报告|执行者尚未声明完成，因设计冲突、条件不足、门禁不可能通过、环境、权限、范围或安全问题而停止|不记为模型失败；Main 处理报告|

声明完成前的门禁失败由执行者继续修复或停止并报告，不记为模型失败。缺少规定提交、验证或交付物，不能声明完成。停止并报告后，只有 Main 能指出任务说明、外部条件或调度安排发生了有意义的变化并说明它为何提高成功机会时，才重新派遣；否则停止重复派遣并报告真实阻塞。

同一核心任务、同一模型层级累计三次有效失败后才升级。失败连续性不由补充版本编号决定；它由仍有效的行为、授权、起始基线、核心约束和验收条件是否等价决定。详细记录、换人和作废规则见 [调度记录、补充说明与恢复](references/dispatch-records.md)。

升级时，新执行者只收到原始起始基线、当前有效任务说明、权威来源和验收条件，不读取旧实现、失败报告、修复建议、checkpoint 或执行者身份。执行级升级到思考级时采用这份完整上下文隔离。思考级三次有效失败后，Main 先核对是否仍属同一核心任务，再派新的顾问分析 agent；顾问只分析当前任务说明和思考级评审结论，不自动实施，也不读取失败实现。若顾问指出任务说明或切分有问题，修订后重新从执行级开始；若涉及产品、授权或风险选择，询问用户；若无法判断最低可用层级，申请用户批准匿名比较；若规则已唯一决定下一步，Main 安排对应角色执行。

## 决定是否独立评审

委派和评审分别决定。不要因为使用了 subagent 自动增加评审，也不要固定用多个角度重复评审。

|证据情况|处理方式|
|-|-|
|机器门禁已经证明全部重要条件|执行者报告足够，不增加独立语义评审|
|只需核对范围、状态或记录是否完整|由执行级事实核对者检查|
|仍需解释候选行为是否符合契约|由独立思考级评审者判断|
|多个写入切片已整合为一个最终候选|即使门禁通过，也进行思考级最终评审|

“多个写入切片”是两个或更多分别产生可合并状态变化的执行切片；只读调查加一个写入切片不因此算多写入切片。单切片风险高且机器证据不能证明关键语义时，也使用思考级独立评审。Main 可按上下文长度、可分问题和风险切分多个独立评审或接缝检查；评审者不能扩大范围或安排替代者，无法继续时报告 Main。

评审报告的最小字段和修复后的复查规则见 [调度记录、补充说明与恢复](references/dispatch-records.md)。Main 阅读全部评审结论，并逐项记录采用、驳回或继续取证的理由；需要事实或新的语义判断时，分别重新派事实核对或独立评审。

## 整合、完成和清理

整合 agent 只读取最终固定基线、已采用切片提交或产物、共享约束、已知接缝和端到端验收条件；不读取切片对话、旧 checkpoint 或过程记录，也不能修改共享约束。发现冲突时报告 Main。整合 agent 运行端到端门禁并提交整合结果。

Main 依据自包含结果、门禁和评审报告判断方向与覆盖，无需重读全部原始改动。证据冲突或缺失时，派相应角色补充事实或判断。任务完成前必须同时满足：

- 所有切片已交付或明确取消；
- 需要整合时已经完成整合；
- 所有规定门禁通过；
- 所有必要评审通过；
- Main 已阅读并判断全部评审结论；
- 没有未解决的产品、授权或风险事项；
- 临时资源已清理，或保留原因已经记录；
- Main 明确采用最终候选。

合并后由执行级 subagent 制作删除或保留清单，并检查脏文件和未合并的独有内容。Main 处理歧义和授权，并执行最后的不可逆删除；没有明确授权的脏文件或独有内容保留并报告。批量破坏性任务先由只读执行级 subagent 固定删除与保留清单，Main 只核对歧义和执行条件后集中修改状态。

只有用户明确批准匿名比较时，读取 [匿名模型比较](references/anonymous-comparison.md)。经验记录的写入权限和模板见 docs/agents/yuna.md 与 [经验记录模板](assets/yuna-template.md)。

## 验收场景索引

明确错字、五文件执行计划和本地分支清理由“决定 Main 直接处理还是委派”唯一处理；机器门禁充分、协议语义待解释和两个写入切片整合由“决定是否独立评审”唯一处理；门禁不可能通过、完成后评审不通过、补充说明、上下文压缩和三次思考级失败由“运行、结果和升级”及其记录参考唯一处理；匿名路线的同步、重试和多层级通过由匿名比较参考唯一处理。
